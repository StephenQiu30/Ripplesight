# 热点事件需求核对

**这是 AI 整理的候选，不是用户已确认需求或已派发任务。尚未编写 POC 代码，尚无业务验证结果。** 来源是本轮用户对热点事件配置的询问，以及[需求与验证入口](../product/reference/04-需求与验证入口.md)中的最新反馈。

## 先把“热点事件”讲清楚

| 可能的意思 | 现有依据 | 需要核对的用户结果 |
|---|---|---|
| 按个人关键词发现相关内容 | [关键词热点](../capabilities/02-关键词热点.md) | 配置一个关心的主题后，能看到哪些命中及其来源 |
| 知道各平台今天最热的事 | [每日社媒热点](../capabilities/03-每日社媒热点.md) | 不设关键词，也能看到某个平台的当前热点 |
| 把多篇报道归成事件并显示关注度 | [事件服务](../../../backend/app/events/services.py)、[热度服务](../../../backend/app/events/heat.py) | 同一事件为何合并、为何排在前面，能否回到证据核实 |

这三种需求的输入、输出和成功条件不同，不能直接合成“接全平台并完善事件系统”。本轮尚未确定哪一种是首要问题。

## 可选的最小验证：一个主题的一次命中

以下范围全部是待核对提案，选择它不意味着排除其他产品目标。

| 项 | 提案 |
|---|---|
| 用户场景 | 我关心一个具体主题，希望集中看到相关内容，并判断是否值得继续读 |
| 唯一假设 | 一个已接入来源的真实内容，经过关键词规则后，能提供用户认为相关且可追溯的结果 |
| 输入 | 一个主题、一组明确关键词、一个已有来源、一个固定时间窗口；具体值待选定 |
| POC | 复用现有路径执行一轮，记录真实取得的内容、命中与未命中及失败原因 |
| demo | 用户从主题和规则走到命中列表，看到来源、时间、匹配理由，并打开原文核对 |
| 成功条件 | 本轮能复跑；用户能判断内容是否相关；来源与失败情况清楚。不预设命中条数，预期为空的案例也应正确呈现 |
| 失败条件 | 来源取不到、关键词含义不一致、结果无法追溯，或用户判断没有帮助；失败原因分别记录 |
| 本轮排除 | 新来源、多平台、调度、AI 事件归并、评论情感、热度排名、报告与告警 |

如果真正的问题是“事件如何归并或热度是否合理”，就换成已有真实报道的一次归并/复算，不先做关键词采集。**选哪一个仍待用户明确场景。**

## 开始前只需要收敛这些答案

1. 用户最希望得到的是个人主题命中、平台热点，还是多报道事件？
2. 用哪一个具体主题/事件和已有来源演示？看见什么结果，用户会认为有用？
3. 本轮是否需要真实在线采集，还是先用可追溯的已有真实样本核对下游？后者不能证明采集接通。

答案回来后，用[POC 验证卡](../product/reference/06-POC验证卡.md)替换提案中的待定值；本轮不为填满整份 PRD 增加问题。旧文档和源码只能作为核对依据，不能替用户选择答案。

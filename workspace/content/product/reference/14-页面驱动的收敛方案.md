# 页面驱动的收敛方案

2026-10-08 用户纠正：不要以文档数量为审查标准；根据当前前端展示的数据、功能需求和操作反推数据库，替换历史冗余设计与实现。本方案直接替换上一版“为所有设计缺口预建完整系统”的做法，不新增另一套任务进度。实施入口为[页面 PRD](../prd/03-PRD-全站页面需求.md)，状态在 BACKLOG。

## 取舍标准

一个持久化字段必须回答：哪个页面显示或修改它、谁负责写入、为何刷新后仍要保留、哪个查询读取、删除或变化后怎样处理。只有布局、标签、过滤、计数或临时选择需求时，优先使用组件、URL、查询或本机状态。后台任务、身份隔离、许可和历史版本属于运行依赖，不能因为不直接显示就删除。

分析依据是路由、实际调用组件、生成客户端、后端合同与唯一 schema。静态依赖闭包只是检索起点；公共组件导入某函数不等于每个页面都会调用它。没有进行新的真实采集、外发通知、生产压测或业务库迁移。

## 当前用户流程

| 流程 | 页面需要的最小能力 | 当前取舍 |
|---|---|---|
| 发现 → 阅读 → 核对来源 | 首页/探索的有界列表、事件与材料关联、详情、固定日报 | 保留公开许可和版本；首页统计由响应计算，不新建统计中心 |
| 收藏 → 找回 → 导出 | 本机ID/时间、回读可公开材料、当前选择导出 | 保留现有本机实现；撤销云同步、备注、同步墓碑设计 |
| 关键词 → 结果 → 评论 | 主题规则/来源/频率、原任务回执、最近5条结果、完整资料/评论 | 复用主题、jobs和content；停止第二套批次状态机 |
| 失败 → 定位 → 恢复 | 来源准入、窗口缺口、任务阶段/原因、允许的重试/取消 | 保留必要后台明细，不发展通用调度/采集平台 |
| 榜单 → 模型 → 证据 | 固定轮次、评分依据、来源协议、价格单位/日期 | 保留当前查询；不新增名次历史、交易或计费体系 |
| 辅助维护 | 事件修订、刊期生产、来源/模型/站点配置、文档编辑 | 现有入口继续工作，新增投入由真实问题决定，不与主流程等优先 |
| 对外分发 | 既有RSS、海报、MCP/Agent兼容代码 | 继续遵守冻结决策，不作为本轮建设或真实外发验收任务 |

## 已撤销的设计与替代方案

这里的“撤销”指撤销尚未落地的工程设计，不是删除运行中的业务数据。

| 历史设计 | 取消原因 | 当前替代 | 重新引入的唯一前提 |
|---|---|---|---|
| reading_bookmarks、reading_event_follows | 当前只有本机收藏，没有云同步/事件关注完整交互 | localStorage ID/收藏时间，公开接口回读 | 用户明确要跨设备收藏/事件关注，并先确定冲突、隐私和删除行为 |
| reading_operations | 为未存在的云写入再造通用账本 | 当前收藏同步本机写；已有异步导出沿用jobs | 有不能由现有事务/Job满足的已确认操作 |
| monitor_run_batches、monitor_run_batch_sources | 现有“立即运行”已有来源结果和job_ids；没有历史批次列表控件 | 原运行响应、jobs、到期窗口；刷新回执不足单独处理 | 先给出跨刷新恢复/全部跳过历史的用户故事和最小合同；不要预先复制Job状态 |
| event_sentiment_snapshots | 当前事件阅读没有可信情感比例数据与稳定展示合同 | 已有content_annotations逐条阅读；现有热度用attention_snapshots | 先验证真实样本和分母，再决定查询是否需要物化 |
| alert_read_states、alert_read_operations | 当前告警页是规则与评估历史，没有已读操作 | 原规则/版本/评估/投递状态 | 出现明确通知收件箱及已读交互需求 |
| 通用候选关联、四档相关性、时间可信度新结构 | 旧POC设计不等于当前页面必需字段 | 当前内容身份/观察/布尔相关性与错误状态；保留时间来源 | 页面或质量实验给出可复核缺口后单独设计；不将旧bool自动转换成四档 |
| 首页overview、公开情感/趋势、收藏同步新端点 | 由设计空位直接推导API，缺少实际动作和数据来源 | 已有四路查询并行；当前范围计数；未知留空 | 用户确认控件、统计范围和源数据，并证明旧查询不能满足 |
| 百万观察/千主题统一容量门槛 | 没有当前业务负载证据 | 按真实页面页大小、权限和状态测试，容量测量单列 | 有数据量/请求量基线或明确目标 |

## 代码和存储清理判定

| 对象 | 调用证据与决定 | 清理边界 |
|---|---|---|
| PageContainer旧header插槽 | 当前唯一使用方BasicLayout不传header，Figma版页内自行提供标题 | 本轮删除该未使用prop、固定header分支与Separator导入；保留正文滚动和登录页脚 |
| /topics、/monitors/[topicId]、/workspace | 都使用同一个TopicsWorkspace，workspace另有管理导航 | 已共用，不再创建新服务；删除路由会破坏现有链接，因此保持兼容 |
| 公私内容和公私报告 | 看起来相似，但有不同授权/投影/修订语义 | 共享展示组件；不能直接合并存储读取边界或删除许可校验 |
| 字段版本/观察/成员关系 | 当前评论追溯、旧主题规则、事件修订和刊期引用都在使用 | 保留；不能简单压成一张JSON表破坏约束 |
| 后台jobs/租约/outbox/预算/审计 | 来源页和任务页之外，Worker/调度/恢复也会读写 | 保留运行链；“前端没有直接调用”不是死代码证据 |
| 历史辅助子系统 | 榜单、Codex公告、评测和发布管理仍有实际入口或后台调用 | 暂缓扩展；先关闭准入、核查调用、外键和数据保留，再分切片退役 |
| 运行提示词与第三方署名 | 服务运行时加载或许可证要求，不属于旧需求冗余 | 不按文档数量删除或重写；与需求清理分开 |

静态路由依赖检查未找到可直接整目录删除的非UI业务组件。该检查不能证明所有导出都被使用，也不能证明后端无冗余。本轮只删除有明确零调用证据的header分支；后续物理删表/大模块删除必须经过下列关口。

## 后续真正需要处理的缺口

| 问题 | 当前证据 | 最小下一步，不预建平台 |
|---|---|---|
| 页面中的“本页”与“总量”容易混淆 | 首页20条/4事件；主题仅最近5条；热点目录最多20条 | 维持范围标签；若需要总量，先定义过滤/时间口径后增加单个聚合字段 |
| 主题立即运行回执跨刷新不足 | 当前客户端保留回执、任务可查询；没有独立批次历史界面 | 先验证恢复需求，优先通过已有operation/jobs或最小查询补足 |
| 部分辅助选项可能拉取过多 | 告警选择器最多100页，每页主题50/事件100；运营部分目录未分页 | 实测达到规模后改为按需搜索选择；不要先加缓存服务 |
| 收藏20项逐条授权回读 | 本机只存ID，避免复制许可内容，但有有界多请求 | 测瀑布；确有瓶颈才加最多20ID的批读，保持逐项授权，不先建云收藏 |
| 情感、趋势和海外数据缺少完整证据 | 设计中出现，不代表当前服务可用 | 保持缺省/说明；先做单一真实样本验证，不填假数据 |
| 内部文档阅读副本与仓库不同 | 正式工作台读已发布快照，不直接读仓库目录 | 单页需求登记到内部允许清单；已有独立副本需审查合并后发布，不能重初始化覆盖草稿 |

## 退役实施关口

确定具体页面不再需要 → 查前端、API、后台任务、导出、运行提示词和运维脚本的消费者 → 停止该功能的新写入并保留兼容读取 → 明确历史数据去向和外键依赖 → 在独立库实际备份恢复/导入验证 → 切换并验证核心页面 → 最后移除代码和表。没有数据迁移证据就只撤销未实施提案，不能把“精简设计”当作对业务库执行DROP的许可。

验收以当前用户能走通的主路径为准，详见[跨页场景](11-全站验收场景.md)。设计取舍完成、代码检查通过、真实平台验收和长期稳定运行分别报告。

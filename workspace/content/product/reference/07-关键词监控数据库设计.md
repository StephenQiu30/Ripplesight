# 关键词监控数据库设计

本页回答：为了让本人从配置关键词走到可追溯的国内帖子与评论，需要保存哪些事实，现有数据库能复用什么，哪些增量确有必要。需求以[总 PRD](../prd/01-PRD.md)为准，免费采集能力依据[GitHub 调研](../../research/2026-10-07-GitHub免费热点与评论采集调研.md)，架构约定以 [PROJECT](../../../../PROJECT.md)为准，进度仍只在 [BACKLOG](../../../../BACKLOG.md)。

**本页为设计提案，不是建表脚本或迁移完成记录。** 2026-10-07 只读审查了仓库 DDL、ORM 和相关服务；没有连接数据库、运行采集、调用模型或执行数据库测试。当前运行库的实际结构、行数和性能均未核验。唯一可执行 DDL 仍为 [schema.sql](../../../../backend/database/schema.sql)，本轮未修改它。

采用 `pm-execution:create-prd` 的需求—目标—约束梳理方式与 `pm-execution:test-scenarios` 的可观察场景方法。本页补充数据设计，不复制一份 PRD；新增字段和表名均为 AI 提案，待按验证卡确认后再进入实现。

## 设计边界与结论

现有结构已经具备主题与来源版本、任务租约和检查点、内容标识与版本、评论关系、AI 回执、覆盖窗口和证据留存。优先沿用这些实体。当前建议最多新增一张通用的**主题候选关联表**；其余用必要字段和约束演进补齐，不另建帖子库、评论库、用户库、任务平台或向量数据库。

以下是本轮需求对数据的直接要求：

- 保存有界的过滤前候选、实际查询和去除原因，才能检查漏判与比较关键词基线。
- 相关性使用“直接相关、弱相关、无关、信息不足”四档；模型未运行、失败和无关分开。暂不引入连续数值分数或模型自报准确率。
- 原帖、直接父评论、根评论、回复目标分别保存；缺父链明确标记，不猜补。
- 来源发布时间、首次发现、抓取观测、入库、结果可读是不同时间；时间未知不补成刚发布。
- 规则、来源配置、采集器及分析版本固定到运行；历史结果不能随当前配置改写。
- 新运行的窗口统一为 UTC 半开区间 `[start, end)`；上游边界不同，适配后在本地统一过滤并去重。
- 取数零第三方服务费用、本人单账号及既有凭据边界继续生效。数据库保存会话引用和版本，不保存 Cookie、token、密码或可还原的登录响应。

本次只支持设计判断。表存在、源码有写入路径和真实平台已接通，分别是不同结论；国内 POC 不以 HN 或海外样本代替。

## 现有数据事实

以下字段、约束和删除行为来自当前 `schema.sql`，不是建议结构。表内列的是当前链路需要的字段；完整定义由链接的唯一 DDL 提供，不在文档维护第二份建表文本。主要 ORM 对照为 [monitors/models.py](../../../../backend/app/monitors/models.py)、[connections/models.py](../../../../backend/app/connections/models.py)、[jobs/models.py](../../../../backend/app/jobs/models.py)、[content/models.py](../../../../backend/app/content/models.py)、[analysis/models.py](../../../../backend/app/analysis/models.py)、[evidence/models.py](../../../../backend/app/evidence/models.py)。本轮做了结构阅读，没有执行 ORM 与实际数据库一致性断言。

### 主题、连接与运行

| 现有实体 | 真实字段与职责 | 键、索引及约束事实 |
|---|---|---|
| `monitor_topics` | `id, owner_id, name, status, readiness_status, current_version, collection_interval_seconds, created_at, updated_at`；还保留报告设置 | 主键 `id`，唯一 `(owner_id,id)`，索引 `(owner_id,updated_at)`；状态为 paused/active/archived。`current_version` 没有指向版本表的当前版本外键，不能说数据库已完整保证它有效 |
| `monitor_topic_versions` | `topic_id, version, created_by, match_any, match_all, exclude, source_keys, editorial_profile_ids, collection_interval_seconds, created_at` | 主键 `(topic_id,version)`；主题 FK 为 CASCADE；JSON 字段只在 DDL 层约束数组等结构，不等于所有业务规则均由数据库校验。没有 `owner_id`，读版本必须先验证主题归属 |
| `monitor_topic_status_events` | 主题状态变更、原因、规则版本、序号和发生时间 | 唯一 `(owner_id,topic_id,event_sequence)`；主题及规则版本 FK 为 CASCADE，规则 FK 可延迟检查；时间线索引包含 owner、topic、time、sequence |
| `source_connections` | `owner_id, source_key, status, current_version`，以及 `safety_stop_reason, safety_trigger_job_id, safety_stopped_at, safety_stopped_version, safety_events` | 唯一 `(owner_id,source_key)`，当前版本复合 FK 可延迟检查。安全停止完整性 CHECK 当前只允许 `source_key='bilibili'`，推广其他平台需要同步改约束，不能只改界面 |
| `source_connection_versions` | `connection_id, version, owner_id, auth_kind, secret_ref, config, execution_policy, created_by, created_at` | 主键 `(connection_id,version)`；唯一 `(owner_id,connection_id,version)`；连接 FK 为 CASCADE。`config` 和执行策略均有键白名单；`secret_ref` 只接受规定引用形式，浏览器状态引用绑定 owner/connection/version |
| `source_capability_evidence` | connection/version、capability、manual/scheduled、probe/persisted_read、结果、停止原因、组件名与版本、证据引用 | 唯一 `(owner_id,operation_id)`；连接版本 FK 为 CASCADE；成功持久读取要求 `resource_ref`，probe 不允许据此伪装成已持久读取；按来源版本、能力、入口和观测时间查最近证据 |
| `jobs` | `operation_id, kind, configuration_ref/version, source_key/capability, scope, request_fingerprint`；上游/补丁 SHA、adapter version；status、租约、checkpoint sequence/JSON、请求和保存计数、错误与运行时间 | 唯一 `(owner_id,kind,operation_id)`；指纹 32 字节；租约/状态及三个采集版本字段有配套 CHECK；索引 `(status,lease_expires_at)`。通用 configuration 引用和 `scope` 中的 ID 不是数据库 FK，接受任务时仍需业务校验 |
| `monitor_schedules` | owner/topic/source/capability、周期、next_run、enabled、last_job | 复合主键 `(owner_id,topic_id,source_key,capability)`；主题 CASCADE；due 索引 `(enabled,next_run_at)`。`last_job_id` 当前没有 FK |

`jobs.status` 的真实枚举是 queued、running、succeeded、partially_succeeded、failed、cancelled。页面所说“部分完成/模型待处理/需要登录”应从任务、阶段和原因映射，不能假称已有一个通用 `partial` 任务枚举。暂停主题、取消本次任务和禁用来源也不是同一状态。

### 内容、出处、评论和分析

| 现有实体 | 真实字段与职责 | 键、索引及删除语义 |
|---|---|---|
| `content_records` | `owner_id, source_key, object_type, native_scope, external_id, identity_basis, created_at`；类型为 post/comment/webpage | 唯一身份 `(owner_id,source_key,object_type,native_scope,external_id)` 使用 `NULLS NOT DISTINCT`；索引 `(owner_id,id)`。这里保存身份，不保存正文或发布时间 |
| `content_versions` | content、32 字节 fingerprint、title/body、text_scope、text_origin/ref、truncation_reason、created_at | 唯一 `(owner_id,content_id,fingerprint)`；主题无关的正文版本；content FK 为 CASCADE；索引 `(owner_id,content_id,created_at,id)`。不同来源相同正文不会因此合成一条身份记录 |
| `content_observations` | content/version、job、`source_operation_id`、source 身份证明、observed/received/published 时间、URL、作者、互动计数 | 唯一 `(owner_id,content_id,source_operation_id)`；content CASCADE，job 和指定 content version RESTRICT；latest 索引 `(owner_id,content_id,observed_at,received_at,id)`；计数可空且非负；缺失不等于 0 |
| `content_discoveries` | content/job、`first_observed_at, created_at` | 唯一 `(owner_id,content_id,job_id)`；content CASCADE，job RESTRICT；索引 `(owner_id,content_id)`。首次发现目前由相关发现记录求最早值，不是 `content_records.created_at` 的同义词 |
| `content_version_inputs` / `content_observation_inputs` | 版本和派生观测的输入观测关联 | 输出侧 CASCADE，输入侧 RESTRICT；观测输入禁止直接引用自身，但 DDL 不保证不存在更长环路 |
| `content_version_relations` | quote/repost、目标原生 scope/id、作者 ID | 版本内目标唯一，版本 FK CASCADE；它描述引用/转发，不是评论父链或模糊去重结果 |
| `content_threads` | comment、post、root、parent、reply_target 的 content ID，`parent_relation_status, created_at` | 主键 `(owner_id,content_id)`；五个 content FK 当前均为 CASCADE；按 `(owner_id,post_content_id,content_id)` 查帖下评论。禁止直接自父，但没有数据库级多跳环检测、同平台/同原帖或对象类型保证 |
| `content_visibility_observations` | visible/deleted/restricted/transient_failure/unknown、依据、job、source operation、observed/received | 同 content+operation 唯一；content CASCADE，job RESTRICT；每种状态有允许的依据。未返回某条评论、404、限流不能全写成 deleted |
| `content_annotations` | content/version、topic/rule version、prompt version、input manifest/signature、`relevant` 布尔、reason、sentiment、summary、viewpoints、AI call、状态、诊断、first_valid 时间 | 唯一 `(owner_id,content_version_id,topic_id,topic_rule_version,prompt_version,input_signature)`；内容版本及主题/规则 CASCADE，AI call 为默认 NO ACTION；索引分别按 content 和 topic 的 created_at。**没有四档标签、数值相关性评分或排名字段** |
| `ai_calls` | provider/model、prompt version、input fingerprint、status/failure、tokens、duration、路由版本/哈希、job、created_at 等 | 唯一 `(owner_id,id)`；job FK 为默认 NO ACTION；状态区分 running/unknown/succeeded/failed；用量字段不是平台取数收费证明 |

评论持久化当前会为晚到的原帖、父评论、根评论和回复目标建立**仅含身份的占位记录**，之后补正文；见 [ContentService.persist_comment_in_transaction](../../../../backend/app/content/services.py)（约第 827 行）。没有 `parent_comment_external_id` 时，当前服务直接按 root 处理。因此“确实一级评论”和“来源未提供父 ID”目前不能可靠区分，属于必须修正的输入契约缺口。`rootid` 只能证明根评论时，适配器不能把它冒充直接父评论。

现有 `content_annotations_output_status_check` 要求有效结果中 `relevant=true` 时 sentiment 非空，并且 reason、summary、AI call 非空；失败时相关性字段为空。不能仅修改提示词就把它变成“仅相关性”的四档流程。约束正文在 DDL 和 [ContentAnnotation](../../../../backend/app/analysis/models.py)（约第 117 行）。

### 覆盖、证据和清理

`coverage_windows` 用 owner、source、capability、target hash、sort、rule version、起止时间唯一识别一个覆盖窗口；保存 pending/running/confirmed/partial、stop reason、last job、checkpoint sequence、page count。`last_job_id` 删除时 SET NULL。`confirmed` 只能表示在声明的查询和来源返回语义下走到已确认终点，不是全平台全量。

`collection_due_windows` 保存计划到期窗口及 pending/accepted/skipped/missed；有 `(owner_id,schedule_key,due_at)` 唯一键及 job、topic 的延迟 FK，用于区分没到期、静默期、预算跳过与调度中断。任务内页游标在 `jobs.checkpoint`，不能把一次完整页提交等同整个时间窗完成。

`outbox_messages` 与业务事务配合，按 job+dispatch sequence 唯一；`job_attempts` 按 job+lease epoch 唯一；`processed_messages` 按 Kafka topic/partition/offset 唯一；`job_stage_attempts` 区分 request/parse/save/analysis。它们已有恢复和观察所需的基础，无需再造一套队列表。

`evidence_resources` 保存 resource type/id、来源策略及留存版本号、data class、collected/expiry、清理目标；资源多态 ID 本身不是到业务表的 FK。`evidence_retention_policies` 的 effective days 是 requested 与 source max 的较小值；当前策略表是现行行加版本号，不能把版本数字当完整历史快照。`provenance_manifests` 及 inputs 保存方法版本、参数、指纹和证据输入；inputs 到资源的删除行为是默认 NO ACTION。`evidence_deletions/cleanup_targets` 保存清理指令、租约、重试和结果；target kind 当前仅 redis_cache/minio_object/postgres_content_observation。新增候选和评估资源必须接入实际清理路径，不能因登记资源就声称已能回收。

## 关系与隔离边界

使用文本关系图，普通 Markdown、Obsidian 和当前阅读站都能阅读；不为本页新增图形依赖。实线含义是逻辑关联，下列“运行配置”部分由服务校验，并非全部已有 SQL 外键。

```text
本人 owner
  ├─ 主题 monitor_topics ── 规则版本 monitor_topic_versions
  ├─ 来源 source_connections ── 配置版本 source_connection_versions
  └─ 任务 jobs ── 固定运行配置 / 分页检查点 / 阶段记录
          ├─ content_discoveries ───────────────────────┐
          ├─ content_observations ── content_versions ──┤
          │       └─ 原始证据与来源输入                 ├─ content_records
          └─ content_topic_candidates【拟新增】          │      └─ content_threads
                  ├─ 主题规则版本                      │           原帖 / 根 / 父 / 回复目标
                  └─ 同一内容版本及观测 ────────────────┘
                             └─ content_annotations ── ai_calls

任务 / 来源窗口 ── coverage_windows / collection_due_windows
证据资源 ── provenance_manifests + inputs ── 留存与清理记录
```

现有大部分业务 FK 包含 `owner_id`，可阻止跨 owner 的已约束引用；`monitor_topic_versions` 依靠其主题归属。**当前 DDL 未启用 RLS，且 monitor/content 等 owner_id 未统一 FK 到 identity_users。** 因此它不是数据库自动完成所有用户隔离或注销清理的系统：API、读取函数、后台任务、游标和证据取回都必须携带并验证 owner；不接受请求体指定别人的 owner。个人使用也不取消此边界，已有第二用户/公开阅读路径不能混读私人监控。

同一平台原帖从关键词搜索、作者页和评论补全再次出现，应按规范化身份归同一 `content_records`；查询、观测与正文版本仍分别保留。source_key 必须代表稳定逻辑来源，不能随着开源采集器名称变化；采集器版本放在 job。若历史 source_key 已按通道区分，不直接重写身份，先列冲突并建立有证据的归并方案。

不同平台转载、相同措辞或相似主题保留不同身份及评论链。近似重复只作展示折叠/事件候选，不建立跨平台唯一正文哈希；正文 fingerprint 只在一条身份内部去重。本人和另一个 owner 的同一帖子也分别入库，避免来源权限、查询主题和删除请求互相影响。

## 最小增量提案

以下均未出现在当前 DDL 中，不提供可以误执行的 SQL。第一轮手工导入和离线评估可先用冻结文件验证字段；用户可操作的持久候选列表获准实现后，再落实候选表及约束。最终 SQL、ORM、DTO、解析器、提示词与结构断言需要同一次变更。

### 通用主题候选关联

拟名 `content_topic_candidates`。一行表示某次运行、某个主题规则、某条实际查询发现的一个内容观测，包含确定性的本地规则判断。它不复制正文，也不替代 AI 分析表。

| 拟字段组 | 类型与约束建议 | 用户价值 |
|---|---|---|
| `id, owner_id, job_id, topic_id, topic_rule_version` | UUID；规则版本正整数；owner+job、owner+topic 和 topic+version FK | 知道是哪一轮、谁的主题和哪一版规则 |
| `content_id, content_version_id, observation_id` | UUID；content/version 与 observation 的复合 FK 对齐同 owner、同内容和同版本；对无可用文本的观测允许 version 为空，不能造空正文；无 version 时仍单独约束 observation 和 content 归属 | 标注、排序和复查使用当时看到的输入 |
| `retrieval_kind, query_fingerprint, query_snapshot` | kind 为 search/author_posts/hotlist/manual_import 等有限来源方式；SHA-256 为 32 字节；query JSON 仅允许文本、词组、排序、窗口、来源字段等非敏感键，大小设上限 | 区分真正搜索、榜单过滤、作者范围和人工导入；保留实际查询差异 |
| `source_rank, first_observed_at, created_at` | rank 可空、存在时为正整数；时间为 TIMESTAMPTZ | 还原平台返回顺序与关键词基线；不从数据库 UUID 猜平台顺序 |
| `keyword_decision, matched_terms, filter_reasons` | decision 为 passed/rejected/insufficient_text；词和理由为有大小上限的结构化数组，理由含排除、缺任一词、缺全部词、时间待核对等独立维度 | 无关、规则排除、文本不足和时间问题可分别统计；不能只保留通过项 |

拟唯一键 `(owner_id,job_id,topic_id,topic_rule_version,query_fingerprint,observation_id)`，重复同页消费不重复写。同一内容被不同查询找到可以有多条候选来源；统计帖子数时按内容身份去重，评估时冻结选择的版本和观测。不同运行可以追加新候选，不覆盖旧运行的判断。

外键存在还不足以证明“本轮取得”。领域写入口必须核对候选的 topic/rule/query fingerprint 与 job 冻结 scope 一致，观测的 job/source operation 与本轮已提交采集页或显式关联的子任务/共同采集批次一致；可表达的关系补复合约束。不能把同 owner 的任意旧观测挂到新运行后计为新实采。人工导入、历史复用和缓存分别记录 retrieval/provenance，保留原取得时间；计数按真实来源动作分类。跨运行错挂、错查询及共享批次都须有固定样本验证。

候选对 job、主题、观测的删除先采用阻止意外删除的策略，清理服务显式删除衍生候选后再处理输入；不让删除一个 job 静默抹掉评估分母。真正用户删除/到期清理必须覆盖候选、AI 输入和评估文件，不能让 RESTRICT 成为永远无法删除的理由。具体 FK 的 RESTRICT/延迟 NO ACTION 在实现任务中与清理顺序共同确定。

`query_snapshot` 不是无约束原始请求日志，不收请求头、Cookie、签名、会话标识。正文、作者和原始响应继续走已有内容/证据路径。不要把图片、视频和整页响应塞进该表。候选返回数、保存数与丢弃数要一致；解析失败但无法形成合法内容身份的条目保留页级错误证据，不造假的 content ID。

### 规则和运行不可变性

拟在 `monitor_topic_versions` 增加 `topic_description`、`aliases`、`rule_contract_version`。别名映射包含规范词、候选表达、来源与审核信息，和原规则一起建立新版本；不直接改 match_any 的含义。别名未启用时可为空，不能由模型偷偷扩词。JSON 的结构与长度需由 DTO 和 CHECK 双方覆盖，不能只写 `jsonb_typeof=object` 就称完成校验。

复用 `jobs.scope` 固定 topic/rule、connection/version、查询集合、窗口及边界版本、评论排序与限额、文本选择规则、analysis contract/prompt/model、排序规则版本、免费取数核验引用。现有三项采集代码版本字段继续使用；适配器实际版本要可对应到固定提交或构建。任务指纹覆盖这些有效输入，排除创建时间等非业务噪声。

所有后续阶段读取任务快照，不重新读取“当前主题”来解释旧输入。相同 operation ID、不同指纹返回冲突；同一 operation ID 与指纹的重试复用运行。显式发起新一轮使用新的 operation ID，即使查询参数相同也可产生新观测，但仍共享用户/来源窗口预算；不能因指纹相同而永远禁止刷新。改关键词、模型或窗口是新配置/新运行；租约重试只是同一运行的新 attempt。主题归档是状态变更，历史结果保留。

当前版本表没有禁止 UPDATE 的数据库触发器，`jobs.scope` 也没有数据库级不可变保护。建议先由领域写入口与测试保证追加版本和接受后只读配置；同时补 `monitor_topics.current_version` 的延迟 FK 候选。是否采用额外数据库权限/触发器，只有发现绕过写入口的现实路径后再决策，不另建审计平台。

### 四档相关性与情感解耦

拟在 `content_annotations` 增加 `analysis_contract_version`、`relevance_label`、`evidence_spans`。四档用 direct/weak/irrelevant/insufficient；reason 继续复用；证据片段记录输入 content version/observation、字段、片段或边界，且必须能在固定输入中复核。长度、数量和 JSON 结构设上限。数字评分、排名、embedding cosine 均不是必要字段。

契约演进建议：

- **旧契约 v1**：保持原 bool/sentiment/summary 的合法性和显示；`true` 仅表示旧版相关，不能自动回填成 direct，`false` 也不代表新四档已经评审。
- **新契约 v2**：有效结果必须有四档 label、reason、必要的证据依据和 AI call；sentiment 可空。相关性标签为 insufficient 也是有效判断，与 pending/failed/invalid 分开。summary/viewpoints 仅在请求该能力时要求，不为相关性强制生成情感或观点。
- v2 中旧 `relevant` 列保持为空，由版本化 DTO 提供明确兼容视图；需要旧客户端 bool 时按显式规则派生，不把该投影再写成原始判断。旧 bool 和新标签的组合由分支 CHECK 约束，不允许互相矛盾的双真值。
- 输入签名纳入 contract version、模型/提示词、规则、输入观测、上下文选择及截断策略；唯一键相应包含 contract version，避免 v1/v2 或模型切换覆盖同一行。已经有效的结果原则上追加新签名结果，失败重试的诊断历史沿用现有机制。

评论分析冻结原帖、直接父评论和本评论的版本/观测。父内容缺失时记录 context missing，模型不能推断出原文；“属于该讨论”可由结构证明，“包含有用观点”仍需相关性判断。情感未来单独启用时，也必须带独立任务/提示词契约；本次不把旧情感指标设为 POC 门槛。

这项改动必须同时演进 `content_annotations_output_status_check`、ORM、AI 输出校验和读取 DTO；仅加 label 列但保留原 `relevant=true → sentiment非空` 约束无法满足新需求。

### 时间可信度与结果就绪

`published_at_fractional_digits` 当前只记录时间戳小数位，**不能表达“只有日期”“约两小时前”“上榜时间”或可信程度**。拟在 `content_observations` 增加以下最小语义：

| 拟字段 | 口径 |
|---|---|
| `source_time_kind` | publication/update/rank_entered/unknown；只有 publication 才可能进入帖子发布时间统计 |
| `source_time_raw, source_timezone` | 经裁剪的原始时间文本和解析时采用的时区；不保存整段含凭据响应 |
| `published_time_status` | trusted/approximate/unknown/anomalous/legacy_unverified；旧数据默认 legacy_unverified，不能仅因非空就批量标可信 |
| `time_precision` | second/minute/day/interval/unknown 等有限值；不把日期解析出的零点当秒级精确发布时间 |
| `published_time_lower, published_time_upper` | 模糊时间可推定区间，存在时 lower < upper；未知保持空。它用于说明不确定性，不伪造一个精确点 |
| `time_rule_version` | 对应解析器/可信判定版本；窗口判断由固定版本完成 |

原 `published_at` 保留解析出的来源值；新查询只有 status=trusted 且 kind=publication 的时间参加“窗口内新帖”和发现延迟统计。approximate、unknown、anomalous、legacy_unverified 单列待核对；模糊区间即使与窗口相交也不混入可信命中分母。未来时间、无时区、字段语义错配分别保存原因；允许多少时钟偏差由验证卡确定。

已有 `content_observations.observed_at` 表示采集页观测时间，`received_at` 表示入库接收，`content_discoveries.first_observed_at` 汇总首次发现。不得用抓取时间填 `published_at`。`content_records.created_at` 可能来自父链占位，不可拿它算首次看到正文。若过期清理发现记录后仍需保留历史 first_seen，必须在删除前保留不含正文的最早发现摘要或承认指标变为“当前留存范围内首次发现”，不能静默重新计时。

拟在观测关联的版本化 provenance manifest 中固定 `acquisition_batch_id`、`acquisition_kind`（live/cache/import）、原始来源操作引用、可空的实际 `fetched_at`、本次 `read_at` 及可空的 `cache_origin_ref`。这些是拟新增的证据字段，不是现有观测列；无法证明原抓取时间时保持未知。重读 JSONL、缓存或历史文件只记录新的读取事实，仍引用原批次和原抓取依据，不生成新的“来源已抓取”证明，也不刷新首次发现。若以后需要按抓取时间高效查询，再演进观测列及索引；POC 先保证证据不丢和口径可复算。

拟用现有结果清单/manifest 承载 `ready_at`：当本轮固定输入的可读投影完成时写一次，含候选池与分析版本及结果指纹；不拿 job.completed_at 或 annotation.first_valid_at 自动等同用户可读时间。首轮可以是受控证据文件中的字段；若运行列表确实需要独立按 ready_at 查询，再为 `jobs` 增加可空 `result_ready_at`，不为未来性能提前加结果表。

新窗口按 `[start,end)`：等于 start 的可信帖纳入，等于 end 的不纳入；页面和导出都标相同边界。接续窗口共享边界时不重不漏，历史闭区间运行保留原 boundary version，不改写旧证据。旧帖新评论保存评论自己的时间和发现记录，不更新原帖发布时间。模型排队、首次回填、来源缓存与持续监控延迟分开统计；缓存时间只有来源提供或请求链路可证明时才记录。

### 评论父链与删除补充

保留 content_threads，不新建评论表。拟扩展 `parent_relation_status` 与输入 DTO，使 root、observed、unavailable、unresolved、missing 可区分：root 必须是来源明确证明一级；unresolved 表示已知父 ID 但父正文未到；unavailable 表示已知父 ID 且有不可见证据；missing 表示来源未提供直接父 ID。missing 允许 parent 为空，并可保留已知 root 或 reply target，不能触发“parent为空就root”的推断。

每个父/根/回复引用必须满足同 owner、同平台、同原帖和正确对象类型；现有 FK 只保证 owner+ID 存在，因此上述业务校验与多跳环检测必须补测试。回复先到、父后到时可以补事实；父 ID 冲突不能静默换父，保留诊断并暂不把它作为完整父链样本。

当前物理删除父 content 会通过 CASCADE 删除引用它的 **content_threads 行**，但不会顺带删除这些子评论的 content_records 正文，可能形成“评论仍在、归属关系没了”。建议来源删除首先写 visibility/tombstone，并清理应删除的正文/原始证据，暂保留必要身份壳。仍被子评论引用的身份壳不得单独物理删除；可在清理事务中检查，并评估将 root/parent/reply_target FK 改为可延迟的 NO ACTION。自己的关系行随自己的内容删除仍可 CASCADE；整帖回收需先处理依赖关系和子评论，再删除父壳。这是待验证删除方案，不能未经级联测试简单把所有 FK 换成 RESTRICT。

源端删除、用户删除、留存到期有不同依据。保留身份壳的内容范围与期限需随留存策略确定；用户要求彻底删除时，按显式依赖顺序完成整套清理，不以“留审计”为由无限保留原文。

## 写入、游标与幂等

复用现有分页事务，不把外部请求包在数据库长事务里。目标过程是：读取固定配置并申请预算 → 外部请求 → 校验/标准化有界页 → 在一个短事务中写内容身份、正文版本、观测、发现、候选、证据与页检查点 → 提交后确认消费。AI 在采集事务之外执行，失败不回滚已经成功取到的原帖和评论。

现有 [CommentPageCommitter.commit_page](../../../../backend/app/content/comments.py)（约第 661 行）会核对运行范围、当前租约和 checkpoint；内容写入、覆盖页记录与预算结算使用同一事务，条目 operation ID 从页 operation 派生。它是可复用实现事实，**不代表每个新平台的帖子路径都已具备同样保证**。

| 情况 | 设计要求 |
|---|---|
| 同页重投、进程在提交后崩溃 | 相同内容身份、正文指纹、source operation 和候选唯一键不新增重复；重复消费仅确认既有提交 |
| 正文编辑、计数变化 | 正文变化产生新 version；同正文复用 version，新的采集轮次可新增 observation 保存计数与可见性；不得覆盖上一轮观测 |
| 评论先到父后到 | 父身份占位不算已读到父正文；后到观测补充事实，原评论身份不变 |
| 当前页解析/写入失败 | 当前页整体不推进 checkpoint，保留错误；已提交页可读；不能写一个“成功空页”掩盖异常 |
| 暂停主题 | 阻止后续调度，在途运行可按冻结配置和剩余预算结束；不把暂停等同取消 |
| 取消、超时、预算耗尽 | 保留已提交页，停止后续请求并按原因终止执行；覆盖窗口为 partial 等真实状态，未完整确认部分不推进跨轮已确认水位；恢复由最后已提交页或安全重扫开始 |
| 旧 lease 迟到 | 通过 lease epoch、checkpoint sequence 比较拒绝陈旧写入；不能用重试次数替代 fencing |
| 游标重复、失效或搜索结果重排 | 无进展/失效时停止当前翻页，标记原因且不前推水位；后续按冻结策略在固定窗口有界重扫并去重，仍占原有来源预算；页 token 不能当永久时间水位 |
| 同一 operation 携带不同 scope | 明确冲突，不将新请求写入旧任务，也不修改原始指纹 |
| 相邻窗口、晚到内容 | 半开边界并按平台实际索引延迟设置有限重叠回扫；重叠去重。迟到窗口未覆盖时记录缺口，不声称已全量 |

覆盖键包含 owner、平台能力、目标哈希、来源排序、规则版本和时间窗。目标哈希必须覆盖规范化查询/原帖身份；同一关键词换排序或规则，不能复用旧已确认水位。评论“热评”返回终点只能证明该热评接口和配额下完成，不能证明全部评论；父链、分页上限、首次/二次扫描分别记录。

## 查询与索引建议

现有索引覆盖身份去重、内容历史、帖下评论、主题分析和窗口到期，但不能据此声称新推荐排序已有索引或达成延迟目标。当前 `ContentService.list_contents` 有基于内容 ID 的游标扫描，且时间展示存在 `published_at or first_discovered_at` 回退；新增产品排序必须单独实现并验收。

新查询顺序建议为：按 owner+topic+冻结运行选择候选 → 去除硬排除和窗外项 → 选择同 contract/input signature 的分析 → direct 且时间可信的结果按发布时间降序 → 用平台原生 ID、内部 content ID 固定破同分。弱相关、信息不足、时间待核对另列；模型失败区不能混为无关。无数值评分，不用互动数改变相关性门槛。

拟索引只围绕实际读取：

- 候选唯一键负责幂等；另加 `(owner_id,job_id,topic_id,topic_rule_version,id)` 用于运行候选分页，并评估 `(owner_id,topic_id,content_id,created_at)` 的跨轮追踪需求。
- 四档分析读取优先复用现有 topic 索引；在已测查询确有瓶颈时，增加含 contract、label、content version 的组合索引，不先为每个状态建索引。
- 时间筛选可评估 observations 上 `(owner_id,published_at,content_id)` 的 trusted/publication 部分索引。先确保读取的是该运行选定观测，而非同一内容任意历史时间，否则索引快也会取错数据。
- 直接回复查询若成为瓶颈，再加 `(owner_id,post_content_id,parent_content_id,content_id)`；JSON query/manifest 目前不做全库模糊检索，无需默认 GIN 全索引。

分页游标绑定 owner、topic/rule、run、不可变结果 manifest 的 ID/指纹、排序版本和最后排序键；manifest 固定候选及选中的 observation、content version、annotation/input signature。不能只绑定 run 后动态读取最新分析，pending 变为 direct 或模型重跑也会改变集合。新结果生成新 manifest，用户显式刷新后采用；旧 manifest 已到期或清理时返回明确失效，不能静默退回最新列表。此约定用于阅读与评估，不混用当前列表的 ID 游标。性能验收的负载、并发和时延初值统一引用总 PRD 的非功能要求，不在本页另定标准；要在独立测试库用对应数据量的查询计划与延迟证明，本轮没有 EXPLAIN 或吞吐结果。

## 留存、恢复与可观测

结构化候选、原文、原始响应、媒体、分析和评估导出分别登记 data class 与证据关系，继承当前来源策略；不因为 POC 默认永久保存。首轮具体天数写验证卡，过期文件和数据库派生内容都要纳入回收。备份与日志同样不能变成不受留存约束的正文副本。

清理要先列依赖，再按现有服务处理：停止引用过期输入的新任务 → 清理或失效候选/分析/事件等派生引用 → 删除原始对象与可删除观测 → 处理无引用的正文版本和身份 → 确认缓存与导出已清理。现有 events、editorial receipts、provenance 等可能通过 RESTRICT 或默认 NO ACTION 阻挡删除，必须有针对性依赖测试；数据库外键不能替代对象存储删除成功回执。

每轮至少能还原：上游版本与实际能力、查询/时间窗口、请求页数、来源返回条数、合法候选数、身份去重数、规则排除数、保存/更新数、父链缺失数、分析成功/失败数、停止原因及各阶段耗时。计数从候选、观测及任务事实聚合，区分“条目”和“唯一帖子”；在分页截断时标注已观察范围，不能把总量字段与真实抓到数量混写。

运行诊断复用 jobs、stage attempts、AI calls、capability evidence、coverage 和 evidence，不新增通用日志表。未知或不可得的指标保持未知；日志只保存 ID、错误码、限额与耗时等所需字段，正文和 credentials 不进普通错误日志。免费准入证据需记录所选路径的版本与依赖；无需用一个常量 `cost=0` 假装已经验证没有收费路径。

备份恢复沿用 PROJECT 的停写、备份、实际恢复核验、空库导入和切换流程。业务库不用于试验；本轮未读取业务连接。RPO/RTO 与保留天数目前未测定，应在首轮容量与恢复演练后确认，不把本地数据库等同天然可恢复。恢复验收同时检查数据库、证据对象和任务指纹，防止恢复后重复对外取数或把旧任务当新任务。

## 迁移、回填与回滚设计

不引入 Alembic 或第二套 DDL，不在现有业务库直接执行完整 `schema.sql`。未来获准实施时遵循以下步骤，具体执行记录另写验收记录：

1. 冻结本次结构变更与输入契约：确定候选字段、v2 分析、时间状态、父链状态和半开窗版本，列所有受影响的 DTO/ORM/校验/查询/清理路径。
2. 在只读导出上统计旧数据形态和外键依赖；检查重复身份、空 version、旧 bool 分析、未知父链、时间精度和历史 source_key。无法确定的记录写回填例外清单，不通过猜测“修好”。
3. 同步更新唯一 schema、ORM 与结构断言，在全新 `hotkey_test_<后缀>` 库初始化并跑约束/恢复测试；完成后删除测试库。此处是后续要求，本轮未执行。
4. 按 PROJECT 停写并备份；实际恢复到独立库确认可读，再在新空库执行完整 schema 并导入。导入保留原 UUID、operation ID、fingerprint、created/observed 时间及旧版本语义，不重新生成以掩盖冲突。
5. 回填规则：旧候选只可从可追溯运行证据重建；没有过滤前证据就记 unavailable。旧分析保留 v1；旧时间先 legacy_unverified；不能把旧 `parent=NULL` 一律证明为真实 root。必要时用兼容显示标为“旧记录关系未核验”。新字段缺事实保持空/未知。
6. 核对各表行数、唯一性、owner 隔离、FK、证据引用、任务/预算状态、清理与旧新读取对照；只有确认后切换应用与库。切换时暂停调度，防止两套消费者同时写入或重复取数。
7. 旧库和相应应用版本保留作回退。新结构启用后若发现问题，先停新写并保存增量与诊断，再切回兼容版本；新增 v2 结果不能无损倒写旧 bool 结构。是否重放新任务按 operation/来源证据去重确认，不能直接重跑所有任务。

迁移成功的证明是新库结构、导入完整性、实际恢复和业务关键读取通过，不是文档构建或 `schema.sql` 能被打开。当前没有迁移、备份或回填结果。

## 数据验收场景

以下按 `pm-execution:test-scenarios` 整理，均为待执行场景。后续由开发在固定样本及独立测试库执行；真实国内来源的可用性另外验收。

| 场景与角色 | 起始条件及操作 | 应观察到的结果 |
|---|---|---|
| 本人重复运行 | 固定规则/来源/窗口；同页重复提交、同任务重投，再发第二轮运行 | 同页无重复观测/候选；第二轮身份与相同正文复用，可新增观测；首次发现不重置 |
| 本人修改主题 | v1 任务已接受后修改关键词和别名到 v2，再完成 v1 | 旧任务与标签仍使用 v1；新运行使用 v2；界面可核对实际查询，历史结果不变 |
| 本人比较基线 | 冻结含通过、排除、模糊和缺文本的候选池，分别跑关键词与 v2 分析 | 两者同候选池；排除和失败可追踪；四档标签有固定输入依据；不把 v1 bool 当已完成四档评测 |
| 本人只做相关性 | v2 direct 结果不包含 sentiment；另有模型超时及 insufficient 样本 | direct 可有效持久化且情感为空；超时仍 failed/pending；insufficient 为有效标签，三者分开 |
| 本人查看回复 | 子回复先到、父后到；另造根 ID 已知但直接父 ID 缺失样本 | 前者先占位后补正文；后者 missing，不当 root；不同平台或不同帖同数字 ID 不串链 |
| 数据清理作业 | 原帖有根评论和二级回复；先写源删除，再清理父正文及身份 | 删除状态有依据；仍保留的子评论不静默失联；身份物理删除按依赖清理或被明确阻止 |
| 本人查看时间窗 | start/end 边界、无日期、只有日期、上榜时间、未来异常及旧帖新回复 | 新运行只有可信 publication 且 start≤time<end 纳入；其余单列；新回复不更新原帖时间 |
| 任务执行者恢复 | 第二页失败/取消/超时，第一页已提交；旧 lease 迟到；随后恢复 | 第一页可读；失败页无水位前移；旧 lease 被拒；恢复不重复计数，覆盖缺口仍可见 |
| 第二位用户 | 两个 owner 同平台 ID，尝试读取对方主题、游标、候选和证据 | 分别去重，跨 owner 的请求/引用拒绝；公开阅读不泄露私有查询或登录证据 |
| 本人到期清理 | 候选、正文、分析、导出和缓存有关联；清理失败后重试 | 按策略到期，重试幂等；引用和外部对象均处理后才完成，失败可查且不误报已删除 |
| 运维恢复演练 | 固定快照备份，恢复到新独立库并核对对象证据 | 行数/约束/关键读取与输入指纹一致；恢复后调度受控，不发生未经确认的重复取数 |

## 待决策项与交付边界

需要在首个平台验证卡确定：平台与逻辑 source_key、实际候选配额和证据留存期限、哪些时间字段可判可信、父 ID 缺失时适配器提供什么事实、关键词基线次序、首轮 ready_at 的记录位置。是否新增排名索引、别名 namespace、数据库不可变触发器或持续标注表，都以实际查询/误例/容量证据再决定。

当前设计采用四档标签和半开窗口，不建议新增连续评分。候选表只为可追溯的有界输入服务；跨平台事件归并、情感看板、全量评论、泛化媒体资产库和海外平台接入不是本轮数据库变更的理由。

本页完成的是现有事实与最小增量的对照。尚待验证的是数据契约是否适合真实国内样本、查询性能、旧数据回填、删除/恢复和用户阅读闭环；未修改 DDL、ORM、业务逻辑或数据库。

来源：2026-10-07 本轮项目聊天，需求提出者原话。

> 现在先不要做任何的代码的实现，最重要的一点我需要你真实的搭建一个workspace，为了很好的阅读和让ai理解我们的需求

据此，本轮明确的工作是：建好需求阅读与核对入口，把文档和执行的理解偏差暴露出来；后续验证围绕最小 POC 和 demo 跑通。**本轮没有授权开始 POC 编码，也没有确认新的产品范围或首个业务场景。**

## 需求、方案和证据怎样区分

| 内容 | 在哪里读 | 怎样使用 |
|---|---|---|
| 用户本轮原话 | 本页上方 | 作为当前阶段和验证方式的依据 |
| 已有产品需求 | [总 PRD](../prd/01-PRD.md)、对应[能力](../../index.md#能力) | 保留现有原文；逐项核对，不能因为文档写了就推断用户认可本次全部实现 |
| 已有边界 | [决策](../../index.md#决策) | 保留生效规则；本轮没有废弃旧决策 |
| 实施方案和计划 | [架构](02-技术架构.md)、[执行计划](../../index.md#执行计划plan) | 是实现建议和原计划，不能反过来定义需求，也不能当作当前派发授权 |
| 当前实现 | 对应源码、配置及运行记录 | 源码说明能怎么做；只有实际运行证据才能说明这次跑成了什么 |
| 验证结果 | 同一张 [POC 验证卡](06-POC验证卡.md) 的结果部分 | 记录真实输入、输出、复跑步骤和局限，结果回来后再决定下一步 |

发现冲突时，写出“用户原话 / 现有文档 / 当前行为”的差异；保持待核对状态，不自动选一方、不把 AI 建议写成用户已确认需求。

## 一次只验证一个场景

```text
一个具体问题 → 一张验证卡 → 最小 POC → 用户能操作的 demo
                                              ↓
                          根据真实结果：继续 / 缩小 / 换方案 / 停止
```

这是对本轮反馈的工作方式整理。POC 和 demo 可以共用一份最小实现，不必分成两个项目。

- **POC**：回答一个风险或假设，例如“这个来源能否拿到可核对的真实内容”。记录失败同样有价值。
- **demo**：让用户从输入走到可见结果，例如“输入一个主题，读到来源和时间明确的命中”。页面截图只证明外观，操作录屏或复跑步骤才说明交互经过。
- **正式实现**：在前述结果支持需求后，再讨论自动调度、多来源、长期运行、架构调整。POC 通过不等于整项能力可用。

验证卡先写清：谁在什么场景下需要什么、唯一假设、最少输入和输出、成功与失败条件、本次明确排除的范围。卡里没有的扩展只列为后续候选，不在执行时顺手补齐。

## 每轮怎样开始和结束

开始时，用一句话复述本轮要解决的用户问题，指向来源；列出这次唯一验证项和范围。结束时，给出能打开或操作的产物、复跑步骤、实际结果、还不能证明什么。执行状态更新在进度原文中。

文档只服务于这次理解和验证。没有被当前问题使用的章节、平台清单、长期排期和复杂流程，本轮无需继续扩写。

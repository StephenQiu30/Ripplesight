# Ripplesight 文档工作区

本轮以原始业务意图重建并合并为一套规格：**核心闭环优先，其余功能保留并重新审视；当前代码与设计不作为正确性依据**。00～58是稳定引用编号，不限定现有页面数量。详细需求定义业务结果与验收，PRD为开发人员组织用户价值、流程和故事，设计推导实现方案，PLAN为agent拆出可执行任务。已失效的旧方案不再并列保留。

- [原始意图、证据确定程度与术语](requirement/00-产品目标与边界.md#原始需求与来源登记)：找回国内平台POC、相关性/时效、免费取数及历史辅助意图。
- [总体PRD](prd/00-产品目标与边界.md)：定位、用户价值、范围与发布取舍；各业务编号都有面向开发人员的PRD。
- [功能与验收](requirement/01-关键词配置.md#业务需求规格)：FR/BR/AC；00为GOV治理，11为VR验证要求。
- [非功能需求](requirement/11-质量评测与验收.md#非功能需求规格)：18类质量要求、公式、验证责任及待冻结门槛。
- [目标架构、ER与完整数据库归属](design/00-产品目标与边界.md#数据库设计)：核心实体字段/键/索引/生命周期，辅助逻辑模型区分物理设计。
- [接口与异步合同](design/00-产品目标与边界.md#接口与异步合同设计)：输入输出、版本、幂等和未知恢复，不绑定旧路由。
- [依赖与发布门槛](plan/00-产品目标与边界.md#总体执行顺序)：面向agent的执行输入、工作包、任务依赖、场景验证和停止条件。

追踪为`OR → REQ/FR/BR/NFR/AC → PRD/US ↔ DESIGN → PLAN/T → 验证与BACKLOG证据`。方案与指标未获正式评审的部分明确待定，不能把文档完成当成能力可用。进度、阈值确认及运行证据只在根目录BACKLOG；运行架构在PROJECT，实施状态以BACKLOG为准。

## 需求驱动的交付规范

本项目采用pm-execution的 `create-prd`、`user-stories`、`sprint-plan`、`test-scenarios` 方法，结合本仓库的业务约束维护一套规格。产品经理先辨认原始意图和证据，再拆场景、业务规则和验收；设计必须解释怎样满足这些要求，PRD将产品行为与设计引用交接给开发人员，PLAN将同一规格转为agent可执行工作。PRD与设计允许迭代，不能倒过来从现有代码生成“必须如此”的需求。

### 文档职责与唯一依据

| 交付物 | 主要读者与问题 | 必须具备 | 正文归属 |
|---|---|---|---|
| 原始意图登记 | 产品负责人：为什么做，依据是什么 | 原始表述或可追溯归纳、来源/确定程度、角色/场景/结果、边界和未找回项 | requirement/00的OR登记；不重建授权历史 |
| REQUIREMENT详细需求 | 产品、设计、开发、QA：必须满足什么 | FR、BR、适用NFR、输入/输出/异常、范围、Given/When/Then/反例、可观察AC | 业务要求与AC唯一原文；GOV/VR与产品FR分开 |
| PRD开发交接 | 人类开发人员及设计/QA：为谁做，如何使用，做到什么程度 | 问题/目标、用户与价值、范围/非目标、主路径/分支、3Cs用户故事、设计与AC引用、未决问题、发布边界 | 用户故事US、产品取舍和交接；公共六段价值主张在00，其他编号落到具体任务价值 |
| DESIGN详细设计 | 技术及交互设计人员：如何满足要求 | FR/NFR映射、流程/状态、模块职责、ER/表字段/键/约束/索引/生命周期、接口/事务/幂等/并发、权限、失败恢复、方案取舍及迁移回退 | 目标方案唯一原文；无持久化需要则说明原因，不为凑表建表 |
| PLAN agent交接 | 编码agent：从哪里开始，怎样实施并证明 | 规格提交/当前差距、明确US/FR/AC切片、输入就绪、T任务产物/依赖、操作与预期、停止条件、检查/独立审查/回退/交付输出 | 工程任务T和执行合同；不另造业务需求或权限 |

这是一套相互引用的交付物，不是四份重复正文。FR/AC/US的同序号表示对应用户结果；T按产物编号，可支持多个故事，交接时列清覆盖集合。设计中的字段、表和接口必须能追溯到FR/BR/NFR；PRD不维护第二份字段字典，PLAN不维护第二套AC。技术选型可协商，确认的业务要求与安全边界不能为旧实现让步。

### 拆解与开发交接顺序

1. **找回意图**：区分用户直接确认、历史转述、设计提案和未知；未知只登记问题，不能假造访谈、业务指标或原话。重要原始意图逐条映射到编号与用户结果。
2. **详细化需求**：按角色、触发、输入、正常/失败/未知结果拆FR/BR/NFR和AC。覆盖规则、身份、权限、时间/分母、版本和外部副作用；保留功能明确首版/后续/待重评，不静默删除。
3. **形成产品与技术交接**：PRD以3Cs组织可交付用户价值；设计从不变量推导数据及流程，比较方案后说明选择、限制和迁移。数据库设计先明确业务身份/关系，再到字段、PK/UK/FK/CHECK、查询索引及生命周期；候选模型不等于已实施DDL。
4. **选择可执行切片**：根据BACKLOG业务优先级和可消费输入拆PLAN，不按现有目录或页面数拆服务。先完成保护与合同，再连接业务结果；禁止“必须先完成所有关联页面”的循环前置。
5. **实施、验证和审查**：先确认规格提交与工作区差异；执行必要工程门禁和AC场景，独立审查后修复问题。把受控样本、真实提供方、浏览器、数据库及自然时间证据分别记录，再按已有授权提交推送。
6. **处理变更**：先修原始登记或所属FR/BR/NFR/AC，再更新受影响的PRD、设计、PLAN和BACKLOG依赖。记录当前变更理由和影响，不在各目录追加历史或重复状态。发现旧方案错误则替换目标方案，并评估数据与消费者迁移，不能以兼容为由保留错误语义。

### 就绪、异常与完成门槛

**可以交给开发的切片**必须有明确US/FR/AC覆盖、可观察预期、输入合同、适用质量门槛、权限与副作用边界、经过评审的必要设计及已知依赖。PRD存在或模板填满不代表就绪；决定性问题未解决只阻塞相关切片，允许准备不依赖该决策的合同和受控样本。正式质量验收前冻结样本、分母、环境、版本和阈值，未知目标不能由agent编造。

开发交接逐项核对适用的正常、空、加载、错误、无权限、输入校验、并发冲突、重复操作、停止/恢复和未知外部效果。明确用户能看到什么、保留什么输入、下一步能做什么；静态页面不套远程加载，读操作不偷偷执行采集，保存草稿不偷偷启用，通知静默不偷偷停止采集。

故事用INVEST核对独立价值、可协商方案、可估量、足够小和可测试；真实依赖保留。没有团队容量、历史吞吐量或来源准入证据时，不编造人员、故事点、日期或固定相对工期。七日自然观察属于完整监测/提醒消费链的验收，不是提醒开发前置，也不是所有模块的统一测试周期。

**代码完成**以AGENTS要求的检查和独立审查为准；**能力可用**以对应真实AC证据为准。独立审查至少核对原始意图覆盖、业务行为、数据库/合同完整性与验证边界，不能由实施者自检替代。文档结构检查、模型JSON成功、手动发送或健康检查均不能替代用户收到自然达标提醒。

## 维护方式

Obsidian直接打开`ripplesight-server/docs/`，通过[文档视图](views/文档.base)按目录和编号浏览。新增需求接续当前最大编号，同时维护同编号、同名称的requirement、prd、design、plan；增删或更名同步修正四目录、H1及引用。编号仅为追踪键，允许多个编号合为一个用户流程，也允许一个编号拆为多个开发切片。research不进入业务编号序列。

项目文档仅用Markdown/Git，不维护统一正文或历史归档副本。可使用templates可选模板，不强制frontmatter；共享.obsidian配置保留，个人布局、缓存和凭据留本机。业务报告Obsidian导出独立于项目文档。

仓库根目录BACKLOG（进度）、PROJECT（技术架构）、AGENTS（工程规范）不在vault内复制。

## 检查

在frontend/执行`pnpm docs:check`检查链接和锚点；工具回归为`pnpm test tests/docs/documents.test.ts`。检查同时核对四目录文件名集合、H1和从00连续的编号；工具通过只能证明结构与引用有效，业务完整性和方案合理性仍须独立审查。不运行文档站或发布流程。

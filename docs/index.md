## 阅读顺序

给人和 AI 的建议顺序：

1. [需求与验证入口](product/reference/04-需求与验证入口.md) → [AI 任务协议](product/reference/05-AI任务协议.md) → [进度与优先级](product/reference/01-进度与优先级.md)的当前检查点。
2. 先核对 Figma 原稿与 frontend/DESIGN.md，再按实际接口依赖阅读[页面需求](product/prd/03-PRD-全站页面需求.md#页面总表)、[收敛结论](product/reference/14-页面驱动的收敛方案.md)及源码，核对输入、输出与数量。
3. 阅读相关[决策](#决策)与[工程规范](product/reference/03-工程规范.md)，只补充当前场景需要的边界。
4. 获准验证后，用一张 POC 卡限定范围；需要核对实现时再读源码、[技术架构](product/reference/02-技术架构.md)和实际证据。
5. 原执行计划（`product/plan/`）作为历史执行依据按需查阅；当前阶段不据大计划自动推进实现。

2026-10-08 用户决定撤销在线项目知识库，恢复 docs 下的 Markdown/Git 管理并保留 Obsidian，使用方式见 [README](README.md)。旧工作台文档知识库需求，见[workspace 项目知识库专项 PRD](product/prd/02-PRD-workspace项目知识库.md)与[执行计划](product/plan/01-PLAN-workspace项目知识库.md)。它们已标为废弃，仅供历史追溯；当前不运行文档站或网页编辑。

每份文档开头都有元数据（frontmatter）：`type`、`title`、`summary`、`status`、`updated` 等。AI 可以先读元数据，再决定打开哪份文档。

## 写作规则

1. **一份文件只讲一件事**：能力文档控制在约 6000 字符以内，决策和记录各控制在约 2000 字符以内，PRD 与执行计划各控制在约 12000 字符以内。
2. **用模板新建**：`templates/` 有能力、决策、验收记录、调研、[执行计划](templates/05-执行计划.md)模板；[POC 验证卡](product/reference/06-POC验证卡.md)直接在阅读入口提供，元数据字段不能少。当前优先用验证卡描述一个场景，避免先扩写整份方案。PRD 使用 `type: prd`，保存到 `product/prd/`；执行计划使用 `type: plan`，保存到 `product/plan/`，记录任务验收、容量和依赖，不另记任务进度。
3. **规则只写一处**：产品规则写在 `decisions/`，技术约定写在根目录的 PROJECT/AGENTS，进度只写在根目录的 BACKLOG。
4. **改决策要本人同意**：旧决策不删除，把 `status` 改成 `废弃`，并新建一条决策替代它。
5. **验收结果一次一份**：放在 `records/`，用 `capability` 字段指向对应能力，并同步更新该能力文档的 `status`。
6. **命名**：文件夹用英文（`product/prd/`、`product/plan/`、`product/reference/`、`capabilities/`、`decisions/`、`records/`、`research/`、`templates/`、`views/`）；文档用“两位编号-中文名”，例如 `capabilities/04-评论舆情.md`；验收记录和调研以日期开头，例如 `research/2026-10-06-开源方案调研.md`。**编号按所在目录独立从 01 顺排，不跨 PRD、PLAN 或产品参考共用序列**。新文档取本目录下一个未用的编号；完成本次分类编号修正后，已有编号不随排序或版本变动，不复用已删除编号。目录迁移或编号调整需同时更新所有链接、元数据关联与索引。
7. **链接用标准相对路径** `[文字](https://github.com/StephenQiu30/Ripplesight/blob/7739c49961dd40ae02ccfa2aa1fe41def62d854d/docs/路径.md)`，不用 `[[双链]]`。
8. 用简单的话写；除文件名编号和 PRD 中的 KR 外，不另起编号体系。标清用户原话、AI 提案、源码事实与运行结论；未执行不写成通过，待核对不写成已确认。

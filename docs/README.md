## 3. 写在哪里

| 内容 | 唯一位置 | 不写的内容 |
|---|---|---|
| 用户问题、范围、FR/NFR/AC、产品决策、执行目标摘要 | PRD | 实现状态、证据、日期快照 |
| 现行技术合同：领域、接口、事务、数据、任务、错误 | Design | 进度、证据、产品决策 |
| 执行目标、可度量结果、工作包状态、步骤与 checklist | PLAN | 第二份需求或证据 |
| 外部资料、平台与竞品调研快照 | Research | 需求或验收结论 |
| 跨计划的总体进度、优先级与阻断汇总 | BACKLOG | WP 细节与步骤 |
| 实际证据与未通过条件 | Acceptance | 计划或预测 |

- 共享规则只在一处定义，其他文档引用编号（如 NFR-001-103、DEC-001-213），不复制原文。
- 临时实施过程、运行快照、视觉参考和版本迁移从 `git log -- docs` 查阅，不另存文档；清理文件不取消需求或改变未通过结论。
- 优先级没有访谈、触达或工时数据时用定性判断，不编造分数或工期。

## 4. 编号规则

- **PRD / Design / Research / Acceptance**：`<类型>/NNN-中文主题.md`，NNN 为领域号，PRD 与 Design 同号成对；新领域取下一个未用领域号（当前为 009）。
- **PLAN**：`plan/NNN-MM-中文主题.md`，NNN 为所属 PRD，MM 为该 PRD 下的计划序号；一个 PRD 可以有多个 PLAN，跨领域计划挂在主责 PRD 下。标题以 `PLANNNN-MM` 开头。
- **条目**：`FR/NFR/AC/BR-<领域号>-<序号>`；产品决策 `DEC-001-xxx`、未决项 `OPEN-001-xxx` 只在 PRD001 §8；工作包 `WP-<PRD号>-<三位序号>`，在同一 PRD 的所有 PLAN 内唯一；计划内可度量结果 `R1…`；证据 `EV-<验收号>-<序号>`；BACKLOG 工作代号 `BL-NN`。

## 5. PLAN 规则

每个 PLAN 采用同一结构，方法参照 OKR（目标定性、结果定量），但不另建 OKR 文档：

1. **目标**：一句话、以用户结果表述的定性目标，并说明现状。
2. **可度量结果**：3—6 项，每项写基线、目标值、验收依据（AC 编号）和反作弊/反向指标；描述结果而非产出，不以“交付 N 个功能”作为结果。
3. **范围与非目标、执行步骤**（按需）。
4. **工作包**：`WP-NNN-xxx`、状态（`planned → ready → in_progress → done`，缺条件为 `blocked`，明确暂停为 `paused`）、前置与完成条件。
5. **风险与阻断**。

角色：产品决策由本人负责；实现由 Codex 执行；任务拆分、复核与真实验收由 Claude 负责。没有人员或工时数据时不写日期承诺。

**检查节奏**：每周按结果给出红/黄/绿；完成一个工作包或外部条件变化时复核目标值；计划收尾时给每项结果打分——0.0—0.3 明显未达成（复盘原因）、0.4—0.6 有进展未达标、0.7—0.9 合理的挑战性目标、1.0 达成或目标偏保守。打分只说明计划完成度，不代替 AC 通过。

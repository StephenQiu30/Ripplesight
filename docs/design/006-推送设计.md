# 推送设计

本设计定义 M5 的领域合同，遵循 [总设计001](001-热点舆情监控平台总体设计.md)。需求为 [PRD 006](../prd/006-推送需求.md)，当前工作见 [BACKLOG](../../BACKLOG.md)。

## 1. 范围与不包含

M5 单独验收报告定稿后的渠道投递与状态恢复。飞书自定义机器人暂缓；SMTP 邮件默认关闭，两渠道分别核收。推送不作为 M1 信息获取、M4 报告生成或 Obsidian 导出的完成条件。现行需求与排期分别见 [PRD 006](../prd/006-推送需求.md) 和 [BACKLOG](../../BACKLOG.md)。

## 2. 验证边界

代码、受控技术、真实运行与产品验收分别判断。现行任务与未完成条件见 [BACKLOG](../../BACKLOG.md)，实际证据见 [Acceptance](../README.md)。

## 3. 架构与数据流

### 3.1 渠道与秘密

- 飞书自定义机器人使用 Webhook 和可选签名密钥，暂缓启用；SMTP 邮件使用标准库适配器，默认关闭。推送不参与信息获取、日报生成或知识库写入的验收门禁。
- 秘密只从环境变量读取（`HOTKEY_FEISHU_WEBHOOK_URL`、`HOTKEY_FEISHU_SECRET`、`HOTKEY_NOTIFICATION_SMTP_HOST/PORT/USERNAME/PASSWORD/FROM_EMAIL`）；`notification_targets` 表只存目标名、类型、收件人和所用环境变量名。
- 飞书设计为摘要卡片：概览 + Top 3 + Web 报告链接 + 已存在时的 Obsidian 链接；邮件从同一固定稿件渲染完整 HTML。不存在的笔记不写入链接。

### 3.2 投递状态

- `notification_deliveries` 保留报告唯一键 `(report_id, report_version, target_id)`，其他subject按目标、subject_kind及dedupe_key幂等，详细合同见Design048；状态 `pending → sending → succeeded | failed | unknown`。
- 发送前先把状态提交为 `sending`；请求前就失败（连接不上、4xx 参数错）记 `failed`，可自动重试 3 次；请求已发出但超时或进程中断，记 `unknown`，**不自动重发**，在 Web 上提示人工确认。

`reports` 只提供已定稿报告及版本，`notifications` 拥有目标、投递和渠道适配器；独立调度在启用渠道时扫“已定稿且无相同版本投递”创建 `notification.send`。`jobs` 负责持久执行/预算，渠道密钥只从进程环境读取。渠道结果不反向更改报告。

## 4. 领域、数据与状态

`notification_targets` 只保存目标名、类型、收件人和环境变量名，禁止秘密明文；新目标默认disabled，已受理投递固定目标修订；更换地址升目标修订，旧任务因过期不得发送，不改写旧投递对象。`notification_deliveries` 保留报告唯一键 `(report_id, report_version, target_id)` 及其他subject的幂等键 与 pending → sending → succeeded/failed/unknown。投递审计通过attempts/resolutions记录外部发送阶段、脱敏响应、人工判断、操作者/时间/依据；确认已收到转succeeded，确认未收到转failed，显式新发送仍须单独动作，不能确认后自动重发。SMTP使用标准库smtplib/email.message，TLS验证、头注入防护，DATA后不确定结果为unknown；SMTP接受与收件方实际收到分开验。

## 5. 接口与页面

运营目标提供 `/api/operations/notification-targets` 的GET/PUT、投递记录读取和unknown确认操作；字段、状态、owner/CSRF 和冲突使用 PRD006 与本文合同，经运行OpenAPI生成客户端。Web显示报告版本/目标、失败原因和人工确认依据，配置只写允许的环境变量引用，不展示秘密。真实渠道须独立验收，SMTP真实发信须平台服务就绪及用户主动订阅其已验证邮箱；飞书继续暂缓。技术准备不启用任何真实渠道。

## 6. 调度、执行与截止

仅已启用渠道且报告定稿时创建确定性 `notification.send` Job；硬截止 60 秒，外部请求也受更短读/连接超时。日报目标为设定生成时间后 15 分钟内送达（默认 08:15 前），周报目标为每周一 08:15 前送达；按渠道和接收方核对实际收到的时间，M4 的 600 秒生成硬截止不能当作送达时限已满足。发送前先提交 `sending`，同一 `(report_id, report_version, target_id)` 不重复受理；Kafka 重投不得无条件重发。每个渠道启用前须明确条件与收件人，飞书暂缓期间不触发。

## 7. 失败语义与恢复

请求前明确失败可记 `failed` 并在上限内有限重试；请求可能已发送后超时或进程中断记 `unknown`，禁止自动重发，等待人工确认/处置。明确成功需核对渠道响应与持久记录；只拿到 HTTP 200、健康检查或任务完成均不足以证明目标已收到。人工确认动作须审计，不能回写为未有证据的成功。

## 8. 安全、风控与可观测

飞书 Webhook/签名密钥与 SMTP 凭据只来自 `HOTKEY_` 环境变量，不入数据库、Git、日志或错误体；报告链接只指真实可访问位置和已存在笔记。按目标/报告版本记录受理、尝试、成功、失败、未知与人工处置数量，日志脱敏；授权用户才可查看目标和确认未知状态。

## 9. 验收设计要点

受控验证唯一键、发送前/后失败分界、超时 unknown 不自动重发及人工确认；启用后分别用真实飞书/SMTP 目标核对送达时间、内容、版本和失败恢复，包含周一 08:15 前收到周报及连续 3 个自然日日报均在设定时间后 15 分钟内收到。来源/Codex 故障生成的缺口或模板版报告、vault 只读时的已定稿报告仍须按获准渠道独立核对送达。每个渠道分别验收，飞书暂缓期间不发送真实请求；平台管理员配置 SMTP 发信凭据，用户在账户验证邮箱并主动选择主题订阅。

飞书须待用户重新排期、指定获准群/机器人且私有配置就绪后，才恢复实施或真实发送；Webhook 签名、时间戳、超时和应用级错误码须核对，HTTP 200 带业务错误不能判成功。SMTP 通过不解除飞书暂缓，也不替代获准群接收方的真实收到时间、报告版本和确认记录。

## 用户邮件订阅实现

notifications/email_subscription.py 主责个人订阅，identity/notification_reading.py 提供当前已验证绑定邮箱的领域读取。复用 notification_targets：按 owner 确定性目标ID、固定“我的报告邮箱”名称，仅 email/report，无任意收件人或用户指定owner。GET/PUT /api/notifications/email-subscription 使用普通会话、写入CSRF、operation_id审计幂等及expected_revision CAS，无运营授权。PUT从identity取绑定邮箱；停用保留旧事实，重新启用计时避免历史回发。邮箱变更、主题取消或目标停用后，准入和执行前复验拒绝旧任务。账户“报告通知”管理订阅，主题报告设置选择发送；仅调用生成客户端。缺平台SMTP时可保存用户偏好，明确暂不能发送。目标不订阅刊物、精选或Codex。

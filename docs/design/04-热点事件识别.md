# 04 热点事件识别

需求依据：[04 热点事件识别](../requirement/04-热点事件识别.md)；开发交接：[04 热点事件识别](../prd/04-热点事件识别.md)；agent工作拆解：[04 热点事件识别](../plan/04-热点事件识别.md)。以下为目标设计，未据此改变代码或业务数据库；共享架构、事务及选型原则见[00 产品目标与边界](../design/00-产品目标与边界.md)。

## 设计目标与业务流程

先区分召回候选、确定性匹配、语义相关与事件归属；事件根据主体、动作、时间等辨识，不能只按标题相似归并。保留不足证据线索与必要排除理由，支持按相关性和时效性解释排序。

1. **相关性前置**（FR-04-01）：情感分析失败不改变有效相关性；未分析不当无关。
2. **具体事件识别**（FR-04-02）：同主体不同事情、旧闻重发、传闻与确认、转载分别进入评测。
3. **可解释归并**（FR-04-03）：每次归并有输入、判断、理由和事件修订；单源/多材料不假称独立多源证实。

## 状态、交互与失败恢复

高互动或模型高置信度不能替代事实依据；未召回与模型排除可区分。验收场景：同公司在两天发布两个产品，另有旧闻转载、传闻与取消消息；判断相关性并生成或关联事件候选后，两个发布不误合并；转载不造新事件；传闻/取消有状态和证据；无法判断允许暂缓。

界面先呈现完成任务所需的事实与限制，再给出动作和回执。遵循[11 质量评测与验收](../design/11-质量评测与验收.md#共享状态与反馈)的共用状态、焦点和过期响应规则；无外部读取的静态内容不套远程加载状态。数量、分页、排列由内容规模和性能基线决定，不继承旧固定页数/栏宽。

## 数据库设计

目标关系模型；字段、键、查询索引和生命周期由同编号需求推导。类型为候选表达，正式DDL需验证枚举、长度、外键、容量、迁移与回退；本轮不执行建表。共享owner复合引用和当前版本指针规则见00。

### `events`

用途：用户主题下稳定可跟踪的具体事情身份。

| 字段 | 候选类型 | 可空 | 业务含义与规则 |
|---|---|---|---|
| id | UUID | 否 | 主键 |
| owner_id | UUID | 否 | 用户 |
| topic_id | UUID | 否 | 主题 |
| current_revision | BIGINT | 否 | 当前有效修订 |
| classification | VARCHAR(24) | 否 | clue、event、insufficient |
| state | VARCHAR(24) | 否 | active、merged、archived |
| canonical_event_id | UUID | 是 | 合并后指向保留身份 |
| first_seen_at | TIMESTAMPTZ | 否 | 本机首次发现 |
| updated_at | TIMESTAMPTZ | 否 | 最近更新 |

键与完整性：PK(id)；UNIQUE(owner_id,id)；复合FK主题及可选目标事件；合并目标不可自指/成环。

查询与索引候选：owner_id,topic_id,updated_at DESC,id；owner_id,canonical_event_id。 索引用真实查询基线复核，不能把索引存在当性能达标。

生命周期：合并保留旧身份重定向，历史通知不重写；拆分的新身份继承关系可审计。

### `event_revisions`

用途：事件摘要、辨识要素和证据范围的固定修订。

| 字段 | 候选类型 | 可空 | 业务含义与规则 |
|---|---|---|---|
| owner_id | UUID | 否 | 用户 |
| event_id | UUID | 否 | 稳定事件 |
| revision | BIGINT | 否 | 修订号 |
| classification | VARCHAR(24) | 否 | clue、event、insufficient；该修订时的证据分类 |
| lifecycle_state | VARCHAR(24) | 否 | active、merged、archived；该修订时状态 |
| canonical_event_id | UUID | 是 | 合并后规范身份，保留同owner同topic继承 |
| title | TEXT | 否 | 可读事件名 |
| summary | TEXT | 否 | 仅基于证据 |
| identity_factors | JSONB | 否 | 主体、动作、时间、对象/地点及未知 |
| previous_revision | BIGINT | 是 | 首修订空 |
| operation_id | UUID | 否 | 修订幂等键 |
| reason | TEXT | 否 | 新证据/纠错理由 |
| created_at | TIMESTAMPTZ | 否 | 修订时间 |

键与完整性：PK(owner_id,event_id,revision)；UNIQUE(owner_id,event_id,operation_id)；复合FK事件；previous_revision<revision；FK(owner_id,event_id,previous_revision)→event_revisions(owner_id,event_id,revision)。一笔合并/拆分操作可对多个事件各写一个修订。

查询与索引候选：owner_id,event_id,revision DESC。 索引用真实查询基线复核，不能把索引存在当性能达标。

生命周期：不可原地覆盖；当前许可改变只影响可读投影，不造历史正文。

### `event_evidence`

用途：按修订冻结材料成员与归并解释。

| 字段 | 候选类型 | 可空 | 业务含义与规则 |
|---|---|---|---|
| owner_id | UUID | 否 | 用户 |
| event_id | UUID | 否 | 事件 |
| revision | BIGINT | 否 | 事件修订 |
| object_id | UUID | 否 | 原生材料身份 |
| content_version_id | UUID | 否 | 实际材料版本 |
| relation | VARCHAR(24) | 否 | primary、supporting、context、contradicting |
| assessment_id | UUID | 是 | 经校验的分析结果 |
| reason | TEXT | 否 | 为什么属于这件事 |

键与完整性：PK(owner_id,event_id,revision,object_id)；复合FK事件修订、材料所属版本及分析结果；跨事件共享仅作明确关联，不误改身份。

查询与索引候选：owner_id,object_id；owner_id,event_id,revision,relation。 索引用真实查询基线复核，不能把索引存在当性能达标。

生命周期：当前/历史成员分开投影；撤权立即不可读但保留最小非敏感修订审计。

## 事件修订、候选与排序

事件当前行只作最新投影；分类、生命周期和规范身份在每个修订冻结，历史读不会套用最新状态冒充当时事实。合并默认限定同owner同topic；跨主题相关事件用关联解释，不无声改主题。canonical不得自指、形成环或跨owner/topic。current_revision复合FK至event_revisions，合并涉及的所有旧/新事件及纠错回执同事务比较预期修订。

归并输入先记录来源召回限制，再取确定性匹配和09有效相关结果；保留必要候选、排除原因及版本，用于区分未召回、硬过滤和模型判断问题。主题、主体相同不直接确认同事件；语义候选可采用相似度，最终依据主体/动作/时间/事实差异。列表排序消费09的相关性/时效解释，不把热度、可信度混成一个无定义分数。

## 当前版本完整性

当前指针采用复合FK：`events(owner_id,id,current_revision)→event_revisions(owner_id,event_id,revision)`。身份首次建立与初版、后续新版本/修订与当前指针/审计同事务；循环关系在DDL采用可延期约束并在提交前验证。不能用应用中随意选最大版本替代当前有效版本。

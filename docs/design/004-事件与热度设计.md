# 事件与热度设计

本 Design 是 M3 Epic，遵循 [总设计001](001-热点舆情监控平台总体设计.md)。需求为 [PRD 004](../prd/004-事件与热度需求.md)，当前候选验证入口为 [Plan014](../plan/014-事件候选与稳定身份执行计划.md)。本文中的“已有”仅表示代码或指定运行证据，不代表产品验收。

## 1. 范围与不包含

事件领域将内容证据组织为事实和故事，提供固定成员阅读、人工归属修订、跨故事合并/相关边、讨论再匹配和独立来源热度。原生榜单仍是来源信号，不能直接创建事件。AIHOT 全量迁移由 Design048 承接；真实来源、模型与渠道验收仍需单独记录。现行需求见 [PRD004](../prd/004-事件与热度需求.md)。

## 2. 当前能力与证据分层

当前实现包含候选归并、固定成员/历史修订阅读、事实与直接进展、六类人工纠错、独立来源热度、两轮跨故事判定、相关边和持久向量/等待讨论再匹配，均使用原 Job、预算和 AI 账本。真实 PostgreSQL 与受控 HTTP/模型测试覆盖幂等、冲突、许可收紧、免费恢复和 unknown；事件与运营页面已有隔离样本的桌面/窄屏浏览器记录。这些证据不代表真实三平台准确性、真实供应商计费、真实渠道送达或持续生产验收。

## 3. 架构与数据流

- 原主题和编辑内容候选使用 `pg_trgm` 标题相似度（初值 ≥ 0.4）及 72 小时时间窗，主题材料还须当前关键词命中；模型确认和事实划分后才成为事件。独立 embedding 默认关闭，开启后服务于最近 6 小时等待讨论的语义召回，两种窗口和分数分别保留。
- 独立来源热度使用 48 小时窗口、24 小时半衰期和来源参与者去重，以可比的 6 小时窗口展示趋势。历史互动 v1 公式和未知掩码保留为不同量纲，不覆盖历史快照。
- 人工合并/拆分优先，自动聚类不覆盖。

`content` 提供已验收内容的身份/版本、代表评论和相关性引用，`events` 拥有事件候选、成员、人工修订和热度计算；`ai` 仅对候选归并与摘要作结构化判断。独立调度扫表创建 `events.cluster` Job；`jobs` 管执行、幂等和预算，`events` 在自身事务中保存事实和快照。报告/知识库可在 M3 验收后消费事件只读 DTO，并在报告引用热度时附公式版本和计算口径，不反向写事件。

## 4. 领域、数据与状态

以下数据合同已有实现和受控验证；真实来源和生产准确性仍未验收。

- `events`：owner、topic、revision、标题/摘要、first_seen_at、active/merged 与 merged_into_id；`event_members` 固定内容身份/版本、来源、加入/移除修订及自动/人工来源，同一 owner/topic/content 只属于一个当前事件。
- `event_candidates`：以排序后的内容版本集合、窗口、prompt_version 生成唯一指纹；状态 pending/confirmed/rejected/failed，保留 ai_call_id 与错误。模型调用在数据库事务外，提交前锁事件并检查修订，人工变更后旧模型结果不得覆盖。候选分两类：新建候选只含未归并版本；追加候选以一个 active 目标事件为锚，成员为该事件当前成员中最近的上下文版本加新增未归并版本，`expected_event_revisions` 固定 `{event_id: revision}` 并计入指纹。追加确认只新增成员（`added_revision=revision+1`）、事件修订加一、首次出现取两者较早值，不改写已有标题/摘要；目标事件非 active、修订变化或上下文成员已不在该事件时按冲突失败并重新候选。
- `event_revisions`：operation_id 唯一，记录操作者、原因、操作前后成员与事件修订；合并/拆分在同一事务按稳定顺序锁行，保留人工排除约束。
- `event_heat_snapshots`：唯一(event_id,event_revision,window_end,formula_version)，固定输入观测、缺失掩码与分项。重算产生新快照，不改历史证据。

Plan014 候选验证涉及的现行目录职责：`events/models.py` 只映射候选、事件和成员；`schemas.py` 定义候选输入与结构化决策；`clustering.py` 生成固定指纹、受控提示词与 pg_trgm 候选；`services.py` 组合 `analysis` 标注身份、`content` 内容/来源/首次出现 DTO 与 `monitors` 当前规则 DTO，负责候选、Job 受理、模型调用外置及提交事务。`analysis/services.py`、`content/services.py` 和 `monitors/services.py` 各自提供本领域只读 DTO/锁接口；成员来源外键指向真实内容身份。`worker/scheduler.py` 注册半小时扫描，`worker/app.py` 装配处理器，`core/config.py` 按保护模型目录的最大超时设有界截止（cluster/digest 至少600秒），并默认关闭 `HOTKEY_EVENTS_CLUSTER_ENABLED`。新增包经架构测试显式登记；历史运行库的保留与重建沿用 [总设计001 §6.3](001-热点舆情监控平台总体设计.md) 和 [PROJECT](../../PROJECT.md) 的恢复合同。

新增模型进入唯一 `backend/database/schema.sql` 和 metadata 注册；保留运行库的变更先满足总设计001与 PROJECT 的同版本备份、恢复、导入校验及回退合同，不就地运行完整 Schema。

### 4.1 全量迁移的事实与人工修订合同

用户全量迁移决定由 Design048 承接，本轮继续使用现有 `events.cluster`、AI账本、Job/Outbox，不引入第二套归组任务。`events` 是 story 稳定身份；`event_facts` 是独立 occurrence 身份；`event_fact_assignments` 按事件修订保留事实归属与 root/development/background/roundup/unreviewed 关系；development/background 必须直接指向本事件 root，不能经进展递归扩展。盘点独立建事件，不能作为普通事件的自动合并根。`event_fact_members` 按事实修订记录 primary/report/mention 及对应历史 EventMember，固定原内容版本。文章修订沿用原 content_id，评论与热榜身份不改写。

`events/fact_models.py` 映射七张新增表；其余为 `event_grouping_overrides`（standalone/manual/regroup_pending）、`event_revision_operations`（operation_id、输入hash、before/after/result）、`event_derived_contents`（事件revision与输入hash绑定pending/valid/failed/stale）、`event_grouping_assessments`（原候选、冻结事实上下文、结构化判断及缺失/格式错误诊断）。所有日期明确 TIMESTAMPTZ。历史 EventMember 唯一键包含 event_id，允许同一内容在不同事件相同修订号出现，另有 scoped member identity 外键；当前 owner/topic/content 唯一归属仍保留。

`events/corrections.py` 拥有人工事务：先 owner/topic 锁，再稳定 ID 顺序锁全部事件；操作输入要求 operation_id、原因与所有影响事件 expected_revision。同 operation_id 与相同hash重放结果，不同hash返回幂等冲突。合并把旧事件标 merged 并保留规范重定向；拆分/移动全事实保留 fact_id，移动部分事实成员生成新 fact_id；排除写 standalone，显式重新归组才解除，失败保留 regroup_pending；自动结果提交重查 override/revision。事实合并保留旧 fact_id→规范 fact_id。重排关闭旧成员/事实归属区间，写新的当前成员，原版本/原正文和历史revision不变。变更同事务失效派生文本，invalid状态title/summary/latest_progress均为空；不能继续展示旧文本。空事件保留稳定地址，有目标时重定向，排除后无规范目标的空事件读取仍404。

`events/facts.py` 拥有事实读取/确定性兼容补录和模型归组写入，跨域正文只取 `content/event_reading.py` DTO；缺失/格式错误关系是待复核诊断，不自动当可靠UNRELATED。新增与追加使用原candidate输入集合和expected_event_revisions，冻结事实修订/root标记/人工约束后调用模型，提交重查。SAME_OCCURRENCE先按confidence再召回分数；SAME_STORY仅选择直接root；ROUNDUP必须非空候选全为盘点；signal-only不能创建事件。候选、判断、业务归属与AI回执分开保留，模型外置和预算合同不变。

独立来源热度作为 `attention-v1-48h-halflife24h` 并行指标：48小时窗口、24小时半衰期、每个参与者只计最新证据，group优先于owner再source；6小时前可比窗口必须排除新增/采集落后参与者，缺失基线显示unknown。至少2个参与者且包含editorial，保留new/up/down/flat/unknown与新出现/骤增/上升标签。不覆盖现行互动v1量纲或未知掩码；快照读取复核撤回/可读性和来源角色。细化执行合同随实际 writer/worker 进入本节，算法测试不能单独宣称热度闭环。

## 5. 接口与页面

事件读取为 `GET /api/events`、`/{id}`、`/{id}/members`、`/{id}/facts` 和 `/{id}/related`；热度为 `/hot`、`/{id}/heat` 与 `/{id}/heat-history`。人工修订统一 `POST /api/events/corrections`，输入 operation_id 和 expected_revisions，成功200、冲突409、越权/不可见404，写入需CSRF。来源角色 `/attention-sources` 的 PUT 需要独立 operator Token 和 CSRF，GET 匿名可读。静态路由在动态ID之前。接口复用统一 DTO、游标和 ErrorView，由运行 OpenAPI 生成客户端。页面显示正常、空、加载、错误、证据失效与历史修订，不把无事件等同来源无内容；产品验收分别记录。

### 5.1 已确认事件与固定成员阅读合同

`events/reads.py` 的 `EventReadService` 拥有 PostgreSQL REPEATABLE READ / READ ONLY 事务，以当前 Demo `owner_id` 过滤自身事件/成员模型；整个请求使用同一事件修订、成员与证据生命周期快照，不用跨事务的最新版本替换。跨领域内容仅通过 `content/event_reading.py` 的 `load_event_member_content_in_transaction` 读取，不直接导入内容 ORM。`content/schemas.py` 定义 `EventContentReadReference` / `EventContentReadView`，后者返回真实内容身份、指定成员版本的最后一个可读观测、完整正文、文本范围/来源/提取依据、引用/转帖关系、互动未知掩码和当前可见性。可读性使用 evidence 领域的过期与删除指令投影，严格同时匹配 owner/content/version；旧版本不可读时禁止回退新版。不存在可读观测的关系目标只保留来源引用，不提供本地可读目标 ID。

列表只返回 active 已确认事件，支持 topic/source、成对且带时区的最多31天首次出现窗口、文本 query 与分页。来源筛选、搜索与返回的来源计数只基于可读固定成员；不可读事件从分页前过滤，零可读成员的详情/成员读返回404。列表游标绑定 owner 和全部筛选，按 first_seen_at 倒序、id 顺序推进。成员接口用 revision（默认当前）选择 added_revision≤revision 且 removed_revision为空或大于revision的版本成员，范围1..当前修订；分页游标绑定 owner/event/revision，默认当前修订改变时旧游标拒绝。成员保留身份与版本、来源和归属修订，不可读成员返回 availability=unavailable、content=null，不泄露其正文和入口。

`EventReadView.evidence_state` 描述当前成员 complete/partial，`derived_text_available` 单独说明派生标题/摘要是否可读。缺少独立派生文本血缘表时，保守要求当前与历史移除成员的全部固定版本仍可读，任一缺失即 title/summary=null；成员数量不冒充内容可用数量。成员表现有代表评论仅固定 comment_id，因此内容 DTO 返回该帖线程中指定评论的最新可读版本及观测时间，并显式给出 none/readable/unavailable，不能称为事件固定评论版本。读取均 Cache-Control:no-store，不产生来源请求、模型调用、Job 或账本变更。HTTP 文件为 `api/routers/events.py`，依赖与总路由由现有 api 装配，错误码为 invalid_event_filter、invalid_event_cursor 和 resource_not_found。

已合并事件的详情及默认当前成员读取沿 merged_into_id 解析到同 owner 的 active 规范事件，返回其身份并用 redirected_from_event_id 标明原请求；显式 revision 的成员请求仍读取原事件历史。循环或缺失规范事件返回404。代表评论失效同样隐藏可能由其派生的标题/摘要。

## 6. 调度、执行与截止

`events.cluster` 按UTC半小时槽扫描：同一调度进程每个槽最多成功扫描一次，调度轮次跨过槽起点时在该槽内补扫，不依赖轮次恰好落在:00/:30；重启后当前槽可再扫一次，由候选指纹保证幂等。初始每候选组最多20成员、模型输入24,000字符、Job硬截止600秒；输入不足保留待归并，超过上限分批并保留剩余候选。每次扫描按标注时间倒序（最新优先）最多读取每(owner,topic,content)去重后的2000个未归并输入，较早输入已在此前各槽参与过比对，超出部分不得使整轮失败并记录截断；标题相似度以单条集合查询在PostgreSQL `pg_trgm` 内计算，禁止逐对往返。未归并输入先与同主题“存在首次出现在72小时内的当前成员”的 active 事件比对（事件自身首次出现可早于72小时），达阈值者形成追加候选，其余再做新建候选聚类。按候选版本/窗口幂等，提交时检查人工修订。

`events.heat` 按 UTC 整点窗口受理小时快照 Job，硬截止300秒，按 owner/事件身份/事件修订/小时窗口幂等。Scheduler 重复扫描会跳过已有快照或已受理任务，使用稳定身份 keyset 分页继续覆盖全部活动事件；单轮最多新增1000个原 Job，后续轮次继续扫描尾部。实时热榜读取在当前许可守门下计算全部活动事件的48小时独立来源热度，以有界内存保留精确前十，不以更新时间截取前1000事件代替完整榜单。历史互动公式与独立来源公式分别保留；上述保护值与性能须随真实样本验证，不能据此宣称性能已通过。

POC 期间事件扫描开关默认关闭，现有运行环境不会因这次代码提交自动发起 Codex 请求；受控测试只用假模型输出。开启真实模型与三平台产品取证须在用户后续授权和 M1 前置条件具备后进行。

公式初版固定自然对数：Σ ln(1+赞+2×评+3×转+0.01×浏览)×来源权重 + ln(1+帖子数)，来源权重初值均为1。缺失量只在分项运算中贡献0并保留缺失标记；所有互动指标未知时热度为null，不能对外显示为0。升温比较近3小时增量与此前24小时的8个3小时增量均值；基线不足、均值≤0、窗口缺口或修订不可比返回 insufficient，不能制造升温结论。当前增量必须>0且≥基线3倍。参数校准和缺失输入影响随真实三平台验收记录。

## 7. 失败语义与恢复

模型不可用或候选证据不足时保留未归并/待复核状态，不能生成确定事件。失败 Job 保留输入版本、原因和可重放位置；重试不得覆盖人工合并/拆分，按版本冲突拒绝或重新候选。来源缺口、标注异常应随事件输入审计传播；热度不可把未知量默认为零覆盖。

## 8. 安全、风控与可观测

仅处理已有授权的来源数据；人工操作需 owner 授权和审计。模型输入最小化且外部内容按不可信文本处理。记录候选数、模型确认/拒绝、人工修订、公式版本、窗口、输入缺口、重放/冲突和预算；不记录敏感正文到通用日志。

## 9. 验收设计要点

用已验收的真实三平台同事件样本核对事件成员、代表内容、来源分布、人工合并/拆分和升温；单条热榜命中、模型输出或内部样本均不能替代真实产品结论。先受控验证幂等、冲突、公式与失败，再作真实运行和人工复核。

### AIHOT 对照后的事实关系实现

[PRD004 FR-004-007 / AC-004-006](../prd/004-事件与热度需求.md#41-aihot-对照后的事实与进展关系) 的同事实、进展和背景已由 §4.1 的独立事实身份与修订关系实现；候选状态仍只表达模型受理结果。内容证据经 `content` DTO、判断经原 `ai`、任务和预算经原 `jobs`，没有第二套聚类管线。

原主题报道候选继续使用 `pg_trgm` + 关键词 + 72 小时窗口；等待讨论的6小时语义回溯已由独立持久向量和真实 `/embeddings` 协议实现，两者分别执行。48小时独立来源衰减与6小时趋势是版本化指标，保留历史 v1 互动快照。所有材料的固定版本、人工排除、代表引用、当前许可和租约 epoch 均在受理、付费前与提交时复验；新算法不覆盖历史公式。

## 10. 决策、风险与对照

沿用 DEC-001-203/207/208/212/215；DEC-001-215 已规定热榜命中先入内容再分析，事件后验。`pg_trgm` 候选阈值 0.4、72 小时窗口和热度公式来自原总设计 v3.2 §12，实施前需在真实样本校准；此处不新建 DEC-004-xxx。风险为跨平台误并、人工改动被重算覆盖及热度量纲偏差。对应原总设计 v3.2 §12、§8 事件输入及 §13 任务类型；历史来源 旧 Design 028 可追溯与可复现（已删除，见 Git 历史）。

### AIHOT 后到引用、重聚隔离与故事关系补齐

原生 quote/repost/reply 优先按内容域固定版本 DTO 解析同 owner、source、native_scope、external_id 的真实目标，不按相似标题替代身份。Scheduler 原事件扫描会重新读取等待材料；48 小时以内后到原帖可形成新的固定候选，人工 standalone/manual 保持优先。无 embedding 时不启动新增 6 小时语义重匹配，保留当前 72 小时 pg_trgm 方法版本和明确的运行状态。

regroup_pending 只作为自己的待处理查询，不能成为其他材料的候选证据。请求 operation_id 进入候选指纹，防止已判过的同版材料吞掉显式重聚；模型提交复核冻结 override revision，失败保留 pending，成功再解除，人工拆离优先。

`events/story_models.py` 的 `EventStoryLink` 仅持有同分区同主题无向 related 边、两端事件修订、至少两篇独立固定联系报道的证据和创建时间；两方向由读取投影，同一对不复制两行。读取复核事件 active、非 roundup、固定成员仍在原事实、原始证据仍可读及来源独立，任一不满足则隐藏。边不是事实成员，不参与热度或继承正文许可。

跨故事融合比较双方根事实代表报道；第一轮 SAME_OCCURRENCE/SAME_STORY 且 confidence≥0.8 后，反向第二轮须≥0.75，两轮通过才合入最早根，roundup 排除。复用原事件任务、AiCall/预算和持久阶段 checkpoint；主归组提交后独立原 Job 承接后处理，未知响应不自动再买。运营人工 merge 的 expected_revision/operation_id 合同不改变。

### 持久语义向量与后到讨论

`event_content_embeddings` 保存 owner、固定 content/version、model、requested_dimensions、文本指纹、实际维数、有限 JSON 向量、原 AiCall/Job 与阶段状态。它是事件召回材料，不授予内容许可。使用固定标题与正文组成至多 2000 字输入，完整同一模型、请求维数和文本哈希才可重用；维数零表示供应商默认，实际向量仍须 1..3072、长度一致且每个坐标有限。读取同时复核当前固定正文/Evidence/可见性，撤回材料不召回。

`events.embed` 复用原 Job、真实 lease 和 AiService 预算账本；适配器实际请求 OpenAI-compatible `/embeddings`，不要求聊天模型编造向量。`embeddings_enabled` 和 `ai_enabled` 均默认关闭，缺凭据同样停用。running 后进程丢失、未知响应均转 unknown，不自动重新购买；已落完整向量/CallID 的 response_saved 可以免费完成业务提交。原生 quote/reply 48h 匹配先于向量，源为 signal 时没有有效原生目标与兼容向量便保留未附着。

兼容向量开启时，新事实扫描近 6h 未附着 signal，cosine≥0.72 才候选，最多 4 个事实；cosine≥0.92 的近乎同文信号可直接固定到已确认事实，其他候选仍须关系判断。人工 standalone/manual 与 regroup_pending 保护在召回和提交两处核对；pending 单条只作查询，不作其他材料的候选证据。没有兼容向量时显式停用该语义分支，继续原生引用匹配。标题 pg_trgm 仅是旧主题候选召回，不代替语义向量。

### 全站编辑内容的事件入口（2026-10-02）

`analysis/event_reading.py` 在调用者事务内读取当前完整编辑结果：固定正文和引用材料仍可读、输入哈希不变、当前人工版本一致、相关性通过、非历史回补才可进入事件；按上游实际入口，低于精选分数但相关性通过的完整结果也可分组。只做 selection 的未完成结构结果不成组。提供标题、摘要、主体/发生框架和 run/manual/source 修订指纹，事件领域不读取编辑 ORM。来源暂停阻止新采集，不等同撤回已有材料；删除、许可收紧和保留期到期会使入口失效。

`monitors/editorial_events.py` 在首条有效输入时建立 owner 专属 UUID5 内部主题，固定 paused、无来源计划、无报告推送。它仅满足既有事件的主题分区与外键，不要求用户创建关键词主题，不出现在公开关注列表，GET、克隆、更新、恢复、暂停和归档均拒绝普通主题 CRUD。事件任务仍复用原 Job/Outbox/租约和预算。已有固定事件成员作为模型上下文时读取原成员版本，不因最新正文修订而替换或丢失；新输入在执行与提交时再次复核编辑版本、权限和人工分组状态。

### 等待中的讨论再匹配执行

`events/signals.py` 从内容领域有界读取最近首次接收的讨论资料与固定版本，来源角色必须明确为 signal；不要求讨论先运行完整精选分析。48 小时内的原生引用、转帖或回复优先直达已有确认事实，零模型调用。无原生目标且首次接收未超过 6 小时，只有当前许可有效的同模型/同维数持久向量才启用语义召回：至少 0.72、每事实最高分、最多四事实；最高至少 0.92 可直接归附，其余使用生产四类关系提示词并要求 SAME_OCCURRENCE/SAME_STORY 至少 0.8。盘点、未确认事实、人工拆离/独立内容和等待重新分组的材料不能成为他人的联系证据。

匹配受理与恢复复用原 `events.signals` Job 和 JSON 标量检查点，不新增队列或通知账本。范围冻结讨论版本、来源修订、候选事实/事件修订及固定报道，发送模型请求前记录阶段标记，完整响应和 AiCall ID 同事务保存。已保存响应免费恢复，已发请求但响应未持久化停为 unknown；提交前再次核对来源角色、材料可读性、向量身份、人工覆盖和任务租约。写入现有 EventMember 与 role=mention 的 EventFactMember，递增事件/事实修订并使旧摘要、热度失效；它不创建新事实。新事实或原帖后到后，扫描会为仍未附着的讨论产生新的冻结候选任务；超过等待窗口不补贴。

### 事件模型与向量的冻结计费合同

`events.cluster`、`events.digest`、`events.signals` 与 `events.embed` 在准备事务之后、原 AiService 预留预算和写入 running AiCall 的同一事务内再次复核固定材料、当前字段许可、Evidence、人工修订与原 Job 执行权。讨论阶段同时核对原 checkpoint 的 pending_stage；聚类通过只读事实/override 快照核对冻结判断，摘要复核全部成员和代表评论的当前许可，向量复核固定版本、模型、维数和输入哈希。准备后撤权或人工修订不得新增 AiCall、预算预留或供应商请求。

`with_admission_guard` 只绑定上述请求前复验，原 lease/epoch 检查仍在调用前后生效；响应返途中撤权不提前丢弃原 AiCall 回执，领域提交仍须重新检查材料与修订，禁止旧模型输出覆盖当前人工结果。受控供应商和注入客户端同样经过原 AiService 守门，不能以测试客户端省略最终准入。

cluster、digest、跨故事 judge/review 和 signal relation 在原 Job.scope 冻结完整11能力模型映射及配置hash；每个阶段按实际purpose选模型，免费恢复核对原 AiCall 的owner/job/purpose/provider/model/modelkey/routingversion/hash，不使用虚构的 saved 供应商。业务响应保存后即使后台切换模型，也不重解释历史阶段。原AiService在请求前复核真实operation lease及epoch，并保留running/unknown，未知结果不自动重付。

向量不进入聊天能力映射。`ai/embedding_contract.py` 冻结公开HTTPS endpoint、真实provider主机、model、请求维数、原币种和每百万输入token价格，hash保存在原Job；API key仅在当前服务端配置读取，绝不写入scope。`ai/embedding_services.py` 通过jobs typed helper复验该冻结合同，HTTP adapter不读取数据库。未知价格停在HTTP前；已知价格仅输入计价（无输出token），仍走原全局/ai.embeddings来源网络及费用预算。当前配置变化不能替换原冻结向量任务的身份或计价；凭据轮换且公开合同未变可以继续。已保存向量须有同Job成功AiCall和匹配冻结模型hash才能免费完成。

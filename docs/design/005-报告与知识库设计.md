# 报告与知识库设计

本 Design 是 M4 Epic，遵循 [总设计001](001-热点舆情监控平台总体设计.md)。需求为 [PRD 005](../prd/005-报告与知识库需求.md)，当前排期见 [BACKLOG](../../BACKLOG.md)，后置能力排期时据本文补具体执行步骤。本文中的“已有”仅表示代码或指定运行证据，不代表产品验收。

## 1. 范围与不包含

M4 单独验收情感/摘要/观点质量、日报与周报、Obsidian `HotKey/` 导出、`pg_trgm` 检索与问答。M1 相关性是信息获取准入，M4 抽检其质量；推送送达属于 M5，事件输入仅在 M3 通过后使用。现行需求与排期分别见 [PRD 005](../prd/005-报告与知识库需求.md) 和 [BACKLOG](../../BACKLOG.md)。

## 2. 当前能力与证据分层

`analysis` 标注、`report.daily`、`knowledge.export` 已有代码及受控测试；开发库 738 条标注中 3 条相关字段为空，真实报告生成/连续送达与 vault 安全写入未证实。`report.weekly`、问答和 `pg_trgm` 端到端能力仍待实现或验证。代码/受控、真实运行、产品验收分开记录，推送暂缓不阻止本里程碑报告/知识库独立验收。

## 3. 架构与数据流

`analysis` 对不可变内容版本按主题规则和提示词版本保存标注，`reports` 冻结窗口输入、程序确定性计算数字/引用并可经 `ai` 润色，`knowledge` 将已定稿对象单向导出到 vault。问答从 PostgreSQL 取有权限的内容/报告/事件资料，再经本机 Codex 返回带引用句子。`report.daily`、后续 `report.weekly`、`knowledge.export` 均由调度扫表建 Job；失败不阻断 M1 入库或 M3 事件。

### 3.1 摘要、情感与标注

- `analysis.annotate` 已有代码，设计为一次批量完成相关性、情感、摘要、观点；信息获取验收至少需对命中主题的实际内容证明 Codex 相关性判断及积压可见，质量阈值另按 PRD 抽检。
- **批大小**：≤ 30 条且序列化后 ≤ 24,000 字符；单条正文截取前 1,500 字符；评论按所属帖子分组，每帖最多取 50 条。
- **结果表 `content_annotations`**：唯一键 `(owner_id, content_version_id, topic_id, topic_rule_version, prompt_version)`；字段：相关与否、相关理由、情感、摘要、观点列表、`ai_call_id`。标注绑定不可变的内容版本，正文变了自然产生新版本，需要重新标注。
- 输出用 Pydantic 校验；单条不合法只标该条"未分析"，不影响整批；整批失败按失败码处理。
- 2026-09-26 开发库真实运行的 738 条标注中有 3 条相关字段为空，原因待查。查明前将其单列为“标注异常”，不计入相关或不相关，也不作为已完成相关性判断；[M1 覆盖查询](002-信息获取主链路设计.md#62-来源覆盖与运行查询)须显示异常数量和可追查的内容/调用标识。

### 3.2 报告

#### 3.2.1 生成步骤（问题 #20）

1. **固定候选**：受理时确定主题、窗口（前一自然日 Asia/Shanghai）、截止时间和候选内容版本集合，之后不纳入迟到内容。
2. **等待并锁定清单**：09:00起只等待候选集合的分析水位，最迟09:10将已有有效标注、覆盖和缺口写入最终 `reports.input_manifest` 并锁定。等待结束后重生成复用最终清单、版本递增。若等待和模型生成预计将超出15分钟目标，提前模板降级并记录原因，不把600秒硬截止当SLA。
3. **取数（确定性）**：程序计算概览、平台与情感分布、Top 内容、风险内容、代表评论、覆盖说明，得到结构化数据；每条内容带引用编号 `[c12]`。
4. **撰写（可选）**：Codex 按 schema 返回句子列表，每句必须带引用编号；程序只保留引用编号全部存在的句子，数字一律由程序填写。
5. **降级**：Codex 失败、限流或校验不通过时，用模板把结构化数据渲染成日报，标注"模板版"。
6. **存档**：`reports` 保存 Markdown、结构化数据、生成方式（model / template）和版本；定稿后可供后续推送或导出。日报生成的验收不以渠道送达为前提。

#### 3.2.2 历史 P1 与 P2 的区别

P1 按"重点内容"组织（DEC-001-114），引用优先链接原帖；若相应 `HotKey/` 笔记已经存在才附笔记链接，不预先生成悬空 `[[帖子/…]]`。P2 帖子笔记与事件归并独立验收后，先导出目标笔记再补双链；事件区块来自 `events`，不得因热榜入库而提前展示事件结论。

### 3.3 Obsidian 与问答

#### 3.3.1 写入位置与结构

- vault：`~/Desktop/Markdown/Obsidian`（`HOTKEY_OBSIDIAN_VAULT_PATH`），HotKey 只写 `HotKey/` 子目录（`HOTKEY_OBSIDIAN_ROOT=HotKey`）。

```
HotKey/
├── 日报/2026-09-25 小米SU7-<短ID>.md    P1
├── 周报/2026-W39 小米SU7-<短ID>.md      P3
├── 事件/<事件标题>-<短ID>.md            P2
├── 主题/小米SU7-<短ID>.md               P3
├── 帖子/<平台>/<标题前 40 字>-<短ID>.md  P2（只收被报告或事件引用的）
└── 问答/2026-09-25 <问题前30字>-<短ID>.md P3
```

#### 3.3.2 笔记格式

- **frontmatter**：`hotkey_id`、`type`（daily/weekly/event/topic/post/qa）、`topic`、`date`、`platform`、`sentiment`、`heat`、`source_url`、`generated_at`、`generator`。便于 Obsidian 属性视图和 Dataview 筛选。
- **正文**分两块：`<!-- hotkey:begin -->` 与 `<!-- hotkey:end -->` 之间由 HotKey 管理，每次导出整体替换；标记之外（含预置的"## 我的笔记"）归用户，导出时原样保留。
- **阶段引用**：P1 日报中的帖子只链接原帖，或链接已经存在的笔记。P2 开始创建精选帖子笔记；导出目标成功后才写 `[[帖子/…]]`，事件和主题笔记同理，保证不悬空。

#### 3.3.3 写入规则（NFR-001-109）

- 路径由 HotKey 生成：去掉 `/\:*?"<>|` 和控制字符，限长，追加短 ID 防重名；最终路径必须位于 `HotKey/` 内（解析后校验）。
- 原子写：读取文件哈希与唯一管理标记 → 合并内容并保留未知frontmatter及用户区 → 同目录临时文件 `fsync` → 再校验原文件哈希 → `rename` → 目录 `fsync` → 数据库登记。并发编辑/标记缺失或重复返回冲突；文件已成功但登记失败可按对象哈希恢复，不覆盖用户编辑。
- `knowledge_exports` 表记录 `(owner_id, object_type, object_id)` → 相对路径、内容哈希、导出时间；内容哈希不变则跳过。
- vault 不存在或不可写时 `knowledge.export` 保留失败与重试状态，不影响信息获取或已生成的报告。

#### 3.3.4 问答（P3）

- 入口：Web 页面或 `python -m cli knowledge ask "问题"`。
- 检索：PostgreSQL `pg_trgm`（对内容版本标题/正文、报告、事件摘要建三元组索引），Codex 先把问题改写为 3—5 个检索词，取前 20 条资料。
- 回答：Codex 按 schema 返回句子列表，每句带资料编号；程序去掉无有效编号的句子；有效资料少于 3 条时直接回答"资料不足"。
- 结果存 `knowledge_answers` 表并导出为 `问答/` 笔记，引用链接到对应帖子笔记或原帖。

### 3.4 AIHOT 对照后的精选、写作与编选目标

[PRD005 FR-005-009—011 / AC-005-010—012](../prd/005-报告与知识库需求.md#41-aihot-对照后补齐的分析与编选需求) 的全量承接由PRD046、Design048和Plan062确定。独立editorial双评分、中文写作、持久翻译与SelectBench已接现有analysis/ai/jobs；原analysis.annotate仍只承担主题相关性。精选标准、错例与评测归analysis，调用及预算归ai/jobs，报告编选与冻结版本归reports；真实模型质量、费用和逐来源验收保留未通过。

人工样本与留出分离、relevant/selected 状态、判断/提示词版本、有效/弃权/异常分母、引用输出、预算与质量目标按当前Design048合同核验；页面只读已存结果，不调模型。报告编选只能在现有自然日/ISO 周冻结清单内使用事实和事件修订，迟到处理和重生成不得改写旧清单；AIHOT 的 08:00 日报与周/月刊时间不替换本项目 09:00 合同。

062已接AIHOT公开日周月刊，原主题报告路由统一为`/api/reports`并生成客户端；vault写前再次复核整文件哈希，管理区冲突拒绝覆盖、已写文件/登记中断按期望哈希恢复，受控故障测试通过。原主题日报扫描与采集就绪解耦、主题周报仍留在BACKLOG；真实报告质量与vault核收未验。普通文件系统无法对不配合的编辑器作跨进程原子CAS，复验后rename的极短竞争窗口保留为边界。

## 4. 领域、数据与状态

`content_annotations` 以 `(owner_id, content_version_id, topic_id, topic_rule_version, prompt_version)` 唯一，关联 `ai_call_id`；无效单条为未分析/异常，整批失败保留 Job 原因。后置质量抽检须补评论样本ID、版本、有效情感计数和观点引用，不能将最多50条样本当全部评论。`reports` 保存锁定清单、结构化数据、Markdown、方式与版本；周报固定选中的七个日报版本/清单，后续日报修订不得漂移周报输入。

报告设置唯一事实源为现有 `monitor_topics.report_time`、`report_timezone`、`weekly_report_enabled`，不新增 `report_schedules` 表或第二份可写设置。日报按现有主题及 `report_time` 调度，周报受 `weekly_report_enabled` 控制；二者与采集就绪独立。`current_version` 仅是关键词、来源和采集间隔的不可变采集版本；报告/推送偏好不升该版本。报告偏好在主题行锁内原子更新，同一采集版本的偏好并发更新按最后成功提交生效，不能把 `expected_version` 描述为独立的报告设置冲突检测。报告 operation 按主题、种类和本地日/ISO周唯一，受理时冻结实际设置与采集版本；修改设置或采集规则不为已受理窗口另建 Job，也不改旧 manifest，只影响未受理窗口。不持久化第二份 `next_due_at`。冻结 manifest 属报告/Job 事实，不属于设置。`knowledge_exports` 保留对象到稳定相对路径的映射，改标题不静默移动文件。后置检索新增可重建的 `knowledge_documents` 投影，以(owner,type,id,version)唯一并建pg_trgm GIN索引；后置问答新增 `knowledge_answers`，保存问题、冻结检索清单、逐句引用、状态与错误。资料索引只能来自已授权领域DTO，不扫描私人vault。这些是后续非核心能力的目标设计，尚未生成或验证数据库，不纳入当前核心 POC。

## 5. 接口与页面

主题报告已统一`/api/reports`并同步运行OpenAPI/生成客户端，旧`/api/v1/reports`无别名。报告设置复用主题读写路由及同一组字段，以`current_version`检查采集版本冲突，偏好按行锁提交/CSRF；专用视图也不能建立并行事实源。后置问答目标为POST `/api/knowledge/answers`（202）及GET列表/详情，问题1—2000字符，owner隔离、资料不足、失败和逐句引用可见，CLI复用同一服务。报告页面显示模板/模型版、缺口和固定版本；未实施部分以BACKLOG为准。

## 6. 调度、执行与截止

日报在 Asia/Shanghai 前一自然日窗口冻结；09:00 检查分析水位，至 09:10 等待上限后可生成并标未分析数。`report.weekly` 每周一 09:00 Asia/Shanghai 触发，以上一 ISO 周（上周一 00:00 至本周一 00:00，即上周日 24:00）为冻结窗口，复用日报的分析水位等待，最迟 09:10 开始生成并记录未分析数。`report.daily`/`report.weekly` 均以 600 秒为硬截止，`knowledge.export` 为 60 秒；硬截止是终止上限，不等于 09:15 送达承诺。周报的程序数字须与该周已存档日报按同一口径的合计一致；有差异时保留原因与缺口证据，验收不通过，修正后重验。operation ID 绑定窗口/对象版本，重生成递增版本但使用冻结输入清单；导出按内容哈希跳过。Codex 每 Job 独立子进程并受调用预算约束。

## 7. 失败语义与恢复

补充任务边界：后置索引的 `knowledge.index` 每批100对象、硬截止60秒；后置问答的 `knowledge.answer` 硬截止600秒，结果入库与vault导出分开。索引失败保留游标；回答成功但导出失败仍可读到答案。以上为初始工程保护值，归既有Worker/Job体系；不新增服务。

模型失败、限流或引用校验不通过，报告降级模板版，数字仍由程序计算；无足够资料的问答答“资料不足”。vault 不存在、不可写或同步冲突时 `knowledge.export` 保留失败与重试，不影响已生成报告；仅在 `HotKey/` 管理区块内原子重写，用户笔记区保留。目标帖子笔记未成功导出前报告不得写悬空双链；后续恢复/重试幂等并保留旧版本。

## 8. 安全、风控与可观测

检索按 owner 授权，路径先规范化并确认位于 `HotKey/`，私有 vault 不进模型输入或日志。记录冻结清单、覆盖缺口、有效/异常标注、模型调用量、引用校验、模板降级、导出哈希/失败和实际路径的受控审计；公开日志脱敏。模型不执行外部文本指令，输出只接受结构化字段及有效引用。

## 9. 验收设计要点

先受控验证数字确定性、引用无悬空、模板降级、哈希去重、原子写与用户区保留；再用真实报告、周报和 vault 写入逐项核对情感/摘要质量、覆盖说明、问答引用与恢复。报告生成、笔记导出和推送分别出结论；M1 标注完成不等于 M4 质量验收。

质量抽检按每主题 100 条已验收 M1/M2 的真实入库内容，抽样前冻结随机/分层方法、来源与日期覆盖、内容版本、提示词版本及人工标准答案，不按模型答对与否换样本。相关性评估全部 100 条；情感只评估人工判相关且可判情感的子集，分别保存分子、分母、判定人和误判原因。未生成、空值或 invalid 算错误，人工无法判定的样本另列原因；相关性 ≥90%、情感 ≥80%，少于 100 条不宣称达标。修改提示词或输出 Schema 后升版并重验同一冻结样本；摘要/观点另核对事实、评论引用和样本代表性，真实模型请求继续遵守总需求暂停边界，受控测试不能替代真实质量结论。

## 10. 决策、风险与对照

沿用 DEC-001-202/207/208/211/212/219 与 PRD DEC-001-109/111/112/114。DEC-001-208 替代 pgvector/jieba 检索路线；DEC-001-219 替代“日报先导出帖子笔记”的引用时序。本次不新建 DEC-005-xxx。风险为模型幻觉、三条异常标注、vault 用户编辑冲突与引用错误。对应原总设计 v3.2 §8 摘要/情感、§9、§11，及 §15/16 相关风险决策；历史约束：旧 Design 028 可追溯与可复现（已删除，见 Git 历史）、旧 Design 037 费用与资源约束（已删除，见 Git 历史）。

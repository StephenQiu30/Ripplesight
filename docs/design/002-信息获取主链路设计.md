# 信息获取主链路设计

### 已有内容只读样本预览合同

`POST /api/topics/sample-preview` 承接 FR-002-009/AC-002-010 的持久样本部分，由 content 服务持有只读事务，复用 monitors 规则函数和 evidence 生命周期权限；路由通过既有 ContentService 注入，不跨域导入 ORM。固定最近7天观察窗，每内容取最新可读、含文字的非评论观察，最多20项并显示截断；不预先筛掉未命中或排除项。规则基于已保存的完整标题与正文判断，返回摘录明确标记截断，不用摘录代替规则输入。空窗说明证据不足，输入为未保存草稿，内容版本单独追溯。选择来源只约束本地样本，不证明平台原生查询已生效。

`TopicRulePreview`跨新建/编辑复用，沿用monitors组件、生成客户端及shadcn/Radix Dialog，显示草稿/来源、原因/时间/作品链接；覆盖加载、空、截断、业务错误/重试，输入变化清旧结果。Demo不检查会话。人工预览保留；查询不新增DDL、Job、Outbox、模型/来源请求或预算实耗，不关闭058与新增产品AC。历史 Plan059 的证据见 Acceptance002。

人工标题预览的既有接口只判断本地规则，上游扩词状态仍未核实。Plan001 在同一组件中根据表单的当前 `sourceKeys` 区分提示：未选来源显示“来源尚未选择”，已选来源显示“尚未核实”，不能因接口的固定占位状态误报表单未选来源。扩词查询次数/预算保持接口的未知值，当前不可启用；不新增逐来源查询合同或发起外部请求。来源选择变化沿用既有组件 key 重建预览，不保留旧结果。

本 Design 定义 M1 的现行合同，遵循[总设计001](001-热点舆情监控平台总体设计.md)。需求见 [PRD002](../prd/002-信息获取主链路需求.md)，待执行或验收的任务见 [Plan入口](../plan/README.md)。完成任务原文从 Git 查阅，实际进度与证据分别归 BACKLOG 和 Acceptance002。

POC 当前按 PRD001 §1 的整个核心链路逐项验证，M1 是当前收尾切片。执行分为 [Plan058](../plan/058-M1短窗POC演示与扩围执行计划.md) 的最小闭环 A（一个主题、HN、一榜，配置→采集→持久化→分析状态→阅读/覆盖→失败恢复）和十来源扩围 B；A 通过只证明该固定来源与短窗，不代替 B 或 M1 产品验收。两阶段均在同一隔离库内逐原始 ID 核对，不以单个 Job 代替闭环。日报、周报和知识库不进入本轮排期；共同 72 小时窗口由 Plan009 在后续产品验证阶段执行。关闭真实 Codex 请求期间，分析链路只能证明受控行为与账本口径。

## 1. 范围与不包含

### 2026-09-28 审核修复合同

- 分析输入：分析候选和执行前的正文、评论读取均消费 evidence 的可读性边界；过期、已请求删除或没有证据的观察不进入模型输入。历史指标账本仍独立保留历史候选口径，不能因当前到期而缩小历史分母。Job 冻结评论版本身份，正文截断与评论截断后仍保持身份和样本逐项对应；执行时核对原版本，不用新评论替换旧输入。旧 Job 若带评论却没有可核对身份，停止模型调用并给出配置错误。范围为 `content/{services,schemas}.py`、`analysis/{services,schemas}.py` 和相关测试，不改数据库或公开 HTTP DTO。
- 调度与受理：来源最短间隔继续按 owner/source 共享；调度按最近一次受理时间优先照顾尚未受理或等待更久的主题，限频跳过不获得更高的已服务优先级。手动和定时受理共用来源事务锁，避免不同主题并发绕过来源间隔。范围为 `worker/scheduler.py`、`monitors/runs.py`、`jobs/services.py` 与 `tests/integration/test_topic_runs.py`；到期缺口、预算及 Job/Outbox 原子性保持原合同。
- 阅读关联：主题作品列表及详情的主题关系取可读发现 Job 与可读热榜观察的 `matched_topic_ids` 并集；热榜身份必须绑定相同 owner/content/job，已删除的旧命中不能借后续未命中观察重新显示。范围为 `content/services.py` 与 `tests/integration/test_hotlist_persistence.py`，沿用现有 DTO。

修复先记录真实隔离 PostgreSQL 的失败用例，再运行适用门禁。受控验证不关闭 M1 的真实来源、模型与 72 小时产品验收。

深扫补充：到期恢复必须允许调度游标已越过上一持久到期点，包括主题修改间隔后的新周期；旧到期事实不按新间隔改写，只有当前重放区间内的既有点才验证节奏一致性。范围增加 `jobs/coverage.py`、多轮及改间隔回归。公平性依据最近一次定时受理时间，手动入口仍共享来源限频锁。evidence 领域通过自有可读资源 ID 查询投影提供 SQL 过滤，业务领域不导入其 ORM；历史账本测试显式验证资源过期后原始候选集合不缩小。分析测试补齐真实生命周期记录，并消除候选起点/账本测试的 fixture 收集顺序依赖。

四个关键词来源（HN Algolia、Google News 搜索 RSS、本机 SearXNG 新闻、本机 RSSHub 36Kr 快讯）、HN 评论父链、六个公开热榜、来源覆盖查询及本机 Codex 相关性构成 M1。每个来源、能力、时间窗单独验收。不包含本人账号 B 站、其他登录平台、事件归并、报告、知识库、推送、告警与导出。对应 [PRD 002](../prd/002-信息获取主链路需求.md) 与[完整Issue清单](../plan/README.md)。

## 2. 实现与证据职责

任务进度只维护在 [BACKLOG](../../BACKLOG.md)，分项真实、受控和未通过条件见 [Acceptance002](../acceptance/002-信息获取主链路验收.md)。设计不维护旧运行计数、部署状态或测试快照；配置、代码、单项真实请求与完整产品验收分别判断，不拼接不同库或时段。

## 3. 架构与数据流

`monitors` 设主题规则，`connections` 原子应用来源预设，独立调度进程扫到期表并由 `jobs` 同事务创建 Job/Outbox，Kafka 唤醒单宿主机 Worker。`sources/adapters` 请求来源，`content` 保存来源身份、版本、发现关系、评论父链和热榜快照；`analysis` 经 `ai` 的本机 Codex 标注不可变内容版本。`jobs` 持有覆盖窗口与预算事实。API 只经所属服务聚合 DTO；浏览查询不请求源站。事务、重投与跨领域依赖沿用[总设计 §3—5](001-热点舆情监控平台总体设计.md)。

Plan 031 的手动入口由 `monitors/runs.py` 在 owner 范围内冻结主题与连接版本，逐来源检查准入、静默和预算，并在同一事务写 Job/Outbox；重复 operation ID 返回原受理结果。`worker/scheduler.py` 领取到期行并在同一事务写到期事实、Job/Outbox 和下次到期点。页面专属 `topic-run-actions.tsx` 消费运行时 OpenAPI 生成客户端，展示受理和跳过原因。

### 3.1 来源预设与连接

`python -m cli sources preset apply hackernews` 应原子应用连接、策略和预算；应用预设只说明配置就绪，来源须经真实采集与持久化验收才标记可用。

- **预设定义**在 `connections/presets.py`：来源键、能力、主机白名单、字段用途、保留天数、组件版本/许可、执行策略与预算。`SourcePresetService.apply_in_transaction` 将连接版本、准入、保留、组件与预算放在同一事务；重复同一配置幂等，改变配置升连接版本。`config JSONB` 仅存白名单许可的非机密端点字段，`source_connection_versions.execution_policy JSONB` 保存严格验证的非秘密执行策略快照；普通连接可以没有预设策略。该新增列只进入全新空库 Schema，保留库先走 051 恢复路径。
- **关键词来源实际入口**：`hackernews` 为 Algolia 公开 API；`google_news` 为 Google News 搜索 RSS；`news_search` 为本机 SearXNG 的 `duckduckgo news` 引擎，宿主机 Worker 访问 `127.0.0.1:8888`，Compose Worker 访问 `host.docker.internal:8888`；`rss_36kr` 为本机 RSSHub `/36kr/newsflashes`，宿主机 Worker 访问 `127.0.0.1:1200`，Compose Worker 访问 `host.docker.internal:1200`，按主题过滤快讯，不走 36Kr 原站 feed。`web` 仍专指单网页正文采集。
- **HN 身份与原帖**：搜索条目的 `objectID` 保持为来源不透明字符串，持久身份与重放按原值核对；原帖使用稳定 HN item 链接，不把外部文章 URL 当作 HN 讨论身份。
- **Google News 身份**：只允许固定 HTTPS `news.google.com/rss/search` 查询模板及该主机；RSS 请求不跟随重定向，以免跳到未经冻结的查询。条目优先保留原生 GUID，缺 GUID 时以规范 URL 加 `url:` 前缀回退，`content_records.identity_basis` 保存 `guid`/`url_fallback` 并随现有内容读取 DTO 返回。导入旧数据后同身份首次再观察可补齐原先可空的依据，已存在的不同依据不得覆盖。新列只进入全新空库 Schema；保留库先走 051 恢复路径。Feed 快照不提供可信历史尾页证明。
- **SearXNG 新闻身份与失败**：`news_search` 仅请求本机 `http://<固定主机>:8888/search` JSON 和 `duckduckgo news`；`HOTKEY_SEARXNG_HOST` 仅选择 `127.0.0.1/host.docker.internal`，白名单必须仅含该主机，不允许改端口、基路径、凭据或 query，不跟随重定向、不自动抓结果正文。结果无原生 ID 时，以规范 URL 的 SHA-256 生成 `url:` 身份，`identity_basis=url_fallback`；仅去除明确列出的 `utm_source`、`utm_medium`、`utm_campaign`、`utm_term`、`utm_content`、`gclid`、`fbclid`，保留有语义 query。实际引擎、页号、失联引擎与错误写入 Job 检查点；HTTP 200 但引擎失联/报错不能记合法空，已有条目按部分页保留。重复页、页大小溢出、请求/页上限和无可信尾段都保留部分覆盖，摘要版本标 `truncated`。
- **节奏契约（DEC-001-213）**：版本化 `SourceExecutionPolicy` 包含最短间隔、带时区起止的静默窗口、每轮词数、每词条数和请求上限、Job `max_seconds`、进程 `hard_timeout_seconds`、最大并发及开关；静默窗口支持跨午夜。B 站预设为 6 小时、Asia/Shanghai 00:00—08:00、3 词、每词 5 条/26 次请求、220 秒 Job、240 秒进程与并发 1。四关键词来源沿用现有 100 条、3 请求、90 秒策略及原日预算；六榜分别保存默认 1800 秒间隔。策略持久化与调度消费合同已合入；调度先检查开关和静默，再取 `max(主题频率, 来源最短间隔)`，词数、条数、请求数与时间上限取保守值。M1 验收窗口按 §3.5 冻结。
- **版本语义**：策略随连接版本保存，可按 owner、连接 ID、指定版本读取；Job 输入保留受理时的连接版本。安全停用状态仍从当前连接行检查，预设重应用不能解除停用。来源日预算以 owner、source、metric、窗口规则对应的稳定 policy 行和窗口累计，变更连接版本或非秘密策略不建立新额度；同一来源/指标/窗口规则的替代预算键被拒绝。调度消费及旧 Job 执行裁决已有受控实现，重试周期沿 Plan032；真实调度、重试与保留库适配分别按 058/032/009 验收，策略快照不能充当真实运行证据。

安全规则：

- 适配器构造时接收**主机白名单**（来自预设），请求 URL 与每一跳重定向的主机都必须在白名单内，否则 `access_denied`；禁止私网地址（复用 `sources/adapters/web_targets.py` 已有规则）。
- 本地服务（SearXNG 固定 8888 端口、RSSHub 固定 1200 端口）以显式条目加入对应预设白名单，由同级 `Docker` 的独立 Compose 项目管理。Compose Worker 预设主机固定 `host.docker.internal`，宿主机 Worker 固定 `127.0.0.1`；分别通过 `HOTKEY_SEARXNG_HOST/HOTKEY_RSSHUB_HOST` 选择，只允许这两个明确主机及既定路由，配置值冻结到连接版本，不把容器自身回环地址当宿主机；Firecrawl 独立编排。MediaCrawler 的 HotKey 入口固定为宿主机子进程，不以它的容器构建或 CLI 帮助通过代替平台采集。

### 3.3 时间口径

- 契约允许 `published_at=None`。关键词发现提交时：有发布时间的按发布时间判断是否落在任务窗口；没有发布时间的可作为发现时观察纳入，记录 `content_discoveries.first_observed_at`，不得伪造发布时间。
- 报告与统计的时间依据 = `COALESCE(发布时间, 首次发现时间)`，并对"按发现时间计"的条数单独计数、写入覆盖说明。
- **三种频率分开**：主题/来源的调度频率决定何时尝试；`HOTKEY_COLLECTION_LOOKBACK_SECONDS` 默认 86,400 秒、最多 7 天，决定当前任务向前查询的窗口；来源自身发布、缓存或榜单更新时间由来源控制。代码用上一窗口终点或首轮间隔起点叠加回看，按身份去重；重复扫描和 24 小时回看不能证明源站历史完整、分页尾段已见或中断缺口已补。无可信终止证据的 `COMPLETE/EMPTY` 仍为部分覆盖。

### 3.4 评论采集

本轮 HN POC 复用 Algolia 整树读取、局部缓存切页和既有有界重扫，不新增逐根远程分页框架。先验证父链、旧帖新回复、采样上限、预算与重放；逐根来源分页和真实十帖留给后续产品核对。整树或缓存页结束不构成固定时间窗尾段证明：提交只消费来源提供的 `terminal_evidence`，未提供或范围/排序/标志不匹配时为 `partial/unverified_terminal`；根或回复上限实际丢弃了样本时为 `partial/budget_exhausted`。跨页保留截断标记，重复身份去重不算采样截断；只读评论页尾与来源覆盖分别判断。

- `source.comments` 执行器已有代码：锁租约、校验连接版本和准入、逐条入库、记录游标与计量；真实来源的页尾和父链仍分别验收。
- 评论 ID 保留来源原生不透明字符串；`content_threads` 分别记录作品、线程根、直接父节点、回复目标的同 owner 身份，以及 `parent_relation_status`：顶层为 `root`，来源已观察父节点为 `observed`，树中仅见无正文/不可访问父节点为 `unavailable`，无法判定为 `unresolved`。根或回复目标未知时保持空值；已知但缺失的父节点创建身份占位，不根据正文或提及用户名猜测父链。HN 树提供根和直接父节点，适配器须校验显式 `parent_id` 与树结构一致；每根评论的回复分页与停止原因分别计量。新列只适用按唯一完整 Schema 建立的新库，存量数据保留与重建由 Plan051 承接。
- Plan041 的只读 `GET /api/contents/{content_id}/comments` 只接受 owner 可读的帖子，不触发来源或 Job。无 `root_id/parent_id` 时按线程根分页；指定 `root_id` 时按该根分页列出各层回复，指定 `parent_id` 时按直接父节点分页，两者不能同时指定。游标绑定当前帖子与查询分支，根或父节点不属于本帖时返回不可访问；分页按关系首次持久时间与身份稳定排序，默认20、最大100。无正文但有可读后代的根保留占位，回复携带独立根/直接父/回复目标及父节点状态；只有仍可读的观察才返回正文，未取完的来源尾段不能凭本地页尾宣称完整。
- Plan041 的只读 `GET /api/contents/{content_id}/comment-run-readiness` 按 owner 可读帖子核对活跃主题、已应用评论预设、来源准入、执行策略、预算和同帖间隔，返回 `supported/available/reason`；不创建 Job。`comments_not_ready` 隐藏“更新评论”，预算不足或频次限制保留禁用操作并说明原因。按钮使用一次点击的 UUID operation ID，请求处理中禁用，网络失败后以同一 ID 重试，受理后进入 Job；POST 始终在事务中重新核对，GET 状态不构成受理承诺。
- Plan041 的作品详情还按 owner 与仍可读观察投影主题及标注：主题名称/当前规则版本由 `monitors` 只读契约提供，标注由 `analysis` 只读契约提供。仅返回仍有可读观察的内容版本对应的标注，保留标注自身的主题规则版本、提示词版本与结果状态。页面选择主题和内容版本时，只有同时匹配当前内容版本、当前主题规则版本与当前提示词版本的 `valid` 行才能显示为当前相关/不相关结论；`pending/failed/invalid` 分开显示，无行显示“暂无标注记录”，旧规则/提示词/正文的结论只列历史，不提升为当前结论。详情读取不受理分析 Job，也不发送模型请求。页面专属 `annotation-panel.tsx` 使用详情生成 DTO，覆盖主题/版本切换、空记录、异常与历史状态。
- 评论上限按来源预设或能力设置。HN 可按候选策略采评论与楼中楼；本人账号 B 站试点当前只取同轮搜索缓存的**一级评论每帖最多 20 条**，不宣称楼中楼覆盖，不为评论 Job 再发平台请求。微博暂不接入。
- HN 评论工程参数保存在来源连接版本的 `config.comment_scan`：默认自动候选期 86400 秒、刷新 21600 秒、每主题 20 帖、每 Job 10 页/10 请求/90 秒、200 根及每根 20 回复。调度以已应用连接版本读取并冻结参数，评论 operation ID 绑定内容、来源连接版本和时间桶；更改参数需重应用预设并只影响新 Job。HN 连接必须匹配当前完整预设（包括 `comment_scan`）才可供新任务使用；缺字段或配置不匹配时需显式重新应用预设并产生新版本，旧 Job 仍使用已冻结 scope。存量库重建按 Design001 §6.3。旧帖超过自动候选期只经 `POST /api/contents/{content_id}/comment-runs` 显式复采：内容必须对 owner 可读、有主题发现记录并仍命中活跃主题规则，当前来源有评论能力、准入与预算；请求按内容行串行检查六小时内同帖评论 Job，并冻结主题和连接版本。重复 operation ID 复用原 Job。该 API 的受控 HTTP/数据库证据见 EV-002-025；手动 Job 执行和模拟 HN 旧根新增回复的受控数据库证据见 EV-002-026。真实旧帖新回复和父链分页仍未验收。

| `hotlist_zhihu` | `/zhihu/hot` | 同上 |

| `hotlist_thepaper` | `/thepaper/featured` | 同上 |

- 已有 `SourceCapability.HOTLIST`、能力 CHECK、`source.hotlist`、`RsshubHotlistAdapter`、`hotlist_snapshots` 与 `hotlist_entries`。调度按 `hotlist_interval_seconds` 创建来源级 Job，默认 1800 秒且可配置。M1 共同 72 小时窗口开始时须记录实际生效的间隔、配置版本及各榜到期相位并冻结；逐榜按该间隔与相位统计 `[T0,T1)` 内实际应到期的桶数，达标数取 `ceil(0.9 × 桶数)`。窗口内配置变化则窗口作废，从新 T0 重开，不拼接不同间隔的桶；仅1800秒且T0与到期点对齐时每榜为144桶、至少130桶。适配器仅访本机 RSSHub，最多取前 100 条；一次成功响应按实际顺序保留排名、标题、链接、可选摘要/热度/发布时间。快照记录 `observed_at`、来源和 Job；条目记录排名、命中主题、可选内容 ID。与**同来源前一快照**按 URL 比较得 `new/up/down/same`，不把热度或发布时间当排名。
- 主题规则复用 `evaluate_monitor_rules`：对标题与摘要作任一/全部/排除匹配；中文可子串匹配，英文/ASCII 词须在字母数字边界形成整词，避免 `AI` 命中 `daily`。命中条目经来源准入后按 URL 身份入库、建立发现关系，再进入 Codex 相关性队列；未命中条目只保留榜单快照。榜单时间以本次 `observed_at` 表示观察，不把来源未给出的发布时间伪造为观察时间。
- `GET /hotlists/sources` 查询已应用来源与最近快照时间；`GET /hotlists/{source_key}` 分页返回最新快照、原到期时刻、operation ID、条目、命中与排名变化。读取不访问 RSSHub。合法 Feed 解析成功但无条目时，单次已计量请求与零条目快照同事务提交，`observed_at` 仍取实际观察时刻；空榜不证明来源覆盖完整。解析、网络、准入或预算失败不建成功快照，保留原到期事实与 Job/尝试失败；后续桶的成功不能覆盖原桶。快照的 `(owner, source, operation)` 唯一，`(owner, job, source, operation)` 外键指向 033 的原到期事实，重复消费只复用原快照；到期、Job、快照分别保存计划、执行与观察时间。
- 快照、条目和页检查点同事务提交，写入中途异常不留半快照；同桶人工重试仍关联原 operation，迟到的跨桶结果保留实际观察时刻，不回填伪造旧桶观察。
- 开发库真实运行在 15:00 的 `hotlist_36kr` 时间桶出现一次 `hotlist_upstream_error`，最近 2 小时统计为 23 成功、1 失败，下一时间桶恢复。该失败桶保留上游错误和覆盖缺口；若重试，只能关联原时间桶的 operation ID，不以后一时间桶的成功覆盖前一桶或把跨桶数据伪记为原桶结果。
- **独立 AC**：六条路由逐一真实采到带观察时间的快照，复扫不重建同一 Job，排名变化与空榜/失败可辨；命中主题的条目落入内容库并获得 Codex 相关性标注，不命中者不进入内容库。事件归并与事件热度属于后续能力，不作为本 AC 条件；RSS 可解析或快照存在本身不能代替入库与分析证据。

### 3.6 运行时前置条件

Codex app-server 初始化必须声明 `experimentalApi`，以支持当前 `thread/start.environments`；`AiService` 与管理命令使用同一个 `codex.app-server` 组件键。当前 Demo 的 `jobs budget-baseline` 经 `db/demo.py` 解析唯一业务历史分区，单次事务设置该分区的请求/分析上限及 Codex 组件策略，不要求账户初始化、不输出凭据；多个分区明确拒绝。保留 `--owner-id` 的运维命令仅以其断言内部分区，不绕过解析。账户功能后置，合同见 Design001 §9.2。独立调度进程先导入完整 ORM 注册表再配置映射。`HOTKEY_COLLECTION_LOOKBACK_SECONDS` 默认24小时、最多七天；回看不能证明分页尾段或完整覆盖。36Kr关键词入口固定本机RSSHub `/36kr/newsflashes`，异常保留失败状态。预算与来源证据不因去登录而自动通过。

分析扫描不以采集时间的 72 小时回看截断旧积压；候选必须是该 owner 已观察的帖子版本，且满足当前主题版本选中的关键词来源，或该版本对应的热榜观察条目曾明确记录该主题 ID 命中。热榜仅同一内容 ID 的历史命中不能使之后未命中的正文版本入队；其他主题的热榜命中也不能使本主题入队。候选仍按当前主题规则复核正文。已受理 Job 的正文版本、实际评论文本和截断标记冻结在 scope，重放不重读最新回复。无效结果仅补偿一次，连续无效记可查询失败，预算不足依账本的下一窗口延后。分析默认关闭，须显式启用 `HOTKEY_AI_ENABLED`；进程限定本机 Codex app-server、ChatGPT 登录、内建 OpenAI 提供方、空工作目录、关闭工具和 600 秒 Job 截止。账户层面仍可能在套餐额度耗尽后动用 credits，真实模型运行前须由账户费用控制确认不会触发付费结算，受控代码测试不代替此核查。

分析每批最多30条，序列化不超过24000字符，每项正文最多1500字符，每帖最多50条实际评论；评论样本及截断标记随输入冻结，不把样本上限当作来源评论完整证明。

## 4. 领域、任务与数据状态

`keyword.search`、`source.comments`、`source.hotlist`、`analysis.annotate` 为本里程碑任务；通用 `webpage.collect` 是已有基础能力，不能替代逐来源验收。`monitor_schedules` 唯一键 `(owner_id, topic_id, source_key, capability)`；Job/`job_attempts`、`coverage_windows`/页检查点和 `resource_budget_*` 记录执行与预算；帖子保留来源原生 ID、RSS 身份依据、作者 ID 与昵称，`content_discoveries.first_observed_at` 与可空 `published_at` 分开；`content_threads` 保留稳定身份与父链；`hotlist_snapshots`、`hotlist_entries` 保存观察时间、排名与命中；`content_annotations` 按内容版本、主题规则和提示词版本唯一。

覆盖 `COMPLETE/EMPTY/PARTIAL/STOPPED` 必须附可信页尾或缺口说明；空榜成功与网络/解析失败分开，后一个时间桶不能补写前一桶。标注区分 `pending/failed/invalid/valid`；只有完整布尔 `relevant` 与理由的有效结论计为已判断，待处理或调用失败的空值不能被填成相关/不相关，也不能仅凭空值断言存储损坏。同一内容/主题规则/提示词版本的 invalid 可恢复为 valid，保留先前稳定错误码、`ai_call_id` 与版本诊断；旧失败不能覆盖 valid，旧版本结果不能写入新版本。状态与字段由唯一 DDL `backend/database/schema.sql` 落地；新增事实表须先按数据库重建门槛设计。

## 5. 接口与页面

热榜历史读取固定 `snapshot_id` 分页，新快照到来不改变已选快照的分页内容；排名比较同来源前一成功快照，合法空快照参与序列，失败时间桶只保留缺口、不生成榜单。`rank_delta = 前榜排名 - 本榜排名`，正值为 `up`、负值为 `down`、零为 `same`；前榜无此条目为 `new`。读取历史不访问来源，仍按数据分区和生命周期判断可读性。

原帖链接仅允许 http/https，正文和评论以安全文本或受限渲染展示，不执行外部 HTML。内容、评论、标注与资格读取不新增 Job/Outbox、来源或模型请求及预算实耗；显式“更新评论”仍按 §3.4 重新核对准入、间隔和预算。

作品列表 `GET /api/contents` 按当前 owner 的仍可读观察取最新正文，支持 `source_key`、`topic_id`、`starts_at`/`ends_at` 和 `analysis_state`。主题筛选只匹配仍可读观察关联的发现 Job 在创建时固定的 `topic:<id>`，不按主题现行来源选择重释历史；无权限主题返回不可访问。时间窗必须成对传入带时区时间，使用 `[starts_at, ends_at)` 且最多 31 天，统计时间取最新可读观察的发布时间，缺失时取该作品仍可读发现的首次发现时间，响应同时标明时间依据。`analysis_state` 仅在指定主题时可用，按最新可读正文版本、当前主题规则版本与当前提示词版本取 `missing/pending/failed/invalid/valid`；旧版本结果不计入当前状态，`valid` 的相关与不相关另由 `analysis_relevant` 区分。列表按作品 ID 稳定排序，游标绑定 owner 与全部筛选值，筛选变化须重置游标。页面专属 `content-list.tsx` 及其筛选控件从生成客户端读来源目录、主题和列表；覆盖加载、空列表、错误、无权限、分页及窄屏状态，不发起采集或分析。

现有 `GET /hotlists/sources`、`GET /hotlists/{source_key}` 返回应用来源、最新快照与分页条目，读取不得访问 RSSHub。快照历史与指定快照、内容/评论/标注和来源缺口按现行读取合同展示。覆盖查询为 `GET /api/collection-coverage`、`/{window_id}`，静态 `/metrics` 优先注册，同一服务供 CLI 复用；正式统计剩余责任见009。查询按owner、source、capability和[start,end)筛选，单次最多31天、默认20/最多100条并使用游标；同一只读事务从各领域DTO聚合，不在路由联表SQL。来源覆盖工作台展示正常、空、加载、错误、部分和无权限状态，不把空列表当完整覆盖。所有接口复用现行ErrorView和生成客户端，真实阅读/覆盖短窗验证归058。

## 6. 调度、执行与截止

### 6.1 主题与调度

`monitors` 的主题选择来源和采集频率；默认 30 分钟、最短 10 分钟只是主题请求频率，实际运行需与 [Design 002 §3.1](002-信息获取主链路设计.md#31-来源预设与连接) 的来源节奏合成。报告时间、周报与推送目标属于各自后续结果配置，不定义信息获取“就绪”。主题具备已应用来源、有效规则和预算可用，仍只算配置就绪；真实连接与采集状态由来源能力证据决定。

Plan 001 将 `monitor_topic_versions` 扩为采集配置快照：关键词三组、按键排序去重的 `source_keys`、`collection_interval_seconds` 随版本保存；规则、来源或主题间隔变化才升版，名称及报告/推送偏好变化不升版。旧 Job 的主题版本与连接版本不变，克隆产生新主题版本 1，归档保留旧版本。创建/更新来源选择须符合当前已应用搜索预设、准入策略和启用的执行策略；恢复另核对当前来源网络预算可用，重复恢复幂等。配置就绪不等于来源持久读取证据，页面分别展示。唯一 DDL 仍为 `backend/database/schema.sql`，仅在新空库应用；存量库按恢复流程处理。

主题创建入口按请求等待`connection()`并注入本次CSP nonce；`TopicForm`只用生成API读取来源能力，无会话请求。生产HTML不共享缓存；runtime核对脚本/CSP nonce匹配且跨请求不复用，浏览器直接冷进入可操作表单。只读样本预览不产生来源/模型调用、Job或预算实耗。

新增主题的首个有效来源周期保留原 PRD 的真实帖子目标：至少一个已准入关键词来源须有可打开原帖的入库结果；若真实来源为空或失败，记录窗口状态与缺口，该验收项不通过，不以模拟帖子补足。

- 入口 `python -m worker.scheduler`，与 Worker 分开运行（Kafka 消费是同步逐条执行的，不能把调度塞进消费循环）。
- 每 30 秒一轮，独立事务领取到期行并用 `JobService.accept_in_transaction` 建 Job、推进 `next_run_at`；行锁、B 站来源级 advisory lock 与确定性 operation ID 阻止重复受理。预设节奏通用化后仍须保持同样的并发证明。
- `monitor_schedules` 以 `(owner_id, topic_id, source_key, capability)` 唯一，保存间隔、下次到期、开关及最近 Job。Job 固定来源连接版本和 `scheduled`/`manual` 入口，事后不按当前主题设置重释旧结果。

### 6.2 来源覆盖与运行查询

- 以**来源 × 能力 × 时间窗**为主键展示到期计划、实际请求与页数、起止及最后成功时间、`COMPLETE/EMPTY/PARTIAL/STOPPED`、停止/失败原因、已入库数与按来源身份去重数、分析待处理/失败/**标注异常**数、预算上限/预留/实际使用和未确认缺口。查询还显示当前连接版本、Job/尝试 ID 与来源是否暂停，允许从时间窗追到快照或内容；不以空结果覆盖缺口。
- 请求、usage attempt 与预算预留未对账时保留 `request_budget_unreconciled` 缺口；网络成功但解析失败不算最近成功观察。不用多表关联乘法放大请求、内容或标注计数。
- 事实分别来自 `monitor_schedules`、Job/`job_attempts`、`coverage_windows`/页检查点、内容发现与版本、`content_annotations`、`resource_budget_*`、热榜快照。API 由所属服务组合只读 DTO，不在路由拼 SQL；Web 来源详情或任务详情按时间窗展示，CLI/受控查询提供同一口径。统一来源能力时间窗查询与页面的技术证据见 Acceptance002；真实逐来源对账、共同窗口与产品验收缺口继续由004/006/009及058核对。
- 覆盖状态只有收到该适配器针对固定时间窗的可信尾段证据才能确认；回看、`COMPLETE/EMPTY`、RSS 头部或固定数量截断不构成完整覆盖。请求失败保留既有内容和缺口；分析积压单列，避免把“已入库”误读成“已判断相关”。
- **验收**：对成功、有结果但页数/预算截断、空榜、限流、登录失效和中途失败各造受控场景，再以真实来源窗口抽查请求、页数、入库/去重、分析积压和预算与数据库一致；展示能定位缺口起止和停止原因。三日连续运行是产品验收证据，受控查询只验证口径。

### 6.3 截止与重试

关键词/评论默认进程硬截止 90 秒，热榜 60 秒、请求预算 45 秒，分析 600 秒；来源预算更保守时优先。`jobs.started_at` 是首次领取，`job_attempts.started_at` 是本次尝试，`collection_cycle_started_at` 是采集预算起点；自动重试沿用周期剩余时间与请求次数，人工重试经权限和来源/全局预算核验后在下一次领取开新周期，但不返还来源日预算。Job 累计请求数持续增长，单周期请求数控制每轮上限；旧代码可能让迟到的人工重试立即耗尽，改动和失败测试见总设计 DEC-001-217。

## 7. 失败语义与恢复

分页截断、未确认尾段、429、访问拒绝、RSSHub 空榜及网络/解析错误分别保留状态、时间桶和原因；已有内容不因后续失败删除。重放按来源稳定 ID、operation ID 和唯一约束幂等；消费位点仅在业务事务成功后连续提交。预设关闭阻止新受理，运行中的 Job 依取消与进程硬截止回收。来源状态只在持久化真实采集证据通过后转可用。

## 8. 安全、风控与可观测

适配器接收主机白名单、校验每一跳重定向，禁止非准入目标和越预算访问；本机 RSSHub/SearXNG 以显式条目配置。日志只保留请求 ID、路由模板、状态、耗时与脱敏错误。按来源/能力/时间窗暴露到期、请求/页、停止原因、预算、入库/去重、标注异常与未确认缺口；不得把回看或 HTTP 200 推断为完整性。

## 9. 验收设计要点

先以受控测试覆盖空榜/失败桶、父链、缺口、预算与人工/自动重试；再逐一核对四个真实入口、六榜排名与命中入库、Codex 标注、来源状态和数据库事实。产品验收要求同窗连续 72 小时，HN 评论分页、旧帖新回复及重放单独核对；真实运行和产品结论写入 M1 Acceptance，不复用旧开发库计数作三日证据。

## 11. 风险与总设计对照

### AIHOT 对照新增需求的设计边界

[PRD002 §4.1](../prd/002-信息获取主链路需求.md#41-aihot-对照后补齐的阅读与素材需求) 的 FR-002-012—014 是后续目标。内容读取、检索、正文质量和时间说明仍归 `content`；来源展示/再分发条件由 `connections`/`evidence` 提供本领域依据，Router 不直接读取来源 ORM。检索只访问已有可读内容版本，不启动采集、分析或正文补齐；沿用现有分区、证据可读性、游标和 OpenAPI 生成客户端。

Plan062 的文本搜索切片在现有 `GET /api/contents`（`listContentRecords`）新增可选 `q`，由 `content/services.py` 的 `ContentService.list_contents` 持有只读事务，API 路由只声明与传递参数。原始输入最多 200 个字符，按 Unicode 空白分词、小写、去重；最多 6 个非空词，超过上限或含 NUL 返回 422 `invalid_content_filter`，不静默截掉条件。空字符串/纯空白等价于不搜索。全部词项以 AND 匹配同一作品当前选中的最新可读观察对应 `content_versions.title/body`；每个词可在任一字段字面子串匹配，`%`、`_`、反斜线不成为通配符。不搜索当前可读投影未选中的历史版本、不可读正文或无正文版本的仅指标观察，不以语义相似代替文本命中。

数据库搜索只读取本批已投影为可读的内容版本，使用 PostgreSQL `lower`/参数化 `LIKE`，不新建持久检索表、第二份内容事实或读取时正文补抓。现有分区、来源、主题、发布时间/首次发现时间、当前标注状态和稳定 UUID 游标分页同时生效；游标指纹绑定规范化词项及原有筛选，改变词项后不得复用旧游标，语义相同的大小写/空白/词序变化可复用。响应沿用 `ContentRecordSummaryView` 的正文版本/出处与时间依据，不改 Schema、DDL、状态账本或任务创建；前端由同一运行 OpenAPI 生成客户端接入。新参数的 OpenAPI 最大长度、错误与实际服务边界须核对。

真实隔离 PostgreSQL 用例分别验证跨字段 AND、中文/大小写、通配符字面、最新可读版本、过期/删除、内部数据分区、既有筛选与游标、无 Job/Outbox/调用/预算写入；不访问业务库。公开网页正文采集与新闻/RSS 摘要读取仍是不同路径，不自动补抓所有发现链接。命中片段、全文许可投影与公开分发不在本片，按所属后续合同实施；文本搜索本身不能关闭完整 FR-002-012/013 或真实产品 AC。

### 现行执行合同

- 来源预设固定 `SourceExecutionPolicy` 版本字段；相同预设幂等、变更升连接版本。Job在受理时固定配置，执行时仍检查当前安全停用状态；日预算身份不含连接版本，换版不能重置日额度。调度与手动受理由现有业务服务承接，人工重试专项见032，当前短窗及正式验证分别归058/009。
- 到期账本保存 `collection_due_windows`，唯一(owner_id,schedule_key,due_at)，到期点与 `[window_start,window_end)` 分开固定；持久化 pending/accepted/skipped/missed 与原因、非秘密 `SourceExecutionPolicy` 快照、连接版本和可空 Job 关联。Job 只在同一受理事务实际创建后关联；恢复逐到期点使用当时版本，最近到期点保留待受理，较早未受理点记 missed。既有 Job 请求数、`coverage_windows` 页数、内容观察、attempt 与预算账本各自拥有事实；原始页观察数随检查点同事务保存，不新建第二套计量账本。没有Job或缺少实耗证据的指标为未知 null，有事实证实无请求/页/实耗时才为真实 0。
- 采集周期编号/开始时间与attempt分开。自动重试沿用周期剩余额度；人工重试在领取时开新周期，来源日额度不返还。页面提交、内容持久化与检查点在同一事务中，重放不重复统计。
- 时效统计以due_at进入[start,end)确定时效分母；未终态窗口保留未完成/超时及延迟下界，不从中位数样本静默消失。热榜按预期相位枚举的缺失到期桶也进入延迟分母并记为未完成；相位尚未在窗口起点冻结核实时，延迟结论保持不可判定，不能凭当前配置宣称达标或不达标。无法确定中位数时返回null与下界，不判通过。分析按内容版本/主题/规则/提示词身份计数，60分钟成熟窗外单列pending_observation，72小时结束后继续等最后一批成熟。`content_annotations.first_valid_at` 在首次有效结论写入时固定；后续重复、失败或无效诊断不能改写。只有有效结论允许该字段非空；直接写入有效行也必须提供时间。它与可变的 `updated_at` 分开，单独提供首次结论事实，不代替逐主题需分析起点或 Codex 限流影响证据；缺后两者时统计仍为不可计算。新增列只进入全新空库 Schema，存量保留库按 Design001 §6.3 恢复核对。
- 统计事实为逐主题需分析起点保留 `monitor_topic_status_events`：主题创建/克隆记初始 paused，真正恢复、暂停、归档及移除全部来源引发的自动暂停分别与主题状态同事务写一条状态事件。事件含 owner、主题、每主题递增序号、规则版本、状态、原因和 UTC 时刻；序号在主题行锁内生成，等时刻事件仍可确定顺序。重复请求不追加事件；名称/报告偏好改动不追加状态事件。规则版本继续由不可变的 `monitor_topic_versions.created_at` 表示，不把 `monitor_topics.updated_at` 当作历史激活时间。旧主题或直接 SQL 写入缺状态事件时不得推断连续启用，也不得将分析比率判为达标。事件只进入全新空库 Schema；存量保留库的恢复与核对按 Design001 §6.3。
- 统计事实为提示词版本保留全局 `analysis_prompt_activations`：仅启用 `HOTKEY_AI_ENABLED` 的调度进程在首次扫描前，以调度进程启动时的 UTC 时刻写当前 `ANALYSIS_PROMPT_VERSION`；同版本重启不覆盖首次时刻，新版本另存。分析关闭时不写入，旧运行记录不从 Job/标注倒推。该时间证明提示词进入可调度配置，不证明 Codex 服务可用或未限流；缺失时分析时效不可计算，实际限流影响仍以调用/窗口证据单独核对。表只进入全新空库 Schema，存量库按 Design001 §6.3 恢复核对。
- 统计事实另存全局 `analysis_prompt_runtime_sessions`，每次调度进程启动生成独立 UUID，记录当前提示词版本、`HOTKEY_AI_ENABLED`、启动时刻、最后成功写入时刻与可空的正常退出时刻。启动事实与首次启用事实同一事务写入；每轮扫描结束后单独提交心跳，无法记录心跳时调度进程停止；正常退出尝试关闭该会话。相同运行 UUID/配置重试不重复建会话，冲突配置拒绝。该事实只证明进程已观察到的静态配置区间：异常退出后最后心跳至下次启动的空档未知，并发运行且启用状态冲突的区间未知；关闭态运行不写首次启用事实。会话不证明 Codex 服务可用或未限流，也不从旧 Job、标注或进程日志倒填。仅在全新空库 Schema 建表，存量库按 Design001 §6.3 保留与核对；在会话区间、历史提示词与限流事实全部能复算前，候选账本和分析时效仍不可宣称达标。
- 只读候选起点按精确内容版本与主题 ID 读取首次接收时间：已选来源使用该版本观察，热榜使用同 Job、同版本、同主题命中观察；再与不可变规则版本有效窗、已验证的主题 active 区间和当前提示词首次启用时间取交集。旧帖先入库后恢复主题、暂停期间换规则等场景以交集首时刻为候选，不复用全局内容创建时间；缺主题初始/完整事件或提示词启用事实返回未知。历史提示词停用区间和 Codex 实际可用/限流尚未持久化，因此该候选不直接进入 60 分钟分析分母，现有汇总仍不可计算。
- 只读候选账本按 owner 枚举观察窗结束前已有观察的帖子版本、全部历史主题规则版本和当前提示词版本，复用上述起点投影并导出原始身份、首次有效结论、60 分钟成熟/未成熟计数；未入分析队列的匹配版本仍可进入候选。缺状态历史或提示词启用事实时列为 unknown，不能计入确定分母。旧提示词版本、提示词停用区间和 Codex 实际限流影响尚未核实，账本不输出达标率，`analysis_status` 保持 `not_computable`。
- `analysis-candidate-v2` 将运行会话与当前提示词逐身份起点相交。会话只覆盖 `[started_at,last_seen_at)`，不把最后心跳后的时间或两个进程之间的空档推断为已启用；无后续心跳的启动行不给出正长度区间。首次启用时间是该版本的下界，主题 active、规则有效、精确内容观察以及该下界相交后的时间才需要逐段判定：同段只有一致的当前版本启用配置则产生候选；一致的关闭态或其他提示词版本继续向后查；无会话或并发配置不一致时，若它在首个已知候选之前则整身份为 unknown，不用后续启用掩盖早先缺口。候选导出支持该判定的运行 UUID，`as_of` 按半开上界处理。该版本仍只覆盖当前提示词，不能把进程配置当作 Codex 实际可用或限流证据，仍只导出原始身份、成熟与未知计数，`analysis_status=not_computable`，不计算 ≥95% 结论。
- `analysis-candidate-v3` 在同一只读事务中枚举窗口前已激活的全局提示词版本、已启用运行会话版本，以及本 owner 截止时已有标注或分析 Job 记录的版本，并始终保留当前版本；按 `(content_version_id,topic_id,topic_rule_version,prompt_version)` 独立投影和取对应版本的首次有效结论。历史版本有首次启用和连续一致的运行事实时，按其自身启用时段给候选；只有旧标注或 Job 而缺首次启用、运行会话时列 unknown，不从标注/Job 倒推起点。当前以外的提示词运行时段对待测版本属于关闭态，版本切换前的缺口或冲突仍为 unknown；无匹配的明确关闭时段不造候选。v2 原始证据保留原口径，v3 仍不表示 Codex 实际可用，`analysis_status=not_computable`。
- 四关键词来源、分析、阅读与覆盖的短窗验证及实际缺陷汇入058；032承接重试，038承接HN父链与旧帖新回复。共享服务、真实来源逐项证据与页面闭合后，由009汇总M1 AC，运行库保留按 Design001 §6.3。
- HN评论把现有每主题20帖、6小时刷新、24小时自动候选期、10页/10请求、200根/根下20回复固定为预设初值；按互动分数及稳定ID排序。超过自动候选期的已入库帖可通过POST `/api/contents/{content_id}/comment-runs`显式复采，仍受6小时间隔/预算/owner与CSRF约束；显式按钮与阅读由058验证，038真实核对跨24小时旧帖的新回复。候选年龄不构成已覆盖全部评论的声明。

来源缓存、有限页与 RSS 头部不证明完整；限流、评论父链错误、预算耗尽和标注空值均可产生未确认缺口。全局资源与 Worker 合同见现行总设计001和 PROJECT；历史章节及版本从 Git 查阅。

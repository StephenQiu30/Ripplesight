# 信息获取主链路需求

本文从 [总需求 001](001-热点舆情监控平台需求.md) 保留的 PRD 001 v3.0 基线按 M1 拆出，既有范围与 [Design/Epic 002](../design/002-信息获取主链路设计.md) 对齐；当前执行入口见 [计划索引](../plan/README.md)，待排期项见 [BACKLOG](../../BACKLOG.md)。历史 Research048 的方向配置、规则预览、来源语义和评论能力边界已纳入当前需求；调研原文已删除，可从 Git 历史查阅。已有样本预览由 Design002/历史 Plan059 实现，其余新增部分须在 Design 定标，具体执行步骤排期时补充。需求状态 `approved` 不表示实现或产品验收通过。

当前 Demo 承接总需求 §1 的核心 POC 边界，先收尾 M1：先在一个主题、一条公开关键词来源和一榜上跑通最小可演示闭环，再扩为四来源、六榜的完整 M1 短窗 Demo。两个阶段都在固定代码和同一隔离库中核对有界采集、持久化、分析状态、阅读/覆盖与失败恢复，分别记录真实来源、受控故障和模型证据。连续 72 小时与 NFR-002-001 的最终比例验收留在后续产品验证阶段；本阶段完成不自动关闭依赖长窗或真实模型的 AC。真实 Codex 请求仍暂停，未发请求时仅记录受控分析证据。

## 1. 目标与范围

**目标**：研究者围绕 AI 等关注方向及实体别名设置主题，核对四个关键词来源、六个公开热榜和 Codex 相关性；从来源能力时间窗进入帖子、评论或快照，区分空榜、部分、失败与待分析。

**不包含**：本人账号 B 站及其他登录平台、跨平台事件归并与事件热度、观点摘要、日报/周报、Obsidian、推送、告警与导出增强。

### 当前 M1 Demo 的具体交付

演示目标：研究者设置一个主题后，能实际取得公开信息，阅读帖子、HN 评论和榜单命中，追溯原帖与时间，分辨相关性结论、未分析和未采完；任务失败后能在预算内恢复，重复操作不制造重复结果或重复实耗。本节定义待交付流程，不表示本次已经完成演示。

**阶段 A：首次最小闭环。** 固定一个主题、`hackernews` 搜索及六榜中预检后冻结的一榜，在同一隔离库和短窗完成下表全部用户操作。Web 至少可打开一条真实 HN 帖及其有父链的评论、一条真实热榜快照与主题命中；分析的相关/不相关和异常状态使用明确标记的受控输入，真实模型保持关闭。Web/API/数据库的原始 ID、来源版本、预算和缺口一致；实际停止重启单 Worker 后重放不产生重复身份或预算实耗。预检时冻结所选榜单，运行中不得靠换榜、旧库样本或模拟帖子补齐失败。阶段 A 的通过仅说明这一个来源与一榜的采集阅读 Demo、受控分析和恢复，不表示四来源六榜或真实 Codex 效果通过。执行与证据归 [Plan058](../plan/058-M1短窗POC演示与扩围执行计划.md)。

**阶段 B：完整 M1 短窗 Demo。** 保持相同用户流程与证据等级，逐一扩到四个关键词来源、HN 评论和六个公开热榜；至少一榜按合法间隔取得前后快照。每个入口各自留真实结果、失败或空的事实，不以 A 的单来源结论代替。下表描述阶段 B 的完整范围；阶段 A 也必须覆盖表中适用于所选来源和热榜的操作。

| 用户流程 | Demo 要看到的结果 | 设计合同 / 当前执行入口 |
|---|---|---|

| 核对相关性与分析状态 | 同一内容/主题/规则/提示词版本下，有效结果显示相关/不相关及理由；无记录、待处理、失败、无效分别可见。当前真实模型暂停，流程与这些状态用明确的受控分析验证，不能称为真实 Codex 效果通过。 | Design002 §3、§6 / Plan058（受控） |

**完成条件与证据**：固定待验代码版本、同一隔离库、来源/策略和主题版本，记录此次实际 `[T0,T1)` 短窗。核心用户操作经 Web 完成，并与 API 和数据库核对；CLI 只用于环境准备、执行控制和证据核查。所有纳入演示的来源逐一记录真实入口和结果，帖子/HN 评论/六榜须有真实可读样本；实际空窗允许如实记录，失败或未就绪不能抵作采集成功。不借旧库样本、跨库结果或受控树补足本窗真实输入。

采集阅读主流程、受控分析状态、故障/预算/进程恢复分别给结论。缺少任一必需流程时记待完成；真实模型暂停期间，即使技术流程通过也只报告“采集阅读 Demo 与受控分析通过，真实分析待验”，不宣布完整真实核心链路通过。真实模型恢复后再核对同库真实内容的相关/不相关及理由；不新增模型提供方或绕开费用边界。

本轮复用已有实现，只修演示中可复现的核心问题。逐根远程评论分页、HN 十帖与旧帖新增回复产品抽检、连续72小时、5分钟中位延迟、95%及时率、正式质量抽检后置；不为这些后置条件提前增加投影、表、任务框架或来源。M2 本人账号和 M3 事件属于后续核心 Demo；日报、周报、知识库和推送继续保留为非核心后续能力。下述正式 FR/NFR/AC 不按 Demo 短窗关闭。

## 2. 用户场景与状态

- 日常打开主题，查看四个关键词来源与六榜最新采集的帖子、评论、命中条目及 Codex 相关/不相关理由；待处理或异常标注单列。
- 选定来源、能力和时间窗，核对计划到期、实际请求/页数、预算、入库/去重与未确认缺口，再进入原帖或热榜快照。
- 比较同一来源前后两次热榜快照的排名变化；核对命中主题的条目已入库并完成相关性判断，未命中者只保留快照。
- 看到失败、部分页、空榜或分析积压时追查停止原因；在允许的预算和权限内手动重试，并核对新旧尝试与剩余预算。
- 调研补充场景：用方向与人工确认的实体别名表达关注范围，保存前查看已有入库样本的规则命中解释，分辨逐来源的原生查询、本地过滤及作品/评论/回复能力。该场景按新增 FR/AC 后续验证，不扩充当前 Demo 的完成条件。

当前匿名 Demo 直接进入业务页面，不要求账户、登录或用户会话；业务 `owner_id`/`created_by` 仅维持历史业务 UUID 分区，按 [Design001 §9.2](../design/001-热点舆情监控平台总体设计.md#92-当前-demo-的访问与数据分区) 解析唯一分区，不能作为用户身份。未来 ToC 账户及多用户隔离见 [PRD001 §2.1 后置账户需求](001-热点舆情监控平台需求.md#21-未来-toc-用户登录需求后置)，当前 Demo 与受控证据不能证明多用户 AC 已通过。页面保留加载、空、业务错误与重试状态；以上场景按本里程碑 FR/AC 与总需求 NFR 核对。

| FR-002-011 | 来源作品与评论能力矩阵 | 按来源入口及版本分别列明关键词发现、作品列表/链接、正文、互动计数、一级评论正文、回复正文/父链、旧帖新增回复能力，并将声明支持、当前配置就绪、真实窗口结果、产品验收分开。显示采样排序、条数/页数/时间上限、截止/失败及缺口；评论计数不等于评论正文，本地读取页尾不等于源站采全。当前 M1 仅 HN 承担评论/回复验收；其他新闻/RSS/热榜入口不得据其原平台能力推定评论支持；本人账号 B 站仍归 M2。 |

**调研补充的执行边界**：FR-002-008—011 与 AC-002-009—012 已纳入需求。已有内容只读样本预览合同见 [Design002 已有内容只读样本预览](../design/002-信息获取主链路设计.md#已有内容只读样本预览合同)，历史 Plan059 的受控/真实只读证据见 Acceptance002 EV-002-053；方向/别名、逐来源执行方式与能力矩阵仍待设计分解，新增产品 AC 未整体通过。它们不增加 Plan058 阶段 A/B 的必需用户操作，不改变一个主题、HN 搜索与一榜起步，再扩至四关键词来源、HN 评论与六榜的当前 POC 范围与完成条件。本次不新增付费来源；事件归并、事件热度及观点摘要不进入 M1 完成条件。实施前须先同步对应 Design，并在排期时补本轮执行步骤，不能以 Research 的竞品声明或开源功能作为本项目通过证据。

**来源与时间口径**：四关键词来源为 `hackernews` Algolia、`google_news` Google News 搜索 RSS、`news_search` 本机 SearXNG `duckduckgo news`、`rss_36kr` RSSHub `/36kr/newsflashes`；六榜为微博、百度、知乎、B 站热门、36Kr、澎湃 RSSHub 路由，具体路径见 FR-002-006。主题默认 30 分钟、最短 10 分钟；来源预设取更保守节奏。默认 24 小时回看、上限 7 天，不证明历史完整覆盖；发布时间、首次发现与热榜观察时间分别记录。

### 4.1 AIHOT 对照后补齐的阅读与素材需求

[Research049 §3—4](../research/049-AIHOT功能拆解与HotKey需求对照.md) 显示，“采到一条链接”与“获得可阅读、可判断的材料”需要分开。以下是后续需求，不追加到 Plan058 A/B 的完成条件；既有正文/分析状态仍按当前 Demo 验收。

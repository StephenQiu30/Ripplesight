# 完整业务需求

完整业务覆盖以下功能及其用户流程；技术固定 Python/FastAPI、Next.js、Kafka。采集、事件、报告、通知及分发的要求由 PRD002/004/005/006/007 持有，本文定义其余完整业务要求。原功能与各领域未通过条件保持有效。

## 1. 完整范围

原有主题规则、来源版本、帖子与评论父链、原生热榜快照、覆盖和预算、证据生命周期、失败恢复、日报及 Obsidian 必须保留。公开欢迎页与说明保留 SEO；账号密码、GitHub、邮箱验证码登录后进入全部业务工作区，按 Design001 §9.2 隔离个人资源；已登录账户可连接GitHub或经验证码绑定/更换邮箱，保持原账户与个人资源，拒绝其他账户已占用的身份；上游管理员身份作为运营控制能力独立承接，不将管理员与平台采集账号或报告收件人混为一体。

业务链路包含：信源配置/采集/外部摄入 → 材料身份与修订/正文质量/媒体 → 行业预筛/精选评分/结构化/中文写作/全文翻译 → 事实与故事/人工修订/独立参与者热度 → 全部动态/精选/搜索/分类主题/本机收藏已读 → 日周月刊 → RSS/API/MCP/Markdown/SEO/分享 → 内容通知/运维告警/调用回执/恢复/备份。模型榜及 Codex 公告监控各自拥有采集、持久状态、读取、页面和定时执行闭环。

“完整”指获准启用后的真实用户操作和持久结果一致，不要求复制上游的已知缺陷、商标、部署拓扑或供应商。真实调用暂停、凭据/费用/许可未定时，功能仍须实现受控路径和明确禁用原因；未执行的真实验证保留未通过，不能以模拟结果宣布完整产品已验收。

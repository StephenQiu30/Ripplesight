# 完整业务需求

完整业务覆盖以下功能及其用户流程；技术固定 Python/FastAPI、Next.js、Kafka。采集、事件、报告、通知及分发的要求由 PRD002/004/005/006/007 持有，本文定义其余完整业务要求。原功能与各领域未通过条件保持有效。

## 1. 完整范围

原有主题规则、来源版本、帖子与评论父链、原生热榜快照、覆盖和预算、证据生命周期、失败恢复、日报及 Obsidian 必须保留。公开首页与说明保留 SEO；资讯、专题、已许可日周月刊和已发布模型榜无需登录，账号密码、GitHub、邮箱验证码登录后进入个人工作区，按 Design001 §9.2 隔离个人资源；已登录账户可连接GitHub或经验证码绑定/更换邮箱，保持原账户与个人资源，拒绝其他账户已占用的身份；上游管理员身份作为运营控制能力独立承接，不将管理员与平台采集账号或报告收件人混为一体。

业务链路包含：信源配置/采集/外部摄入 → 材料身份与修订/正文质量/媒体 → 行业预筛/精选评分/结构化/中文写作/全文翻译 → 事实与故事/人工修订/独立参与者热度 → 全部动态/精选/搜索/分类主题/本机收藏已读 → 日周月刊 → RSS/API/MCP/Markdown/SEO/分享 → 内容通知/运维告警/调用回执/恢复/备份。模型榜及 Codex 公告监控各自拥有采集、持久状态、读取、页面和定时执行闭环。

“完整”指获准启用后的真实用户操作和持久结果一致，不要求复制上游的已知缺陷、商标、部署拓扑或供应商。真实调用暂停、凭据/费用/许可未定时，功能仍须实现受控路径和明确禁用原因；未执行的真实验证保留未通过，不能以模拟结果宣布完整产品已验收。

### 用户问题、目标与价值

用户首先需要稳定取得可读材料，再把个人关注转成有出处的日报和周报。完整业务的价值是减少重复查找、帮助核对信息与讨论、保留可复用的研究结果；模型榜、公告、媒体和运营能力分别服务于这些具体任务，不以功能数量衡量交付。

| 用户任务 | 要解决的问题 | 应获得的结果与价值 |
|---|---|---|
| 匿名阅读公开资讯 | 无法确认页面是否持续更新、模型异常后还有什么可读 | 阅读真实标题、来源摘要、原文及时间，看清更新和缺口；基础阅读不依赖个人账户或模型精选 |
| 登录后关注关键词并阅读报告 | 保存规则后不知道实际取得什么，也难以整理某日或某周的材料 | 规则、命中材料、支持来源的评论及个人日周报可追溯；已知材料、待分析与采样范围清楚，减少重复查找 |
| 比较模型、跟进公告及分享证据 | 排名、价格或预测缺少时点和依据，分享内容可能失去许可 | 核对已发布榜单的来源和方法、公告原话与复核状态；分享固定版本且仍获准展示的内容 |
| 维护公开发布和运行 | 故障、撤权、未知结果或备份失败后难以确认影响与恢复 | 在独立运营权限下定位受影响来源、任务、版本和预算，执行可审计的纠错、撤回与恢复 |

以上按用户任务划分范围，不推定所有用户都需要运营、问答或通知。目标由下文原 FR/AC 中的真实操作、持久结果、引用、权限与窗口核对衡量；减少阅读时间、提升个人研究价值和付费意愿仍需实际使用验证。需求主责沿用各领域 PRD，具体执行责任与排期维护在 BACKLOG，本文不指定未经确认的联系人或工期。

### 范围与假设

最低交付包含公开基础资讯及登录后的关键词、可支持评论、个人日报和周报，分别由 FR-002-015、FR-005-012 持有。后续事件、精选、知识库、推送、模型榜及运营增强保持完整产品范围，按各自条件发布；它们不成为已就绪来源上的基础阅读和个人报告的统一前置。

- **来源假设**：指定来源能在获准用途、频次与预算内持续提供有效材料，须用逐来源运行证据验证。六类输入和既定四搜索/六榜范围已经确定；具体站点、账号、字段许可和运行表现仍须分别核查，不将类型支持当作平台接入或全量检索。
- **个人价值假设**：关键词与实体别名能取得用户需要的信息，日报/周报的窗口、去重和出处能帮助实际研究。沿用总需求 OPEN-001-110/112，以真实主题、工作样本和后续使用反馈验证；没有结果时不宣称减少阅读时间或已证明付费价值。
- **评论假设**：来源允许读取的评论样本足以支持相应讨论说明。可采正文、回复父链和观点质量分别验收；没有评论能力、缺口和真实零评论保持不同含义。
- **供应与恢复假设**：来源、模型、对象存储和渠道在启用范围内满足其合同；凭据、费用、许可、故障恢复和真实送达逐项留证。受控响应、健康检查和文件上传分别不能替代真实供应、业务恢复或恢复演练。

**非目标**：全平台、全历史或全部评论覆盖；跨设备收藏同步；用户实际 Codex 配额到账保证；复制上游品牌、重建服务栈或另建正文库、队列和收费账本。模型、X、本人 B站、SMTP 与飞书的既有暂停或启用条件不变，未定许可和费用不因本需求成为完整范围而获准调用。排名公式、时间边界、费用口径及技术合同仍由原 PRD/Design 持有。

## 3. 整体退出条件

所有源处理器、业务状态、定时任务、HTTP/MCP/RSS 出口、生成客户端、页面和管理员操作逐项可追踪，无仅配置/仅枚举/仅占位的完成项。受控测试验证正常、失败、并发、撤回、修订、幂等、预算与重启；实际 PostgreSQL/Kafka/对象存储和浏览器验证接入。各真实来源、模型质量、渠道送达及既有持续窗口单独留证，前置条件未满足即保留未通过。原 HotKey 操作与数据回归无损后，才撤下被替代的路径。

### 分能力发布门槛

发布按能力判断实现完整性、启用准入、真实运行和产品验收，分别留下证据。处理器或投影缺失属于实现缺口；已有路径尚缺真实来源、权限或连续窗口属于对应验收缺口，两者分别核对。受控路径可用于检查功能与失败边界，面向用户的能力声明须由相应真实结果支持，不以“代码基础已有”概括全部完成，也不把未验真实供应的能力一律写为缺实现。

| 能力 | 面向用户发布的必需门槛 |

| 公开基础资讯与个人日周报 | 分别满足 AC-002-015、AC-005-013 及相关原 AC；所用来源、公共发布分区和个人归属明确，原始资讯投影、个人日/周处理器与合法到期结果逐一核对。持续性、质量、vault 和送达仍单独验收 |

# 热点舆情监控平台总需求

本文保留跨里程碑产品原则、用户与证据口径、来源和时间规则、共享 NFR 及全局追踪。各能力的现行 BR/FR/AC 见 002—007；现行总设计为 [Design001](../design/001-热点舆情监控平台总体设计.md)，当前排期见 [计划索引](../plan/README.md)。旧设计从Git历史查阅。

## 1. 需求结论与原则

研究者按主题设置关键词，查看各来源实际采到的帖子、评论和热榜条目，追溯原帖、观察时间、采集窗口与分析依据，并看清未采到、未采完和未分析的部分。只有逐来源、逐能力的真实采集和持续运行证据，才能支持“信息获取已验收”。

1. **先取得可信信息**：来源逐个准入、逐个验收；采集频率、回看窗口和来源更新节奏分别记录。回看和空结果不能证明完整覆盖。
2. **结果与证据分开**：已入库、已判断相关、覆盖已确认是不同状态；失败、部分结果、预算耗尽和分析积压可见。内容、评论父链、榜单快照均可追到来源与时间。
3. **数字由程序计算，Codex 只做判断与写作**：当前用本机 Codex app-server 判相关；后续报告中的数字、排序和引用由程序生成，模型不可用时可生成标明降级的模板版。
4. **后续结果独立验收**：日报、周报、知识库写入与问答、报告渠道投递属于后续独立能力；登录验证码邮件属于身份认证，独立实现和验收，不能被报告推送暂缓所阻塞。

### 产品定位与目标流程

HotKey 是面向普通用户的 ToC 信息监控产品，提供**关注方向 → 发现具体事件 → 观察升温与进展 → 阅读原文及讨论**的流程。当前Demo无需登录注册，直接进入业务页面；正式产品账户需求后置。事件应说明发生了什么、为何命中关注方向、热度来自哪些已采来源、评论讨论什么，以及证据和采样缺口。

方向和中英文实体/别名沿用监控主题及现有词组；来源的原生搜索与本地过滤分别说明。事件相似度只生成候选，不证明同一事件；不同版本发布及后续争议应保留事实差异。热度描述观测范围内的关注，评论结论描述明确样本，不称全网热度或全部用户意见。

信息获取定位沿用历史 Research048 的已承接结论；调研原文已删除，可从 Git 历史查阅，现行要求由本文及子 PRD 保持。当前 Demo 已清理用户体系，未来 ToC 账户要求留在 §2.1，按产品阶段后置排期。M1先收尾信息获取与阅读，事件/热度归M3，观点质量归M4，来源扩展归M6；不改写058证据与产品阈值。

### 当前核心链路 POC 边界（2026-09-30）

最终目标是整个核心链路的 POC 验证：主题与来源配置 → 有界调度和手动采集 → 帖子、评论、热榜持久化 → 相关性分析 → Web 阅读、覆盖查询、任务控制与失败恢复。当前先在一个主题、HN 公开搜索和一条已准入热榜上跑通首次可演示的完整用户流程，再把相同证据扩至四关键词来源和六榜。首轮最小闭环不能代替扩围或 M1 产品验收；单个适配器、单个 Job 或单个页面通过也不能代替整条链路。两阶段均须在固定代码版本、同一隔离库和明确短窗中核对输入、持久事实、状态与用户操作；模型受控验证和真实来源证据分别记录，真实 Codex 请求暂停期间不宣布真实分析效果通过。

本人账号来源按 M2 的本人核查条件推进，事件组织、人工修订和热度按 M3 后续切片推进。日报、周报、Obsidian、知识库检索/问答、报告导出和渠道投递不纳入当前核心 POC 排期，也不作为 M1—M3 的技术前置。复用既有底座，只修实际失败和补核心功能缺口；不为未来能力提前增加模块、表或通用框架。M1 的009与 M2 独立72小时运行、正式时效指标和质量抽检留给产品验证，需求编号、最终产品验收条件与阈值保持不变。

当前 M1 Demo 的最小闭环、十来源扩围、用户操作和完成条件见 [PRD002 §1](002-信息获取主链路需求.md#当前-m1-demo-的具体交付) 与 [Plan058](../plan/058-M1短窗POC演示与扩围执行计划.md)。M1 信息获取、M2 本人账号、M3 事件是分步推进的核心能力；不把任一阶段通过写作整个核心能力已交付。

## 2. 用户、场景与证据状态

当前Demo使用者直接访问主题、连接、任务和内容，不建立账户或登录注册入口。来源平台账号属于采集连接，报告接收方属于投递对象。来源软件许可证和平台数据授权单独准入；现有 MediaCrawler 本人 B 站试点仍受其许可和授权限制。正式ToC账户及用户权限要求见下节后置需求。

### 2.1 未来 ToC 用户登录需求（后置）

用户2026-10-01最新决定：当前 Demo 无需登录、注册和用户体系。相关页面、API、密码/会话/部署密钥依赖已删除，业务页面无需 Cookie 即可读取，写入使用固定自定义头；已有业务分区 UUID 仅保持数据关联。当前不实现下表账户需求，不保留实现骨架。此前用户名密码、GitHub App、邮箱验证码和无感登录要求保留给正式产品阶段；恢复时重新审核详细合同。Demo 通过不能关闭下表产品 AC。

| FR | 功能 | AC 与完成条件 |
|---|---|---|
| FR-001-122 | GitHub App 登录 | AC-001-123：经 GitHub App 用户授权取得稳定用户 ID 和已验证主邮箱，创建或读取正确的产品账户并建立会话；取消、过期或错误回调不登录。只读身份与邮箱，不请求仓库或组织权限。 |
| FR-001-123 | 邮箱验证码登录 | AC-001-124：发送并核验 6 位、5 分钟有效、单次使用的验证码；正常邮箱可首次注册及再次登录。发送冷却、频次、最多 5 次校验、过期和重放均有明确结果；真实邮件收取另留证据。 |
| FR-001-124 | 登录与注册共用入口 | AC-001-125：`/login` 提供用户名密码、GitHub App 和邮箱验证码。首次 GitHub/邮箱验证成功即注册，同一已验证邮箱关联同一账户；已有 GitHub ID 绑定不可被另一个 GitHub 账号覆盖。用户名密码登录只读取已有账户，不自动注册。移除单部署初始化、部署密钥及重复工作区身份接口。 |
| FR-001-125 | 多用户数据隔离 | AC-001-126：真实两个账户分别创建主题、连接、内容与任务，互不可见、不可修改；列表、详情、导出、预算及异步任务均按会话用户和资源归属检查，不依赖单账户假设。 |
| FR-001-126 | 会话与退出 | AC-001-127：所有登录方式共用可撤销的数据库会话与 Cookie；验证过期、CSRF、退出和页面会话失效。身份返回用户 ID、用户名、邮箱与过期时间；保留凭据版本用于密码变化后的会话失效，删除重复工作区包装。 |
| FR-001-127 | 用户名密码与凭据维护 | AC-001-128：保留唯一用户名、密码哈希及用户名密码登录；已验证账户可设密、改密、找回密码，邮箱验证码须绑定当前用户和凭据更新用途。密码变化撤销全部旧会话；错误账号与密码不暴露用户是否存在，限流与 CSRF 可验证。 |
| FR-001-128 | 无感登录 | AC-001-129：有效 Cookie 下刷新、再次打开页面或重开浏览器可恢复同一用户，访问 `/login` 自动跳产品页；默认固定有效期 12 小时。会话过期、撤销、主动退出或密码变化后须重新验证；网络失败提供重试，不误判已退出，不在客户端保存密码或会话令牌。 |

以上正式产品账户AC均未通过；当前Demo访问与数据分区合同见 [Design001 §9.2](../design/001-热点舆情监控平台总体设计.md#92-当前-demo-的访问与数据分区)，清理实施为历史 Plan061。未来需求排期时重新审核实现与迁移合同，不提前维护详细执行卡。不增加组织、租户、角色矩阵、邀请或通用身份平台。

### 2.2 使用场景与已有证据

| 场景 | 当前或后续的用户结果 |
|---|---|
| 日常查看 | 打开主题，查看最近各来源采到的帖子、评论、热榜命中和 Codex 相关性；能点回原帖，知道哪些内容尚待分析 |
| 调整关注方向 | 用“大模型、AI Agent、开源模型”等方向及用户填写的实体/别名调整词组，保存前查看已有样本的命中原因和来源执行方式；无可用样本时明确提示 |
| 发现事件与进展（M3 后续） | 按关注方向查看具体事件、首次已知时间、最新进展、来源构成及升温依据；打开代表作品和评论，核对覆盖与人工修订 |
| 理解讨论（M4 后续） | 查看已采样评论的问题、观点和引用，区分实际体验、支持、质疑及补充证据；缺少有效评论时显示证据不足 |
| 核对覆盖 | 按来源、能力、时间窗查看到期、尝试、请求与页数、停止原因、入库/去重、预算和缺口；空榜、失败与部分结果有不同状态 |
| 试用本人账号来源 | 低频启用 B 站试点；遇验证、登录失效或访问频繁立即停止，由本人检查并人工恢复 |
| 阅读与追查（后续） | 分别查看日报、周报；从报告进入原帖或已存在的 Obsidian 笔记，在知识库中浏览、检索、提问并查看出处 |
| 接收提醒（后续） | 在推送能力单独启用并验收后收取邮件或飞书报告；突发告警更晚交付 |

**证据分层**：代码已合入、受控测试通过、真实运行通过、产品验收通过分别记录；前者不能推定后者。截至 2026-09-26，开发库 `hotkey_p1` 的约 4 小时运行记录包括四个关键词来源入库、六榜快照与 738 条 Codex 标注（其中 3 条相关字段为空，须列为标注异常）。HN 评论 45 个线程来自同日较早、随后被重建的开发库，不能与当前库统计合并。四来源尚无连续 3 天产品验收；六榜尚无逐榜持续覆盖验收。B 站修复前真实尝试失败，修复后尚未真实采集，来源开关默认关闭。日报、Obsidian 和飞书已有代码及受控测试记录，真实连续送达与写入未证实；SMTP 尚未见实现。这些开发证据不能宣布任何对应产品能力完成，详见 Design 001 第 2 节。

## 4. 来源与时间范围

每个来源按支持的**搜索、帖子、评论、热榜**能力单独验收。预设已应用、RSS 可解析、诊断探针或单个成功 Job 只说明相应步骤，不代表来源接入完成。

| 范围 | 来源键与实际入口 | 本轮能力与限制 | 里程碑 |
|---|---|---|---|
| 四个关键词来源 | `hackernews`：Algolia 公开 API | 搜索、帖子；HN 评论及楼中楼用于父链和重放验收 | M1 |
| 四个关键词来源 | `google_news`：Google News 搜索 RSS | 搜索、帖子 | M1 |
| 四个关键词来源 | `news_search`：本机 SearXNG `127.0.0.1:8888`，`duckduckgo news` 引擎 | 搜索、帖子；发布时间以来源实际字段为准 | M1 |
| 四个关键词来源 | `rss_36kr`：本机 RSSHub `127.0.0.1:1200/36kr/newsflashes` | 36Kr 快讯按主题过滤；不是 36Kr 原站 feed，也不同于热榜 `/36kr/hot-list` | M1 |
| 六个公开热榜 | 微博、百度、知乎、B 站热门、36Kr、澎湃；均经本机 RSSHub，路由见 FR-002-006 | 来源级快照、排名变化、主题命中、内容入库和 Codex 相关性 | M1 |
| 本人账号试点 | B 站：固定补丁版本的 MediaCrawler 宿主机子进程 + 独立 CDP 浏览器资料 | 搜索、帖子；同轮缓存的一级评论每帖 ≤ 20，不采楼中楼；修复后真实验收前保持未接入 | M2 |
| 后续逐项准入 | 微博、小红书、抖音、知乎登录能力、微信公众号；Reddit 官方 OAuth；X 官方 API | 各自单独确定许可、凭据、频率、分页和失败状态；X 凭据与月度上限未确认前不发真实请求 | M6 或另定 |

**三种时间口径**：主题请求频率默认 30 分钟、最短 10 分钟；来源预设另有最短间隔、静默时段和预算，实际尝试取更保守节奏。`HOTKEY_COLLECTION_LOOKBACK_SECONDS` 默认向前回看 24 小时、上限 7 天，决定当前任务查询窗口；来源自身发布时间、RSS 缓存时间和榜单更新时间由来源决定。重复回看按来源身份去重，但**24 小时回看不等于历史完整覆盖或缺口已补**；可信尾段与分页边界不足时仍标部分覆盖。有发布时间的内容分别记录发布时间与首次发现时间；无发布时间的内容保留空发布时间，以首次发现时间作统计依据并单列，不伪造发布时间。热榜另按默认1800秒、可配置的独立观察桶运行，M1验收窗口按PRD002冻结实际间隔。

## 5. 共享非功能需求

| ID | 要求 | 验收口径 |
|---|---|---|
| NFR-001-101 | 可追溯 | 内容、评论、热榜命中和分析可定位到来源、原帖、采集/观察时间及版本；报告每个数字、观点可追到冻结输入并可复算 |
| NFR-001-102 | 数据正确 | 同来源同原生 ID 唯一，评论父链正确；缺失与 0 不混淆，时间存 UTC、按 Asia/Shanghai 展示；发布时间、发现时间、热榜观察时间分离 |
| NFR-001-103 | 时效 | M1 在正常可运行时段，以来源计划到期至对应 Job 结束计，四个关键词来源和六榜逐来源的中位延迟 ≤ 5 分钟；Codex 可用时，新入库且需分析的内容在入库后 60 分钟内取得有效相关性结论的比例 ≥ 95%。来源静默、来源限流延后和 Codex 限流时段分别记录并从相应达标率样本中排除；正常时段未受理或未结束的到期窗口记为超时，待分析与失败计入相关性分母，不得静默排除。日报在获准渠道的送达目标为设定时间后 15 分钟内，周报为周一 09:15 前；报告生成与渠道送达分别按 M4/M5 验收 |
| NFR-001-104 | 可靠执行 | 重复调度、重试、进程重启或消息重放不重复内容、Job 与投递，不静默丢任务；失败和部分结果保留原时间窗证据 |
| NFR-001-105 | 故障隔离 | 单来源、单页或 Codex 故障不抹掉已入库内容；未完成覆盖和分析积压可见；后续报告标明缺失或降级 |

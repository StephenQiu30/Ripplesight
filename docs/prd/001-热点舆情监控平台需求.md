# PRD001 热点舆情监控平台总需求

本文定义跨领域的产品原则、用户、来源与时间口径、共享 NFR、里程碑和产品决策。各领域需求见 PRD002—008，总体设计见 [Design001](../design/001-热点舆情监控平台总体设计.md)，进度只看 [BACKLOG](../../BACKLOG.md)，证据只看 Acceptance。

## 1. 产品定位与原则

HotKey 是面向普通用户的 ToC 信息监控产品，流程为：**配置关注方向 → 持续获取资料 → 阅读相关内容 → 发现具体事件 → 观察升温与进展 → 追溯原文及讨论**。首页公开展示已许可发布的资讯、事件、专题、刊物和模型榜；创建个人关注、生成或发送报告及管理操作须真实登录。

1. **先取得可信信息**：来源逐个、逐能力准入和验收；采集频率、回看窗口和来源更新节奏分别记录，回看和空结果不能证明完整覆盖。
2. **结果与证据分开**：已入库、已判相关、覆盖已确认是不同状态；失败、部分结果、预算耗尽和分析积压可见；内容、评论父链和榜单快照可追到来源与时间。
3. **数字由程序计算，模型只做判断与写作**：报告的数字、排序和引用由程序生成；模型不可用时生成标明降级的模板版。
4. **各能力独立验收**：关键词资料、评论与个人日报/周报构成最低个人闭环；报告不等待事件、知识库或消息送达。登录验证码邮件属于身份认证，不受报告推送暂缓影响。
5. **观测口径不外推**：方向和实体别名沿用监控主题词组；原生搜索与本地过滤分别说明。事件相似度只产生候选；热度描述观测范围内的关注，评论结论只描述明确样本，不称全网热度或全部用户意见。

## 2. 用户与价值

| 使用对象与任务 | 价值 | 必须交付的结果 |
|---|---|---|
| 匿名读者：了解公开新信息并打开原文 | 首次访问即可阅读，模型不可用时仍能核对来源事实 | 公开分区的获准标题、来源摘要或无摘要说明、原文与时间可读；按 FR-002-015 / AC-002-015 |
| 个人关注用户：跟踪关键词、核对讨论、形成日周报 | 保存一次关注即可找回材料，知道哪些已分析、哪些未知 | 规则和来源能力可追溯，材料/评论范围可核对；日报与周报分别生成；按 AC-005-013 及各领域 AC |
| 运营维护者：维护来源、发布权限与运行边界 | 故障、额度耗尽和撤回有依据，能恢复且不泄露个人内容 | 准入、版本、频次、费用、预算、任务、许可和恢复可追溯；按 FR-008-007—009 与共享 NFR |

不扩展到组织租户、团队协作或企业全量舆情。减少重复查找、提高判断效率和付费意愿属于待验证假设（OPEN-001-110/112），未取得使用数据前不承诺提升比例或用户规模。交付日期在执行前核定。

职责：产品负责人确认问题、范围与验收口径；研发负责任务链、契约与页面结果；运营负责发布分区、来源/数据许可和额度；验证负责人记录受控、真实运行与产品证据。人员未登记时保持待定。

### 2.2 使用场景

| 场景 | 用户结果 |
|---|---|
| 日常查看 | 打开主题，查看各来源采到的帖子、评论、热榜命中和相关性；能回到原帖，知道哪些待分析 |
| 调整关注方向 | 用方向和实体/别名调整词组，保存前查看已有样本的命中原因和来源执行方式；无样本时明确提示 |
| 发现事件与进展（M3） | 查看具体事件、首次已知时间、最新进展、来源构成及升温依据；打开代表作品和评论 |
| 理解讨论（M4） | 查看已采样评论的问题、观点和引用，区分体验、支持、质疑和补充证据；证据不足时明示 |
| 核对覆盖 | 按来源、能力、时间窗查看到期、尝试、请求与页数、停止原因、入库/去重、预算和缺口 |
| 试用本人账号来源 | 低频启用 B 站试点；遇验证、登录失效或频繁访问立即停止，本人检查后人工恢复 |
| 个人报告与追查 | 分别查看日报、周报和待分析材料并回到原帖；无评论能力、未采集、部分与真实零分别说明 |
| 沉淀资料 | 从报告进入 Obsidian 笔记，浏览、检索、提问并查看出处 |
| 接收提醒 | 推送单独启用并验收后收取邮件或飞书报告；突发告警更晚交付 |

### 2.3 证据等级

代码实现、受控测试、真实运行和产品验收分别判断。受控测试验证状态机、边界与故障；真实运行验证实际来源、外部依赖和持久结果；产品验收按各 AC 的样本、连续窗口和用户核对口径判断。较低等级不能替代较高等级，代码实现本身不是产品通过证据。

## 3. 账户与登录

公开首页提供许可阅读与 SEO；账号密码、GitHub 和邮箱验证码登录后进入个人工作区。历史业务分区只能由维护者显式映射到指定账号，首个注册者无权取得旧数据。访问与分区合同见 [Design001 §9.2](../design/001-热点舆情监控平台总体设计.md#92-公开欢迎页登录与个人数据访问)；不增加组织、租户、角色矩阵、邀请或通用身份平台。

| FR | 功能 | AC 与完成条件 |
|---|---|---|
| FR-001-122 | GitHub 登录 | AC-001-123：经 GitHub OAuth App 授权取得稳定用户 ID 和已验证主邮箱，创建或读取账户并建立会话；取消、过期或错误回调不登录；不请求仓库或组织权限。 |
| FR-001-123 | 邮箱验证码登录 | AC-001-124：6 位、5 分钟有效、单次使用；可首次注册和再次登录；发送冷却、频次、最多 5 次校验、过期和重放有明确结果；真实收件另留证据。 |
| FR-001-124 | 登录与注册共用入口 | AC-001-125：`/login` 提供邮箱或用户名密码、GitHub 和邮箱验证码。首次 GitHub/邮箱验证即注册，同一已验证邮箱关联同一账户；未设密码的账户进入设密步骤后返回安全原目标；已有 GitHub 绑定不可被覆盖；密码登录不自动注册。 |
| FR-001-125 | 多用户数据隔离 | AC-001-126：两个真实账户分别创建主题、连接、内容与任务，互不可见、不可修改；列表、详情、导出、预算和异步任务按会话用户与资源归属检查。 |
| FR-001-126 | 会话与退出 | AC-001-127：所有登录方式共用可撤销的数据库会话与 Cookie；过期、CSRF、退出和会话失效可验证；身份返回用户 ID、用户名、邮箱与过期时间；凭据版本用于改密后的会话失效。 |
| FR-001-127 | 密码登录与凭据维护 | AC-001-128：唯一用户名和密码哈希；已验证邮箱或用户名加密码均可登录；可设密、改密、找回。新近验证会话可首次设密，超期须重新核验邮箱；已有密码时须当前密码或凭据更新用途的验证码。改密撤销全部旧会话并为当前操作建立新会话；错误账号、无密码账户和错误密码返回同一公开结果，限流与 CSRF 可验证。 |
| FR-001-128 | 无感登录 | AC-001-129：有效 Cookie 下刷新、重开页面或浏览器恢复同一用户，访问 `/login` 自动跳转；固定有效期 12 小时；过期、撤销、退出或改密后须重新验证；网络失败可重试，不误判退出，客户端不保存密码或会话令牌。 |

账户设置为左右布局：左侧展示头像、用户名、邮箱和验证状态，支持 JPG/PNG/WebP（≤2 MB）上传；右侧分基本资料和登录安全。头像规范化后持久保存，资料栏与顶部菜单一致；非法图片和失败上传有明确结果且不覆盖原头像。改用户名不要求改密码。窄屏依次显示，保留键盘、焦点和未提交草稿。

## 5. 来源与时间范围

每个来源按**搜索、帖子、评论、热榜**能力单独验收。预设已应用、RSS 可解析、诊断探针或单个成功 Job 只说明相应步骤，不代表来源接入完成。

| 范围 | 来源键与入口 | 能力与限制 | 里程碑 |
|---|---|---|---|
| 关键词来源 | `hackernews`：Algolia 公开 API | 搜索、帖子；评论及楼中楼用于父链和重放验收 | M1 |
| 关键词来源 | `google_news`：Google News 搜索 RSS | 搜索、帖子 | M1 |
| 关键词来源 | `news_search`：本机 SearXNG `127.0.0.1:8888`，`duckduckgo news` | 搜索、帖子；发布时间以来源实际字段为准 | M1 |
| 关键词来源 | `rss_36kr`：本机 RSSHub `/36kr/newsflashes` | 36Kr 快讯按主题过滤；不同于热榜 `/36kr/hot-list` | M1 |
| 六个公开热榜 | 微博、百度、知乎、B 站热门、36Kr、澎湃，经本机 RSSHub（路由见 FR-002-006） | 快照、排名变化、主题命中、入库和相关性 | M1 |
| 本人账号试点 | B 站：固定补丁 MediaCrawler 宿主子进程 + 独立 CDP 资料 | 搜索、帖子；同轮一级评论每帖 ≤20，不采楼中楼 | M2 |
| 后续逐项准入 | 微博、小红书、抖音、知乎登录、公众号；Reddit 获批官方 API/OAuth；X 官方 API；七平台免费路线见 PRD007 | 各自确定软件许可、数据授权、凭据、费用、频率、分页和失败状态；X 未确认凭据与月上限前不发真实请求 | M6 |

**时间口径**：主题请求频率默认 30 分钟、最短 10 分钟；来源预设另有最短间隔、静默时段和预算，实际取更保守值。`HOTKEY_COLLECTION_LOOKBACK_SECONDS` 默认回看 24 小时、上限 7 天，**回看不等于历史完整覆盖**。发布时间与首次发现时间分别记录；无发布时间的内容发布时间留空，以首次发现时间统计并单列。热榜按默认 1800 秒的独立观察桶运行。

## 6. 共享非功能需求

| ID | 要求 | 验收口径 |
|---|---|---|
| NFR-001-101 | 可追溯 | 内容、评论、热榜命中和分析可定位到来源、原帖、采集/观察时间及版本；报告的数字和观点可追到冻结输入并可复算 |
| NFR-001-102 | 数据正确 | 同来源同原生 ID 唯一，评论父链正确；缺失与 0 不混淆；时间存 UTC、按 Asia/Shanghai 展示；发布、发现、观察时间分离 |
| NFR-001-103 | 时效 | M1 正常时段内，四关键词来源和六榜逐来源从计划到期到 Job 结束的中位延迟 ≤5 分钟；模型可用时新入库待分析内容 60 分钟内取得有效相关性结论的比例 ≥95%。静默、来源限流和模型限流时段分别记录并排除；未受理或未结束的到期窗口记超时，待分析与失败计入分母。日报在获准渠道送达目标为设定时间后 15 分钟内，周报为周一 08:15 前，按 M4/M5 分别验收 |
| NFR-001-104 | 可靠执行 | 重复调度、重试、进程重启或消息重放不重复内容、Job 与投递，不静默丢任务；失败和部分结果保留原时间窗证据 |
| NFR-001-105 | 故障隔离 | 单来源、单页或模型故障不抹掉已入库内容；未完成覆盖和分析积压可见；报告标明缺失或降级 |
| NFR-001-106 | 资源控制 | 来源频次、词数、条数、请求、并发和模型调用经预设及持久预算账本设硬上限；限流后按规则延后或停用，不发起付费模型请求，重试不返还已用预算 |
| NFR-001-107 | 安全 | 只采公开或本人授权数据；凭据与浏览器资料不入前端、数据库、日志、Git、容器或模型输入；外部正文按不可信内容处理，请求和重定向限白名单，模型子进程使用最小环境 |
| NFR-001-108 | 分析质量 | 每主题人工抽检 100 条，相关性准确率 ≥90%、情感准确率 ≥80%；抽检前不得宣布质量达标 |
| NFR-001-109 | 知识库安全写入 | Obsidian 只写 `HotKey/` 管理区块、原子替换、保留用户区块；vault 不可写不阻断获取或报告 |
| NFR-001-110 | 本人账号风控 | 以不触发风控为硬上限；遇验证码、滑块、登录失效或访问频繁立即停该来源及后续调度并记录原因，不破解、不换号、不自动恢复，本人核查后人工重启 |
| NFR-001-111 | 采集可观测 | 来源 × 能力 × 时间窗的到期、请求/页数、停止原因、入库/去重、分析积压/失败/标注异常、预算和缺口可核对；空、截断、失败、未分析状态不同 |
| NFR-001-112 | 重试时间与计量 | 保留 Job 首次启动时间，每次尝试另记；自动重试和限流重排沿用原预算剩余量，手动重试在下次领取时开新采集预算周期，不重置每日/全局预算；重复点击幂等 |

领域时效与风控口径见 NFR-002-001（M1）、NFR-003-001/002（B 站）、NFR-005-001/002（报告与知识库）。共享技术证据见 [Acceptance001](../acceptance/001-共享运行门槛验收.md)，不直接关闭 M1—M6 产品 AC。

# 热点舆情监控平台总需求

本文定义跨里程碑产品原则、用户与证据口径、来源和时间规则、共享 NFR 及里程碑边界。各能力的现行 BR/FR/AC 见 002—007；现行总设计为 [Design001](../design/001-热点舆情监控平台总体设计.md)，当前排期见 [当前工作](../../BACKLOG.md#当前工作)。

## 1. 需求结论与原则

研究者按主题设置关键词，查看各来源实际采到的帖子、评论和热榜条目，追溯原帖、观察时间、采集窗口与分析依据，并看清未采到、未采完和未分析的部分。只有逐来源、逐能力的真实采集和持续运行证据，才能支持“信息获取已验收”。

1. **先取得可信信息**：来源逐个准入、逐个验收；采集频率、回看窗口和来源更新节奏分别记录。回看和空结果不能证明完整覆盖。
2. **结果与证据分开**：已入库、已判断相关、覆盖已确认是不同状态；失败、部分结果、预算耗尽和分析积压可见。内容、评论父链、榜单快照均可追到来源与时间。
3. **数字由程序计算，Codex 只做判断与写作**：当前用本机 Codex app-server 判相关；后续报告中的数字、排序和引用由程序生成，模型不可用时可生成标明降级的模板版。
4. **后续结果独立验收**：日报、周报、知识库写入与问答、报告渠道投递属于后续独立能力；登录验证码邮件属于身份认证，独立实现和验收，不能被报告推送暂缓所阻塞。

### 产品定位与目标流程

HotKey 是面向普通用户的 ToC 信息监控产品，提供**配置关注方向 → 持续获取资料 → 阅读相关内容 → 发现具体事件 → 观察升温与进展 → 追溯原文及讨论**的流程。采集和任务控制是支撑能力，用户最终需要看懂值得关注的新信息、减少重复阅读，并知道判断依据。首页是公开信息入口，展示已许可发布的资讯、事件、专题与周报，并提供公开模型榜入口；公开阅读无需登录，创建个人关注、生成或发送报告及管理操作仍验证真实会话。事件应说明发生了什么、为何命中关注方向、热度来自哪些已采来源、评论讨论什么，以及证据和采样缺口。

方向和中英文实体/别名沿用监控主题及现有词组；来源的原生搜索与本地过滤分别说明。事件相似度只生成候选，不证明同一事件；不同版本发布及后续争议应保留事实差异。热度描述观测范围内的关注，评论结论描述明确样本，不称全网热度或全部用户意见。

完整领域合同见 [Design048](../design/048-完整业务设计.md)。各能力独立验收，获取短窗、持续窗口和质量标准保持各自范围。

### 核心链路与完整业务范围

完整业务包含信息获取、分析、事件、报告、知识库、渠道、公开分发、模型榜、公告与运营维护，具体需求见 [PRD046](046-完整业务需求.md)，架构见 Design048。每项功能保持独立验收；报告、vault与渠道不作为获取链路的技术前置。

核心链路先完成一个主题、HN与一榜的同库短窗演示，再扩四关键词来源、HN评论和六榜；之后独立验证M1/M2持续72小时、M3事件与正式质量。最小演示不代替扩围或产品验收，真实Codex/付费模型仍暂停，运行顺序与未通过条件见 BACKLOG。

## 2. 用户、场景与证据状态

用户可直接阅读公开资讯、专题、刊物和模型榜，个人主题、连接、任务和采集内容经真实登录访问。来源平台账号属于采集连接，报告接收方属于投递对象。来源软件许可证和平台数据授权单独准入；现有 MediaCrawler 本人 B 站试点仍受其许可和授权限制。账户及权限要求见下节。

### 2.1 ToC 用户登录需求

公开首页提供真实许可的信息阅读与SEO，账号密码、GitHub和邮箱验证码登录后进入个人工作区；账户与个人数据按以下要求验收。账号凭据完整找回/维护与多用户全业务产品AC仍按实际证据验收，不能以登录页存在关闭。历史业务分区仅经维护者显式映射到指定账号，首个公开注册者无权取得旧数据。
| FR | 功能 | AC 与完成条件 |
|---|---|---|
| FR-001-122 | GitHub 登录 | AC-001-123：经 GitHub OAuth App 用户授权取得稳定用户 ID 和已验证主邮箱，创建或读取正确的产品账户并建立会话；取消、过期或错误回调不登录。只读身份与邮箱，不请求仓库或组织权限。 |
| FR-001-123 | 邮箱验证码登录 | AC-001-124：发送并核验 6 位、5 分钟有效、单次使用的验证码；正常邮箱可首次注册及再次登录。发送冷却、频次、最多 5 次校验、过期和重放均有明确结果；真实邮件收取另留证据。 |
| FR-001-124 | 登录与注册共用入口 | AC-001-125：`/login` 提供邮箱或用户名密码、GitHub OAuth App 和邮箱验证码。首次 GitHub/邮箱验证成功即注册，同一已验证邮箱关联同一账户；邮箱验证后未设置密码的账户进入设置密码步骤，完成后返回安全原目标。已有 GitHub ID 绑定不可被另一个 GitHub 账号覆盖。密码登录只读取已有账户，不自动注册。移除单部署初始化、部署密钥及重复工作区身份接口。 |
| FR-001-125 | 多用户数据隔离 | AC-001-126：真实两个账户分别创建主题、连接、内容与任务，互不可见、不可修改；列表、详情、导出、预算及异步任务均按会话用户和资源归属检查，不依赖单账户假设。 |
| FR-001-126 | 会话与退出 | AC-001-127：所有登录方式共用可撤销的数据库会话与 Cookie；验证过期、CSRF、退出和页面会话失效。身份返回用户 ID、用户名、邮箱与过期时间；保留凭据版本用于密码变化后的会话失效，删除重复工作区包装。 |
| FR-001-127 | 邮箱或用户名密码与凭据维护 | AC-001-128：保留唯一用户名和密码哈希，同一账户可通过已验证邮箱或用户名加密码登录；已验证账户可设密、改密、找回密码，首次设置无需已有密码或填写自动生成的用户名。新近验证会话可首次设密，超过验证期限须重新核验绑定邮箱；已有密码时须当前密码或绑定用户和凭据更新用途的邮箱验证码。密码变化撤销全部旧会话并为当前已验证操作建立新会话；错误账号、无密码账户和错误密码使用同一公开结果，限流与 CSRF 可验证。 |
| FR-001-128 | 无感登录 | AC-001-129：有效 Cookie 下刷新、再次打开页面或重开浏览器可恢复同一用户，访问 `/login` 自动跳产品页；默认固定有效期 12 小时。会话过期、撤销、主动退出或密码变化后须重新验证；网络失败提供重试，不误判已退出，不在客户端保存密码或会话令牌。 |

账户设置采用左右布局：左侧展示本人头像、用户名、邮箱和验证状态，支持 JPG、PNG、WebP 图片上传（最大 2 MB）；右侧以基本资料、登录安全切换用户名编辑及独立改密操作。头像规范化后持久保存，更新和刷新后资料栏与顶部账户菜单一致；非法图片、失败及重复上传有明确结果，不能覆盖原有效头像。用户名修改不要求同时改密码；密码继续按 AC-001-128 核验身份与轮换会话。窄屏依次显示资料及设置，保留键盘、焦点和未提交草稿。

账户访问与数据分区合同见 [Design001 §9.2](../design/001-热点舆情监控平台总体设计.md#92-公开欢迎页登录与个人数据访问)。真实集成和数据保留独立验证，不增加组织、租户、角色矩阵、邀请或通用身份平台。

### 2.2 使用场景

| 场景 | 当前或后续的用户结果 |
|---|---|
| 日常查看 | 打开主题，查看最近各来源采到的帖子、评论、热榜命中和 Codex 相关性；能点回原帖，知道哪些内容尚待分析 |
| 调整关注方向 | 用“大模型、AI Agent、开源模型”等方向及用户填写的实体/别名调整词组，保存前查看已有样本的命中原因和来源执行方式；无可用样本时明确提示 |
| 发现事件与进展（M3 后续） | 按关注方向查看具体事件、首次已知时间、最新进展、来源构成及升温依据；打开代表作品和评论，核对覆盖与人工修订 |
| 理解讨论（M4 后续） | 查看已采样评论的问题、观点和引用，区分实际体验、支持、质疑及补充证据；缺少有效评论时显示证据不足 |
| 核对覆盖 | 按来源、能力、时间窗查看到期、尝试、请求与页数、停止原因、入库/去重、预算和缺口；空榜、失败与部分结果有不同状态 |
| 试用本人账号来源 | 低频启用 B 站试点；遇验证、登录失效或访问频繁立即停止，由本人检查并人工恢复 |
| 阅读与追查（后续） | 分别查看日报、周报；从报告进入原帖或已存在的 Obsidian 笔记，在知识库中浏览、检索、提问并查看出处 |
| 接收提醒（后续） | 在推送能力单独启用并验收后收取邮件或飞书报告；突发告警更晚交付 |

### 证据等级

代码实现、受控测试、真实运行和产品验收分别判断。受控测试验证状态机、边界与故障；真实运行验证实际来源、外部依赖和持久结果；产品验收按各AC的样本、连续窗口及用户核对口径判断。AC表中所列等级均须满足，较低等级不能替代较高等级，代码实现本身不属于产品通过证据；状态见BACKLOG，实际证据见Acceptance。

## 4. 来源与时间范围

每个来源按支持的**搜索、帖子、评论、热榜**能力单独验收。预设已应用、RSS 可解析、诊断探针或单个成功 Job 只说明相应步骤，不代表来源接入完成。

| 范围 | 来源键与实际入口 | 能力与限制 | 里程碑 |
|---|---|---|---|
| 四个关键词来源 | `hackernews`：Algolia 公开 API | 搜索、帖子；HN 评论及楼中楼用于父链和重放验收 | M1 |
| 四个关键词来源 | `google_news`：Google News 搜索 RSS | 搜索、帖子 | M1 |
| 四个关键词来源 | `news_search`：本机 SearXNG `127.0.0.1:8888`，`duckduckgo news` 引擎 | 搜索、帖子；发布时间以来源实际字段为准 | M1 |
| 四个关键词来源 | `rss_36kr`：本机 RSSHub `127.0.0.1:1200/36kr/newsflashes` | 36Kr 快讯按主题过滤；不是 36Kr 原站 feed，也不同于热榜 `/36kr/hot-list` | M1 |
| 六个公开热榜 | 微博、百度、知乎、B 站热门、36Kr、澎湃；均经本机 RSSHub，路由见 FR-002-006 | 来源级快照、排名变化、主题命中、内容入库和 Codex 相关性 | M1 |
| 本人账号试点 | B 站：固定补丁版本的 MediaCrawler 宿主机子进程 + 独立 CDP 浏览器资料 | 搜索、帖子；同轮缓存的一级评论每帖 ≤ 20，不采楼中楼；真实采集验收前不宣称接入完成 | M2 |
| 后续逐项准入 | 微博、小红书、抖音、知乎登录能力、微信公众号；Reddit 官方 OAuth；X 官方 API | 各自单独确定许可、凭据、频率、分页和失败状态；X 凭据与月度上限未确认前不发真实请求 | M6 或另定 |

**三种时间口径**：主题请求频率默认 30 分钟、最短 10 分钟；来源预设另有最短间隔、静默时段和预算，实际尝试取更保守节奏。`HOTKEY_COLLECTION_LOOKBACK_SECONDS` 默认向前回看 24 小时、上限 7 天，决定当前任务查询窗口；来源自身发布时间、RSS 缓存时间和榜单更新时间由来源决定。重复回看按来源身份去重，但**24 小时回看不等于历史完整覆盖或缺口已补**；可信尾段与分页边界不足时仍标部分覆盖。有发布时间的内容分别记录发布时间与首次发现时间；无发布时间的内容保留空发布时间，以首次发现时间作统计依据并单列，不伪造发布时间。热榜另按默认1800秒、可配置的独立观察桶运行，M1验收窗口按PRD002冻结实际间隔。

## 5. 共享非功能需求

| ID | 要求 | 验收口径 |
|---|---|---|
| NFR-001-101 | 可追溯 | 内容、评论、热榜命中和分析可定位到来源、原帖、采集/观察时间及版本；报告每个数字、观点可追到冻结输入并可复算 |
| NFR-001-102 | 数据正确 | 同来源同原生 ID 唯一，评论父链正确；缺失与 0 不混淆，时间存 UTC、按 Asia/Shanghai 展示；发布时间、发现时间、热榜观察时间分离 |
| NFR-001-103 | 时效 | M1 在正常可运行时段，以来源计划到期至对应 Job 结束计，四个关键词来源和六榜逐来源的中位延迟 ≤ 5 分钟；Codex 可用时，新入库且需分析的内容在入库后 60 分钟内取得有效相关性结论的比例 ≥ 95%。来源静默、来源限流延后和 Codex 限流时段分别记录并从相应达标率样本中排除；正常时段未受理或未结束的到期窗口记为超时，待分析与失败计入相关性分母，不得静默排除。日报在获准渠道的送达目标为设定时间后 15 分钟内，周报为周一 09:15 前；报告生成与渠道送达分别按 M4/M5 验收 |
| NFR-001-104 | 可靠执行 | 重复调度、重试、进程重启或消息重放不重复内容、Job 与投递，不静默丢任务；失败和部分结果保留原时间窗证据 |
| NFR-001-105 | 故障隔离 | 单来源、单页或 Codex 故障不抹掉已入库内容；未完成覆盖和分析积压可见；后续报告标明缺失或降级 |
| NFR-001-106 | 资源控制 | 来源频次、词数、条数、请求、并发和模型调用经来源预设及持久预算账本设硬上限；限流后按规则延后或停用，不发起付费模型请求，不以重试返还已用预算 |
| NFR-001-107 | 安全 | 只采公开或本人授权数据；凭据与浏览器资料不入前端、数据库、日志、Git、容器或模型输入；外部正文按不可信内容处理，请求及重定向限白名单，Codex 子进程使用最小环境与空目录 |
| NFR-001-108 | 分析质量 | 人工抽检每主题 100 条，相关性准确率目标 ≥ 90%、情感准确率目标 ≥ 80%；异常标注不计作完成结果，抽检未做前不得宣布质量达标 |
| NFR-001-109 | 知识库安全写入 | Obsidian 仅写 `HotKey/` 管理区块、原子替换、保留用户区块；vault 不可写不阻断信息获取或报告生成 |
| NFR-001-110 | 本人账号风控 | B 站等本人账号来源以不触发风控为硬上限；遇验证码、滑块、扫码/登录失效或访问频繁立即停该来源及后续调度，记录认证或限流原因，不破解、不自动换号或绕过、不自动恢复；必须由本人核查后人工重启。频率、条数、请求和并发按来源配置 |
| NFR-001-111 | 采集可观测 | 来源 × 能力 × 时间窗的到期、请求/页数、停止原因、入库/去重、分析积压/失败/标注异常、预算和缺口可核对；空结果、截断、失败、未分析有不同状态，回看不当作覆盖确认 |
| NFR-001-112 | 重试时间与计量 | 保留 Job 首次启动时间，每次尝试另记；自动重试和限流重排沿用原采集预算剩余量，用户手动重试在下次实际领取时开新采集预算周期，但不重置每日/全局预算或历史耗时；重复点击幂等 |
| NFR-001-113 | 登录安全与隐私 | 密码、验证码、PKCE verifier 与 GitHub 访问令牌不得进入日志或 API 响应；code/state 仅用于 OAuth 协议跳转，不进入最终页面跳转参数、错误消息或访问日志。密码仅以 Argon2 哈希保存，访问令牌不持久保存。验证码和密码登录按账户标识及可信 IP 限流，Redis 不可用时拒绝继续验证；业务会话和用户归属仍由 PostgreSQL 保存。 |

共享时效口径分别见 NFR-002-001（M1）、NFR-003-002（B站）与 NFR-005-001（报告），风控与知识库写入分别见 NFR-003-001、NFR-005-002。

共享NFR的实现维护规范见 [PROJECT 文档维护](../../PROJECT.md#文档维护)，共享技术证据见 [Acceptance001](../acceptance/001-共享运行门槛验收.md)。同版本恢复、证据保留/删除/谱系与 `lifecycle cleanup-once` 合同见 Design001；HTTP契约、OpenAPI→客户端及CI归日常维护。通用网页/Browser 准入遵守 Design001；这些技术证据均不直接关闭M1—M6产品AC。

# Plan 031：来源调度与手动采集入口

## 交付与边界

交付可从主题页面立即运行、暂停和恢复的采集入口，以及消费版本化来源预设的独立调度器。承接 FR-002-002、NFR-001-104/106/111，贡献 AC-002-002/006。现有 `worker/scheduler.py` 已受理搜索，`POST /api/jobs` 当前以网页任务为主，不能据此认定主题搜索有完整手动入口。重试时钟属于 Plan 032；真实来源适配分别属于 007、035—038。

### 本卡冻结的实现合同

- 后端文件：`monitors/runs.py` 负责手动受理事务，`monitors/schemas.py` 定义输入/逐来源结果，`api/routers/monitor_topics.py` 与 `api/dependencies.py` 装配端点；`core/errors.py` 和 `api/exception_handlers.py` 登记所选来源不属于主题的 422 错误。`content/discovery.py` 复用单次关键词 Job 规划，`connections/services.py` 提供到期时刻的非秘密来源策略快照，`worker/scheduler.py` 编排到期事实、Job/Outbox 与调度游标，`monitors/services.py` 只负责主题/调度行。无新表；Plan 033 的 `collection_due_windows` 是到期事实源。
- 手动请求仅接收当前主题已选来源；暂停或归档不新受理。服务以请求 `operation_id` 串行，按当前主题及来源版本冻结查询窗口、执行策略和 Job 输入；同 ID 同来源集合返回既有结果，改来源集合返回 409。部分来源不可受理时，202 逐来源返回 Job ID 或稳定跳过原因；全部不可受理时 409。前端保留网络结果未确定时的操作 ID，避免点击重试创建第二次请求。
- 调度到期点固定为 `monitor_schedules.next_run_at`，当前主题间隔与来源最短间隔取较大值；到期时刻、主题版本及连接版本参与确定性 Job 操作 ID。调度器以 `FOR UPDATE SKIP LOCKED` 领取行；恢复按相同到期相位逐点写漏窗，旧点记 `missed`，最新点受理或显式 `skipped`。同一事务内写到期事实、Job、Outbox、`last_job_id` 和下一到期点；来源当前停用、静默和预算不足保留原因。已受理 Job 仍由现有连接版本围栏在执行时判定，不能按新配置重释。
- 前端专属 `TopicRunActions` 归 `monitors/[topicId]/components/`，只在主题编辑页使用；数据来自生成的 `runMonitorTopic`。覆盖未选来源、暂停、提交中、部分受理、全部未受理、重试、会话失效及任务详情跳转。生成文件为 `frontend/src/api/jiankongzhuti.ts` 与 `frontend/src/api/typings.d.ts`，只能由运行时 OpenAPI 生成。
- 验证文件固定为 `backend/tests/unit/test_scheduler.py`、`backend/tests/integration/test_topic_runs.py` 和页面专属 `topic-run-actions.test.tsx`；真实 PostgreSQL 新空库与 Kafka/浏览器证据分层记录，不用跳过的集成测试宣称通过。

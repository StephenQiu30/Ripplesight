# Plan 006：逐来源时效与分母统计

2026-09-28 技术进度：采集时效与热榜预期桶已接入只读 API/CLI，见 Acceptance 002 EV-002-033；首次有效结论时间见 EV-002-034，主题启用/暂停历史事实见 EV-002-035，分析扫描的已选来源/同版本热榜命中资格见 EV-002-036，提示词首次启用时间见 EV-002-037，逐身份只读候选起点见 EV-002-038。EV-002-045 将热榜缺失的预期到期桶计入延迟分母，公式升为 `metric_version=collection-v2`；v1 证据保留原口径。EV-002-046 导出当前提示词逐身份候选账本，EV-002-047 保存调度启停/心跳事实，EV-002-048 将已证实的启停区间接入账本，公式升为 `analysis-candidate-v2`。EV-002-049 枚举有持久事实的历史提示词版本，逐版本核对候选并将缺事实旧版列未知，公式升为 `analysis-candidate-v3`。`analysis_status=not_computable` 和热榜 `phase_verified=false` 仍为明确未验状态。分析还需核对实际 Codex 限流影响区间；热榜还需在观察窗起点冻结间隔/相位和配置版本，按 Plan009 对账。本 Plan 与 AC 尚不能关闭。

## 计算与接口合同

新增 `backend/app/jobs/metrics.py`；修改 `jobs/schemas.py`、`jobs/coverage.py`、`analysis/services.py`、`api/dependencies.py` 和 `api/routers/collection_coverage.py`。提供 GET `/api/collection-coverage/metrics`（getCollectionCoverageMetrics，静态路由在window_id路由之前注册），沿用004筛选/权限，返回metric_version、截止时间、分子分母、排除窗及逐来源明细；页面属于034。API 依赖将运行中应用配置的热榜间隔传给服务，CLI 使用同一配置对象；CLI在 `backend/app/cli/jobs.py` 加 `jobs coverage-metrics`，调用同一服务，不复制计算逻辑。

`SPEC-006-OBS-001`：窗口取due_at∈[start,end)，采集延迟=finished_at−due_at，单位秒。到截止仍未受理/未结束的正常到期点记超时；精确中位数无法确定时返回median=null、median_lower_bound_seconds与timeout_count，只有下界已超目标可明确失败，其余保持不可判定，不能从中位数样本删除超时后宣布达标。最终有充分结果才按PRD判定≤300秒（M2≤900秒）。

`collection-v2` 热榜修正：以当前间隔/UTC 相位枚举截至 `cutoff_at` 的预期桶；未记录的桶作为无结束时间的样本，加入 `due_count`、`sample_count`、`timeout_count` 和删失中位数，已记录但不在预期相位上的异常桶保留原样本。由于当前配置不能证明 T0 相位，热榜有样本时 `result=indeterminate`，`phase_verified=false`；数值只供原始 ID 核对。关键词等非热榜仍按持久到期点计算。Plan009 冻结 T0 间隔、相位及配置版本后再给出产品结论；不得将 v1 和 v2 数值混作同一证据。

`SPEC-006-OBS-002`：按来源和 `(content_version_id,topic_id,topic_rule_version,prompt_version)` 建需分析集合，起点为该分析需要产生的入库/发现时间；旧内容首次加入新主题不能拿旧全局入库时刻倒算。已到60分钟观察期限的样本计分母，首次有效结论≤3600秒计分子；未成熟样本单列pending_observation，不宣称通过，009结束后至少等尾部60分钟。失败/invalid保留分母。Codex限流须有实际受影响样本与时间区间证据，不能按整个自然日删除样本。

首次结论事实由 `analysis` 领域持有：修改 `backend/database/schema.sql`、`backend/app/analysis/models.py`、`backend/app/analysis/services.py`，增加可空 `first_valid_at TIMESTAMPTZ`，并约束它与 `result_state='valid'` 同时出现。首次有效写入时取该结果的时间；重复有效结果或之后的失败/invalid诊断不改写。直接插入有效行的受控 fixture 也必须给该时间。先用隔离 PostgreSQL 证明旧 Schema 缺列，再用全新空库复测。该单项只提供必要原始事实，不变更现有 `analysis_status=not_computable`；逐主题需分析起点和实际限流区间尚未有完整事实时不能输出分析比率。

主题启用历史由 `monitors` 领域持有：修改 `backend/database/schema.sql`、`backend/app/monitors/models.py`、`backend/app/monitors/services.py`、`backend/app/db/metadata.py` 和 `backend/tests/integration/test_monitor_topics.py`，新增 `monitor_topic_status_events`。创建/克隆时写初始 paused，只有状态变化才写后续 active/paused/archived；移除全部来源的自动暂停须同事务记录。事件按 owner/topic/递增序号与时间可读，含当时规则版本与原因；规则变动仍查不可变版本行。旧 Schema 先因缺表失败，全新隔离 PostgreSQL 再验证幂等、失败回滚和独立进程读取。该事实仍不单独构成分析分母：内容版本的首次入库/发现、提示词版本的生效、逐主题匹配和 Codex 限流样本还需合并；缺证据时 `analysis_status` 继续为 `not_computable`。

提示词首次启用事实由 `analysis` 领域持有：修改 `backend/database/schema.sql`、`backend/app/analysis/models.py`、`backend/app/analysis/services.py`、`backend/app/db/metadata.py`、`backend/app/worker/scheduler.py` 和备份清单测试，新增全局 `analysis_prompt_activations`。调度进程仅在 `HOTKEY_AI_ENABLED=true` 时、扫描前写入当前提示词版本和启动 UTC 时间；同版本重复启动不覆盖，新版本独立记录。旧 Schema 先因缺表失败，再用新空库验证关闭时零写入、并发/重复启用、事务回滚与新进程读回。该表不证明 Codex 真正可用，不按缺失历史补写；逐身份需分析起点与实际限流区间未齐时分析比率仍为 `not_computable`。

提示词启停运行事实切片：新增全局 `analysis_prompt_runtime_sessions`，不替代首次启用表。修改 `backend/database/schema.sql`、`backend/app/analysis/models.py`、`backend/app/db/metadata.py`、`backend/app/analysis/services.py`、`backend/app/worker/scheduler.py` 与 `backend/tests/integration/test_backup_restore.py`；新增 `backend/tests/integration/test_analysis_prompt_runtime.py`，扩展现有激活测试。每次调度启动以新运行 UUID 原子写入静态启用状态和首次启用事实；每轮扫描结束提交最后确认时间，写失败时停止调度；正常退出关闭会话，异常退出只信最后心跳。重复同 UUID/配置启动与心跳幂等，冲突重试拒绝；旧 Schema 缺表先红，全新隔离 PostgreSQL 验证回滚、启停、重启/进程读回与约束。并发启用/关闭冲突、最后心跳后的空档、无历史会话均保留未知。会话只给配置时间事实，不证明 Codex 可用/限流，不改变本次只读候选账本的 `analysis-candidate-v1` 或 `analysis_status=not_computable`；后续结合历史提示词身份与实际限流样本再计算比例。

运行会话进入候选账本的 v2 切片：新增纯区间计算 `backend/app/analysis/runtime.py` 与 `backend/tests/unit/test_analysis_runtime.py`；修改 `backend/app/analysis/services.py`、`backend/app/analysis/schemas.py`，扩展 `backend/tests/integration/test_analysis_need_origin.py`、`test_analysis_need_ledger.py`。账本在只读快照中一次读取全局会话，单身份投影共用该集合。按 `[started_at,last_seen_at)` 确认静态配置区间，当前提示词以外的会话属于该提示词关闭态；并发不同配置、首个候选之前的无会话空档、旧历史缺失均列 unknown。只有在最早可分析时段之前的配置状态完整且一致，才确定起点；导出支撑判断的运行 UUID。`as_of` 为半开上界，观察窗仍 `[start,end)`，公式升 `analysis-candidate-v2` 并保留 v1 证据。先以旧投影错误地把停用时段算候选的受控用例留红，再验证关闭→恢复、崩溃空档、配置冲突、其他提示词、零长度心跳、首个候选后的空档、窗界与独立 CLI 读回。仍不接入正式 60 分钟比例；实际 Codex 限流样本与旧提示词版本留待后续核对。

历史提示词逐身份账本 v3 切片：修改 `backend/app/analysis/services.py`、`schemas.py`，扩展 `backend/tests/integration/test_analysis_need_origin.py`、`test_analysis_need_ledger.py`。一次只读快照枚举窗口前已激活的全局提示词、窗口前启用的运行会话版本、本 owner 截止时可见的标注与分析 Job 版本以及当前代码版本；每个规则/内容版本按提示词分别求起点、读对应标注，排序及公式版本一起升级。旧版本有激活与连续运行事实时可形成候选；只有历史标注或 Job 而缺事实时必须保留 unknown，不从结果倒填激活时刻。用隔离 PostgreSQL 先证实旧实现漏掉旧版本，再验证切换前后双候选、旧标注与未完成 Job 留未知、CLI 读回及全量回归。无 DDL/API/前端变化；真实 Codex 可用性和限流排除仍缺，分析比率保持不可计算。

## 当前受控进展与待验边界

2026-09-27 在独立 worktree 核对 PRD/Design 002、Acceptance 002 所引历史 046 S03、Plan 031/033、`connections/presets.py` 的 HN 搜索/评论能力与来源日预算，以及 `sources/adapters/hackernews.py`、`content/discovery.py`、`content/discovery_execution.py`、`jobs/{execution,services}.py`。隔离库应用 HN 预设取得连接版本 1，并另设全局网络请求上限；Job 固定主题版本 1、连接版本 1、查询词与 UTC 24 小时窗口。Algolia `objectID` 保留原字符串，源发布时间未知时留 null、用发现时间记录；每页先经准入和主题规则，再于同一事务提交内容/发现、覆盖检查点和预算结算。只在可信尾段确认窗口，评论归 038。

适配器不再把外部故事 URL 伪作正文；缺 `nbPages`/页数不一致不声明已到尾页，50 页上限遇真实后续页返回 partial。`test_keyword_search_adapters.py` 的三个新用例先 Red 后 Green；后续加入越界重定向与零预算请求断言。`test_keyword_discovery.py` 的 HN MockTransport 两页集成用例在真实隔离 PostgreSQL 验证第一页两个同标题不同 ID 帖子（其中一个无发布时间/互动量）、第二页 429 后内容仍在、覆盖 partial、两级预算请求账本 2 次请求/4 条策略预留，且连接禁用后无请求。此进展覆盖 CHK-007-001/002 的部分场景及 CHK-007-003；并发重复消息、旧租约、真实 Worker 进程重启和真实 HN 原帖仍缺专项证据，CHK-007-004 未完成，Plan 保持 `in_progress`。见 EV-002-019/020。

EV-002-021 增加独立 Kafka 4.1.2 的受控 HN Job 投递/重投：Outbox 到测试 Topic，第一次由关键词处理器在 PostgreSQL 持久化，故意不提交 offset；新建 Consumer 和处理器实例收到相同 offset 后重放，只保留一个内容、一次发现/观察/网络请求及一条处理记录，随后提交 offset。此证据覆盖消息持久化与重复投递，尚未重启真实 Worker 进程，也未向真实 HN 发请求。CHK-007-004/G5 继续等待获准主题的真实帖子、原帖打开、重启及同库对账。

EV-002-022 使用新的隔离 PostgreSQL 17/Kafka 4.1.2，对同一测试加显式开关 `HOTKEY_TEST_LIVE_HN=1`，经预算准入向公开 HN Algolia 发送一次 `AI` 搜索请求；Outbox 投递后故意不提交 Consumer offset，处理器持久化，再由新 Consumer 和处理器重放同一 offset，最后提交。两次独立运行分别入库原生 ID `49860178`/`49860188` 和 `49860188`；两个不同 ID 均在 HN 原帖页打开核对。最终运行确认连接版本 1、请求 1、页 1、内容/发现/观察各 1、两级预算预留 2 条且实扣各 1、网络尝试和处理消息各 1；消息重投没有再次请求。仅抓第一页，覆盖 `partial`，不声称固定窗口完整。现仍是测试中直接受理 Job 和进程内重建处理器，非 031 入口和真实 Worker 进程重启，CHK-007-004/G5 保持未完成。

EV-002-023 将真实/受控 HN Kafka 用例都改为由 `MonitorTopicRunService` 受理活跃主题。真实分支的首次 Red 发现 031 所加 `manual_*` scope 字段被关键词执行器的严格字段集合拒绝，Job 在外发前以 `search_scope_invalid` 失败。执行器现仅接受原有字段集合或完整的四个手动字段，并校验请求 ID、查询索引、来源列表和手动入口。受控分支因此成为无需公网即可回归的 031→执行器→Kafka 测试。真实 `AI` 查询经现行 HN 预设发送 2 次请求、存 118 条内容/发现/观察，两级预算实扣共 4；同 offset 重投后仍只有一条处理消息且无重复网络尝试。尾页虽返回但缺固定时间窗终端证据，覆盖为 `partial/unverified_terminal`；这不是完整覆盖。真实 Worker 进程未重启，未完成消息 offset 阻塞未验证。

EV-002-024 将受控 HN Kafka 用例再加一个独立 OS 进程分支：两个进程各自创建数据库引擎、Consumer 与项目的 `create_job_message_handler`。第一个完成内容持久化后关闭 Consumer，不提交 offset 并退出；第二个进程在同组收到相同 offset，经 `process_message` 去重并提交，仍只有一条内容、发现、观察、请求尝试和处理记录。接着经 031 受理第二个 Job，先由测试持有其有效租约；第三个进程收到下一条消息后获得 `MessageDeferredError`，未提交该 offset，数据库没有处理记录。此分支覆盖跨 OS 进程重建处理器及连续 offset 约束，但用的是受控 Algolia 响应、测试组装的 Worker 消费函数，尚未启动生产 `python -m worker` 或其 `JobProcessSupervisor`，因此 G5 保持未完成。

EV-002-025 在同一隔离 PostgreSQL/Kafka 上显式开启 `HOTKEY_TEST_LIVE_HN=1` 与 `HOTKEY_TEST_PRODUCTION_WORKER=1`，仅在生产 Job Topic 尚不存在的独立 broker 运行。031 手动主题服务创建真实 HN Job，Outbox 发布后由生产 `python -m worker` 与 `JobProcessSupervisor` 子进程执行真实 `AI` 搜索；最终运行请求 2 页、入库 121 个不同内容/发现/观察，连接版本 1、两级预算实际耗用共 4，覆盖 `partial/unverified_terminal`。停止 Worker 后测试把其专属 Consumer 组 offset 回拨至已完成消息，再启动新的生产 Worker；组 offset 回到下一位置，而内容、网络尝试和处理记录计数不变。第二个 Job 预先持有有效租约，生产 Worker 日志记录 `message_processing_deferred`，数据库请求仍为 0、处理记录为 0，组 offset 停在该消息之前。入库样本 `49849546` 的稳定 HN 原帖在浏览器打开核对。此回拨是可复现的重投故障注入，不宣称捕获到自然崩溃窗口；父级 AC-002-001 的评论父链、AC-002-002 的四来源 72 小时和 AC-002-004 的其他来源仍未完成。

EV-002-026 补齐 CHK-007-001/002：适配器单测固定 UTC 24 小时上下界，检查 Algolia `numericFilters`、同标题不同 ID 两页顺序、下一页 token 和可信末页；既有单测覆盖缺正文/发布时间/互动量。HN 隔离库用例扩展第 1 页为 7 个候选，窗口起点恰好命中、终点恰好等于上界和早于下界的帖子分别核对，主题不匹配与 `sponsored` 排除词均不入库；最终仅 3 个内容保存，7 个观察候选计数和第二页 429 的两级预算实扣一致。首次页写入后旧 epoch 的租约无法将部分 Job 写成成功；另一个 Job 在内容写入后人为中断检查点事务，内容/发现/检查点全部回滚，而已发网络请求及两级预算按失败计量。Kafka 受控并发分支在首次请求未结束时把同一消息交给第二处理器，第二处理器收到延期信号；后续重投后只有一次来源请求和一条 Job attempt。单测 11 passed，HN 指定集成 4 passed/2 skipped，隔离 PostgreSQL/Kafka 全量 823 passed/15 skipped；Ruff、格式、`mypy app` 均通过。G2 的逐场景实施前 Red 历史仍缺，保持未完成。

EV-002-027 将 HN 从手动受理扩展到真实调度窗：受控测试先复现定时 Job 的 `search_scope_invalid`，原因是执行器漏掉调度追加的 `schedule_key/due_at`；现在识别这两个定时字段的完整组合，并验证 UUID、UTC 到期点等于固定窗口终点。隔离 PostgreSQL 中调度、真实 Algolia 搜索和覆盖 API 同窗核对通过；真实窗口仍为 `partial/unverified_terminal`。这项修复不改变评论或四来源连续验收结论。

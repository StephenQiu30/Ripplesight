### CORE-01 独立账本与恢复屏障切片

方案分为R1账本输入验证与隔离重放复演、R2在线独立拒绝账本、R3身份/附件及全入口屏障、R4追赶与切换。先执行R1；它消费固定账本样本，不接管在线删除，不产生开放许可。R2～R4的决定性输入未就绪时不能用R1结果代替它们。完整目标见[设计10恢复方案](../design/10-权限与数据生命周期.md#独立账本与恢复方案)。RPO/RTO及实际保留期仍由容量、许可和演练冻结，不由agent编造。

| 合同 | 实施时必须证明的结果 |
|---|---|
| 独立性与最小化 | 账本不随旧业务备份回退，不被资源FK级联删除；只保留设计允许的最小标识/原因/时间/operation及期限，不存正文/验证码/凭据 |
| 账本保留与备份年龄 | 账本/tombstone覆盖全部仍允许恢复的一致性点；合法清理或截断后，缺完整删除证明的更旧备份拒绝开放，不以“保留期已到”允许复活正文 |
| 写入与失败 | 明确何时删除/撤权生效、持久确认及幂等；覆盖账本写失败、业务提交失败、进程中断和重试，不以双存储顺序调用假装原子 |
| 恢复输入 | 备份身份/一致性点、schema版本、独立账本有效范围及重放高水位都可核对；时间戳本身不充当连续完整性证明 |
| 恢复状态 | 隔离→基础恢复→账本校验→幂等重放→派生物/附件及身份失效复核→允许开放；缺失、损坏、断档、重放或复核失败一律保持隔离 |
| 全入口隔离 | API、Worker、Scheduler、队列/outbox、模型/通知、对象文件直出和缓存均受围栏约束；重放完成前旧任务不得执行或外发，预签名附件不能旁路 |
| 当前事实与追赶 | 恢复期间新发生的删除/撤权纳入最终追赶及切换屏障；旧政策不得覆盖当前更严格政策；明确切换期间写入围栏 |
| 身份与消费者 | 旧会话/未完成挑战不得因恢复重新生效；旧密码/第三方绑定/已删除或停用账户/凭据版本不得从旧备份重新获得授权；正文、标题、计数、修订、媒体、缓存/索引、报告、事件、导出及公开投影按当前合同重验 |
| 回退 | 回退仍受独立账本和读取屏障约束，不回退到“恢复成功即可开放”的错误方案；仅对明确授权目标操作 |

#### R1 账本输入验证与隔离重放复演

**范围与就绪**：覆盖FR/AC/US-10-01/02恢复反例及T-10-03/04的明确子集。实现evidence共用账本交换合同、事务内拒读重放及backups临时恢复/CLI消费者；本切片不更改业务DDL，不增加长期正文库。读入快照是独立账本的交换格式，不是已部署的账本权威库。独立审查通过并以Git提交固定本SPEC后开始代码；人工可信checkpoint和固定快照可作为受控样本，不据此批准生产来源。

**独立账本及后续写入协议**：目标选择独立PostgreSQL实例/专库、独立凭据及备份生命周期，由单一账本事务原子分配连续sequence、追加事件、更新head和检查operation唯一。它不能包含业务资源FK，也不能随业务dump恢复。同机专库只能证明独立回退域；硬件/管理故障域、账本自身备份恢复及部署凭据在R2准入时验证。R1不建立该权威库或启用写入，不把JSON样本当作持久确认。R2须账本先持久化保守deny，并让所有相应在线读取/采集授权消费此deny后才回写业务投影；业务失败或未知不能撤销deny，只能按相同operation重试。仅业务outbox或两次顺序提交不构成完成。原生身份/来源/账户级事件另冻结规范化版本，R1不猜测映射。

**R1交换数据合同**（所有模型拒绝额外字段，未知版本/动作/原因拒绝）：

| 输入 | 固定字段与约束 |
|---|---|
| snapshot | format_version=`ripplesight.recovery-ledger.v1`；ledger_id UUID；epoch正整数；normalization_version=`resource_uuid.v1`；entries为完整的1..N事件序列，最大10000项 |
| entry | sequence正整数；operation_id、owner_id、resource_id均为UUID；action=`deny_resource`；resource_type匹配`[a-z][a-z0-9_]{0,63}`；reason为user_request/retention_expired/authorization_revoked/source_deleted；occurred_at为有时区时间；previous_digest、digest为小写64位SHA256 |
| trusted checkpoint | format_version=`ripplesight.recovery-checkpoint.v1`；ledger_id/epoch/normalization_version；backup_id、archive_sha256、schema_sha256精确绑定本次备份；head_sequence非负且<=10000；head_digest为可信当前水位 |

文件最多16MiB，必须是600普通文件，拒绝符号链接；checkpoint通过调用者的独立可信通道提供，CLI从指定大写环境变量读取JSON，不从candidate或snapshot复制head，也不把秘密或完整事件输出到日志。checkpoint文件/环境的真实性不是链摘要能证明的，R1人工输入仅用于复演，不具备上线授权效力。epoch由账本权威产生，不接受业务备份回退的epoch。

规范化：UUID输出标准小写带连字符文本；时间转UTC，固定6位微秒并以Z结尾；JSON键排序、ASCII转义、无空格分隔。genesis=SHA256(`ripplesight.recovery.genesis.v1`+NUL+规范化{ledger_id,epoch,normalization_version})；entry.digest=SHA256(`ripplesight.recovery.entry.v1`+NUL+规范化该entry除digest外的所有字段)。首条previous_digest=genesis，后续=前条digest。空序列head=genesis。验证完整序列、每个摘要、同owner的operation唯一及最终可信head；即使重复operation内容相同也不能追加第二条，生产者幂等返回原收据。仅比较时间戳、snapshot自报head或内部链完整均不通过。R1只接受从genesis完整重放，不支持截断/归档或增量游标；R2合法清理须提高最旧可恢复边界，没有覆盖证明的旧备份不得开放。

**隔离与重放**：

1. 先验证candidate与完整快照/checkpoint绑定；缺失、畸形、尾部截断、断号、冲突、错备份/epoch/摘要全部在CREATE前拒绝。R1拒绝所有带证据对象inventory的候选，避免将已撤回附件恢复到当前bucket；附件隔离属R3。
2. 只创建随机新临时库；CREATE时ALLOW_CONNECTIONS=false，撤销PUBLIC的数据库权限后才允许维护连接。非测试复演要求来源与维护角色不同，来源角色不得是superuser或维护角色成员；普通业务角色不得具有CONNECT。测试只使用hotkey_test_*和拥有的临时角色。数据库owner/superuser属于受信维护边界，不能据此声称抵御管理员。
3. 不注册API/Worker/Scheduler，不消费Kafka/outbox，不运行模型、通知、清理或对象适配器；CLI不输出临时库连接信息，不提供promotion/切换命令。旧密码/绑定/会话/挑战和旧任务即使存在于临时库，也没有业务入口。R1不能证明将来真实服务的全入口屏障。
4. 基础恢复先核对原manifest完整性及表计数，然后在一个PG事务重放全部事件（包含checkpoint之前的事件，不能漏掉账本已写而业务未提交的intent）。通过evidence公开合同按owner/type/id精确找资源并锁定；先核对operation是否已指向另一资源，再处理目标缺失或已有拒读的幂等返回，不能用目标缺失跳过冲突。新记录使用原operation/reason/time生成拒读和待处理清理回执；即使没有cleanup_targets也保持pending，不能把“未评估/未执行清理”记成物理完成。既有完成回执不据此新增擦除证据。物理清理不在复演执行，不声称正文或派生物已被抹除。
5. 每个匹配资源重放后核对生命周期可读查询不可得；任一步/提交失败整批回滚，不返回成功水位。重复运行同一批不增加拒读记录。未匹配资源仅表示此恢复快照没有相同身份，不能证明原生身份重采阻断。
6. 成功回执仅包含backup_id、验证范围、指定ledger/epoch/head、匹配资源数及用时；replay_verified只指该有限批次，service_open_permitted固定false。普通verify-restore与maintenance的完整性校验也必须明确integrity_verified和service_open_permitted=false，不再把完整性成功写成泛化restore_verified=true。
7. 成败都关闭连接并删除本次实际创建的临时库；删除失败作为失败返回，不能宣称已清理。R1不存在持久恢复目标或解除隔离动作；中断后遗留目标仍只有维护权限，后续仅按拥有证明处理，不扫描删除别人的库。

**验证矩阵与产物**：

| 起始状态→操作 | 预期与证据 |
|---|---|
| 无对象候选、A/B不同owner、A资源备份后受限→重放 | 原表计数先通过；A资源生命周期拒读，B不受影响；无服务/对象/队列副作用，回执不允许开放 |
| 完整空序列+正确genesis/checkpoint→复演 | 只证明空批次校验，不能据此证明历史删除完整或允许开放 |
| 缺checkpoint、错备份/epoch、断号/尾截断/改字段/未知版本/重复operation→复演 | 在创建库前拒绝，无成功水位 |
| 同批次重复重放、资源已删除/已有指令→重放 | 幂等；不回退政策，不重复创建指令或越owner写入；operation指向别的资源即使新目标缺失也拒绝；无清理目标仍不宣称已擦除 |
| 第二事件/事务提交失败→重放 | 整批回滚；服务保持不可开放；临时目标清理 |
| 原备份含附件→复演 | 创建前拒绝；不调用当前bucket恢复器，不返回字节 |
| 临时库存在→以非维护业务角色检查CONNECT | PUBLIC拒绝；业务角色不可连接；源superuser/维护成员的非测试配置拒绝 |
| 完整性成功、重放成功或清理失败→CLI/维护回执 | 明确区分验证范围；任何情况不产生开放许可；清理失败失败返回 |

R1-A冻结并评审本合同；R1-B实现输入验证、事务内重放及隔离消费者；R1-C执行后端全门禁、真实隔离PG dump/restore反例、CLI/maintenance回执及独立代码审查。所有结果只写BACKLOG。R2在线账本权威接入、R3全入口/身份/对象隔离、R4最终追赶与切换仍须独立SPEC就绪，不因R1通过关闭CORE-01。切换/回退不得把完整性校验当开放许可，也不能激活旧身份或旧预签名链接。

#### R2 在线独立账本与 journal-first 协议

覆盖FR/AC/US-10-01/02、BR-10-01及T-10-03/04。R2拆成有真实消费者的R2-A“独立事务及R1可信导出”和R2-B“在线写入、投影与全部消费者接入”。R2-A不等于在线接管：R2-B矩阵未逐项通过前，不把任何业务删除入口切到新账本，不启用部分双写或回退。R3仅延期恢复后的身份权威、独立恢复bucket/ACL/旧预签名处理；当前在线媒体、导出和外发保护属于R2。R4负责恢复目标追赶/切换，不是在线拒绝生效的前置。

**共同协议与不变量**：

1. 此版本只确认`deny_resource/resource_uuid.v1`，最小身份为owner/type/UUID，动作只收紧、不撤销。来源/连接/账户级限制、原生身份重采阻断另冻结合同；不能把新UUID当作旧资源tombstone的延续，也不宣称本版本已解决这些范围。
2. 在线命令须先在业务事务中验证调用者及资源归属、冻结稳定command，再结束业务事务；独立账本追加持久确认是deny的线性化点。全部对应消费者从该点起拒绝新的读取/准入，不等业务投影。账本成功而业务事务失败/进程中断，不补偿allow，按同operation修复。确认未知先用原operation读回，禁止生成新ID重发。未确认不能显示删除成功。
3. 命令身份为owner、operation、resource_type、resource_id、reason；occurred_at、sequence和摘要由账本首次分配，不参与重试输入。相同operation及command返回原事件，不同command冲突；不同operation指向同资源可分别保留真实请求。业务投影仍需幂等，不能以清理完成删除独立事件。
4. 不持业务行锁等待独立账本，不在跨库间模拟原子事务。R2-B选择每次准入直接查独立deny，或明确的owner水位保守门禁；若采用后者，head领先本地应用水位时整个相关owner范围拒绝，不能只过滤已成功投影的UUID。所有进程使用相同权威；未配置、不可用、pin不符、epoch回退、链断档、投影落后或依赖未知均拒绝，不把它们当空集合，不用TTL缓存保留allow。
5. 读取以最后一次当前权威检查作为返回准入点；媒体/object get前后、通知prepare后且send前、模型prompt冻结后且请求前、文件输出及结果提交前均重验完整ALL输入闭包。deny之前已准入的在途调用不宣称能撤回，结果返回/持久化仍需复核；尚未准入的排队任务不能沿用旧allow。R2-B必须把该并发合同转成逐入口反例，不以一次启动/claim检查代替。

**全部消费者保护边界与R2-B门槛**（未接入路径须关闭，不能默默使用本地许可）：

| 写入/消费者 | 保护身份及必须执行的边界 |
|---|---|
| 显式删除、到期、源确认删除 | 稳定command先确认账本，再更新拒读投影及清理回执；源暂时失败不造删除；到期批次中断后可重试 |
| 派生清理及物理处理器 | related_cleanup不得再随机私建无账本指令；冻结依赖目标与稳定operation；物理清理前确认独立deny，清理失败不释放deny；保留既有租约、有限重试及版本化对象保护 |

#### R2-A 独立事务及可信重放消费者 SPEC

**就绪与范围**：使用上面的确定资源合同，实现独立PG事务、严格pin和权限检查、完整链只读导出，并由新增维护CLI调用R1隔离复演，构成真实消费者。测试使用两个独立`hotkey_test_*`库及本轮专属运行角色；同机只证明独立回退域。线上故障域、独立凭据分发/备份、历史覆盖起点以及R2-B全路径反例未就绪时，不接管在线删除。此切片不改业务DDL，不增加仅供未来使用的抽象层，不部署或自动初始化账本。

**独立数据与唯一DDL**：`backend/sql/journal.sql`仅用于全新空的独立账本库；业务唯一schema仍为`backend/sql/schema.sql`，两者禁止互相导入。schema为`restriction_journal`，无业务FK或正文。唯一head行以slot=1固定，含ledger_id UUID、epoch正BIGINT、normalization_version=`resource_uuid.v1`、sequence非负BIGINT、digest小写SHA256；events主键sequence，UNIQUE(owner_id,operation_id)，保留R1字段，资源索引(owner_id,resource_type,resource_id)。head和事件只属于一个预先初始化的ledger/epoch，不支持在线重建/清空/截断；初始化由独立DDL所有者显式提供pin，运行角色遇空库必须拒绝，不能创建新genesis继续运行。

DDL撤销PUBLIC的schema/table/function权限。初始化和追加由SECURITY DEFINER函数完成，固定`pg_catalog,pg_temp`搜索路径（临时schema显式放末尾）、显式schema和内部类型引用；运行角色只能SELECT head/events及EXECUTE append，不能直接INSERT/UPDATE/DELETE/TRUNCATE、建schema/函数或重建epoch。导出角色只有SELECT，不授予append。DDL所有者不作运行角色；客户端检查当前角色不是superuser、不是head表所有者或其成员、没有直接修改表、数据库CREATE或任何持久schema的有效CREATE权限。账户授权/grant只由部署或本轮测试管理，应用不提升权限。

**追加事务**：函数输入包含预期ledger/epoch、稳定command；先锁head，再核对pin/规范化版本及operation。相同command返回原收据，不重新取now；冲突拒绝且head不变。新事件在同一PG事务分配head.sequence+1，以账本时间生成occurred_at，计算R1相同规范摘要，INSERT事件并更新head。使用事务内整数分配，禁止数据库sequence跳号。SQL与Python规范摘要交叉验证，失败/回滚不得推进head；并发新事件顺序由head行锁确定。BIGINT耗尽拒绝，不换epoch或截断。客户端提交/连接失败统一返回确认未知/不可用，调用方只可用原operation读回或重试；错误不输出SQL、command或连接串。

**只读与导出**：连接必须显式配置预期ledger_id/epoch，不能从当前库自报值自动信任；业务与账本数据库名必须不同，缺pin/缺head拒绝。一次REPEATABLE READ READ ONLY事务读取head及从genesis至head的事件，验证全部字段、连续序列、owner/operation唯一及摘要链；并发追加只能全部位于该快照之前或之后。在线账本及共用事件模型的sequence使用正BIGINT范围，不沿用R1事件模型原有的10000上限；10000条/16MiB只约束R1完整快照和checkpoint。在线账本可以超过10000条；导出超过10000条/16MiB时明确拒绝，不截断、不重建epoch。R1导出的checkpoint精确绑定已经校验的candidate backup/archive/schema及同一head；读取权威产生的pin仍不是历史覆盖、新鲜度或开放许可证明。

**CLI与减法**：增加`backup verify-journal`，从指定大写环境变量读取独立账本URL和维护隔离URL，显式传ledger/epoch；预检候选后，从独立权威生成完整快照和checkpoint，快照仅写本轮700临时目录下600文件，再调用R1并可靠清理。CLI不构造对象/队列/通知适配器、不输出连接串/command，固定不开放服务。R1人工pin复演仍有受控样本用途，不伪装成线上权威。把既有交换模型/规范摘要/输入验证移到evidence所属合同模块，backups直接消费；删除原backups重复归属文件，不保留兼容转发模块或第二套模型/哈希算法。不要删除仍承担投影、清理租约/回执的业务表或R1验证器。

# 06 持续监测与恢复

依据：[06 持续监测与恢复](../requirement/06-持续监测与恢复.md)；设计：[06 持续监测与恢复](../design/06-持续监测与恢复.md)。采用pm-execution的Card / Conversation / Confirmation拆解。本文定义交付工作，不登记进度，不授权提交推送、真实请求或数据库改造。

## 用户故事与工作拆解

### US-06-01 自然调度

**Card**：作为个人监测用户，当离开页面后仍要监测并能安全暂停时，我希望能够无需打开页面也按期监测，以便离开页面也可靠监测且随时停止。

**Conversation**：使用FR-06-01及BR-06-01确定范围。需要讨论的边界为“页面自动刷新及人工连续点击不能充当自然调度”；需对齐的业务输入合同为01状态、02执行、46预算，不以当前实现是否方便决定取舍。

**Confirmation**：AC-06-01使用固定输入“每小时调度，服务离线跨两窗口；恢复前主题已暂停；另一运行第1请求在途第2未发”，执行“恢复服务并核对窗口，再提交采集暂停和后续恢复”，核对“至少两轮自然运行形成回执；窗口无执行必须有跳过或漏轮原因。”，并验证对应反例。界面样本通过与真实业务验收分别记录。

### US-06-02 停止保证

**Card**：作为个人监测用户，当离开页面后仍要监测并能安全暂停时，我希望能够明确停止具体作用域，以便离开页面也可靠监测且随时停止。

**Conversation**：使用FR-06-02及BR-06-01确定范围。需要讨论的边界为“被停止作用域仍发起新请求、密集补发积压或绕过验证码均阻断验收”；需对齐的业务输入合同为01状态、02执行、46预算，不以当前实现是否方便决定取舍。

**Confirmation**：AC-06-02使用固定输入“每小时调度，服务离线跨两窗口；恢复前主题已暂停；另一运行第1请求在途第2未发”，执行“恢复服务并核对窗口，再提交采集暂停和后续恢复”，核对“领取前、请求前及重试前检查状态；恢复不复活已停止的旧运行。”，并验证对应反例。界面样本通过与真实业务验收分别记录。

### US-06-03 有界恢复

**Card**：作为个人监测用户，当离开页面后仍要监测并能安全暂停时，我希望能够按当前授权有界恢复失败工作，以便离开页面也可靠监测且随时停止。

**Conversation**：使用FR-06-03及BR-06-01确定范围。需要讨论的边界为“更换账号、代理或默认重发未知通知不得作为恢复方式”；需对齐的业务输入合同为01状态、02执行、46预算，不以当前实现是否方便决定取舍。

**Confirmation**：AC-06-03使用固定输入“每小时调度，服务离线跨两窗口；恢复前主题已暂停；另一运行第1请求在途第2未发”，执行“恢复服务并核对窗口，再提交采集暂停和后续恢复”，核对“恢复保留冻结输入及已提交材料；模型延后可追踪且不丢数据。”，并验证对应反例。界面样本通过与真实业务验收分别记录。

数据合同先行，数据提供方与消费入口可按同一合同独立开发；关联编号不是相互完成前置。任务按下表顺序推进；共享实现步骤只维护一次，各故事通过同序号FR/AC关联。任何发现的设计缺口先补同编号规格，再实施。

## 验收与发布门槛

本编号交付先满足FR-06和全部AC，质量方法见[11 质量评测与验收](../requirement/11-质量评测与验收.md)。核心需取得相应真实来源/模型/自然窗口/送达证据；辅助功能还须先确认用户价值与批次。读界面、工程样本、数据迁移和真实业务验收互不替代。

每项任务将实际结果、证据范围、未冻结参数、阻塞及下一步写入根目录BACKLOG；没有证据则保持待验收。实施需要的提交/推送与真实外部请求按AGENTS及已有授权单独处理。

# AIHOT 全量业务迁移执行计划

完整业务范围由 PRD046 定义，领域、接口、版本、事务和调度合同见 Design048。全部领域及 API/Worker/Web 入口已经接入；技术证据见 Acceptance001。本计划只保留仍需完成的真实验证与缺陷修复，不以静态检查关闭产品验收。

## 1. 剩余执行步骤

1. 在 `hotkey` 业务库冻结当前代码、来源版本、预算和任务基线，按 058 完成同库短窗演示，再逐来源扩围；人工重试和 HN 评论分别按 032/038 验证。
2. 在既有许可、费用与开关条件满足后，逐项验证六类来源、模型分析/精选/翻译、真实事件归并、报告质量、榜单与公告。真实 Codex 请求仍暂停，未满足条件的项目保留待验。
3. 分别核对真实 MinIO 媒体、公开出口的许可收紧与撤回、报告/vault、SMTP 接收和通知未知结果人工恢复；飞书暂缓。保留库恢复和独立灾备另取真实证据。
4. 按 009/014 和各领域 PRD 的原指标完成持续窗口与产品验收。真实失败先复现，再按所属 Design 修复，并完成受影响的静态、集成和浏览器检查。

## 2. 运行与修改边界

业务状态继续由所属领域持有，任务复用 Job/Outbox/Kafka。Schema、模型注册、路由、Worker、生成客户端和文档需要保持同一版本；修改遵守 AGENTS 的目录、事务与检查要求。

业务数据库名统一为 `hotkey`，集成测试只使用独立 `hotkey_test_<suffix>` 库并由执行者在结束后删除。完整 Schema 只用于新空库，存量业务数据按 PROJECT 的备份恢复合同处理。外部调用开关和预算上限保持有效；模拟材料、吞掉失败或手改生成客户端不能作为通过证据。

## 3. 收尾

动态进度只维护 BACKLOG，实际证据进入所属 Acceptance。退出要求仍为完整范围、原功能回归及所需真实验收全部通过；凭据、费用、来源、渠道和持续窗口缺口必须明确保留。历史移植步骤和源码对照从 Git 查询。

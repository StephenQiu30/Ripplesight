# Plan 041：内容、评论与分析结果阅读

交付用户从主题/来源进入帖子、父链评论、相关理由及异常的阅读路径，承接 FR-002-003/004/005、NFR-001-101/102/111；不能只有 Worker 和数据库结果。

2026-09-28 评论阅读切片：`listContentComments` 按 owner 可读帖子查询，默认线程根、指定根的各层回复或直接父节点分页，游标拒绝跨分支复用；无正文根若有可读后代，以不泄露过期正文的占位呈现。作品详情按根逐步加载回复，显示父节点缺口和本地页尾边界，不隐式受理 Job。受控 PostgreSQL、桌面/390px 浏览器及门禁见 Acceptance 002 EV-002-029。随后显式复采切片实现只读资格核对、受控按钮、固定操作标识与 409 状态反馈；受控旧帖浏览器完成一次 Job 受理并在重入页面看到频次禁用，见 EV-002-030。标注阅读切片又补按主题/正文版本切换、当前规则/提示词版本核对，以及 pending/failed/invalid/valid/无记录和历史结果区分，见 EV-002-031。作品列表筛选的受控验证见 EV-002-032；真实 HN 产品样本仍待验，`CHK-041-001/002/003` 不关闭。

| SPEC | 文件与契约 |
|---|---|
| SPEC-041-API-001 | 扩展 `backend/app/content/schemas.py`、`content/services.py`、`api/routers/content_records.py` 的 `/api/contents`、`/{content_id}`：列表支持 topic_id/source_key/时间窗/analysis_state，稳定游标；详情返回当前/请求版本、发布时间/发现时间依据、来源原生身份、采集Job和按主题的相关性/理由/摘要/情感/异常。新增 `GET /api/contents/{content_id}/comments`（listContentComments），默认按根、指定 `root_id` 按该根各层回复、指定 `parent_id` 按直接子节点分页，两个筛选互斥；游标只可用于当前帖子和分支，limit默认20最大100。无正文但有可读后代的根保留占位，只有可读观察才返回正文，不能把本地页尾冒充来源尾段；不在一次详情塞入全部评论。 |
| SPEC-041-UI-001 | 修改 `frontend/src/app/content/components/content-list.tsx`、`content-presenters.ts` 和 `[contentId]/components/content-detail.tsx`；新增详情内 `comment-thread-list.tsx`、`annotation-panel.tsx`。呈现真实null、原帖链接、按发现时间统计、父节点缺失/未取完、主题版本；标注 pending/failed/invalid/valid 分别显示，不能将无记录当不相关。 |
| SPEC-041-SEC-001 | 内容/评论按 owner 过滤；原链接仅允许http/https，正文以安全文本/经过限制的渲染展示，禁止执行外部HTML。详情查询不访问外部平台、不自动创建分析/评论Job。 |

评论区的显式“更新评论”操作调用038生成的runContentComments；点击固定operation_id并显示受理Job、频次/预算拒绝，连点不重复。只有来源具备且允许评论能力才显示操作，页面读取绝不触发采集。补 `comment-thread-list.test.tsx` 的点击/重放/禁用断言和浏览器旧帖复采验证，作为SPEC-041-UI-001与CHK-041-002的必需内容。

本次按钮切片在 `content/comments.py` 复用 POST 的只读资格核对，`content/schemas.py` 增加 `CommentRunReadinessView`，`api/routers/content_records.py` 增加 owner 鉴权的 `getContentCommentRunReadiness`；页面专属 `comment-refresh-action.tsx` 置于 `[contentId]/components/`，仅由作品详情使用。组件数据来自生成客户端，只覆盖加载/隐藏、可受理、预算/频次禁用、提交中、409/网络错误和受理跳转；不新增公共组件、数据表或隐式采集。GET 后的资格会变化，POST 仍是最终判定。测试先留路由 Red，再以隔离 PostgreSQL 和浏览器旧帖核对。

标注阅读切片保留现有 `GET /api/contents/{content_id}`，由 `analysis/reads.py` 提供 owner/版本限定的标注只读 DTO，`monitors/services.py` 提供主题名称与当前规则版本 DTO，`content/services.py` 在已验证可读的观察版本上组装详情；`content/schemas.py` 加 `analysis_topics/annotations`，运行时 OpenAPI 生成前端类型。页面专属 `[contentId]/components/annotation-panel.tsx` 从详情 DTO 选择主题和版本，显示当前 `valid/pending/failed/invalid/无记录` 与旧规则/提示词历史，不把旧版本相关性误作当前结果。不改表或分析受理；先保存详情缺字段的 Red，再做 PostgreSQL、组件与浏览器核对。

列表筛选切片沿用 `GET /api/contents`，增加 `topic_id/source_key/starts_at/ends_at/analysis_state`，时间窗成对且至多 31 天；发布时间空值以仍可读发现的最早时间代入并显示依据。主题归属从发现 Job 的固定 `configuration_ref` 读 DTO；分析状态由 analysis 领域按最新可读正文、当前主题规则和提示词版本批量投影，缺旧版新结果为 `missing`。游标绑定 owner 与筛选值，变化后拒绝复用。`content-list.tsx` 的页面专属控件用生成客户端加载来源、主题和列表，切换条件重置页码；无模型请求。先保存筛选、边界和游标失败测试，再做 PostgreSQL、组件及桌面/窄屏浏览器验证。

运行 B、C、F 门禁；结果归 M1 Acceptance 的 Plan 041。M2 复用页面时只显示一级评论范围；页面回退不改变持久资料。

| R2 | 已归属内容被排除后只能与其他未归并内容成组，后到的同事件内容永远无法加入已有事件，或另生重复事件 | 新增追加候选：未归并输入先与同 owner/topic、存在首次出现在72小时内当前成员的 active 事件（事件自身 first_seen_at 可早于72小时）的这些成员标题比对（共同关键词+相似度≥0.4），取最高分事件为目标；按目标事件分组，成员=新增未归并版本+该事件当前成员中最近的上下文版本，总数≤20且上下文≥1；`expected_event_revisions={event_id: revision}` 计入指纹。提示词说明上下文成员已属同一事件，模型判断新增内容是否同一事件并原样返回全部ID。确认事务：锁主题→候选→目标事件；事件须 active、revision 等于期望值、上下文成员仍为其当前成员、新增成员仍未归属，否则 `EventCandidateConflictError` 并标 failed；成功时新增成员 `added_revision=revision+1`、`assignment_origin=model`，事件 revision+1、`first_seen_at` 取较早值及其依据、`updated_at` 更新，不改标题/摘要；拒绝时事件不变。未命中任何事件的输入才进入原新建候选聚类。 |
| R3 | `cluster_candidates` 对每对标题单独 `SELECT similarity()`，同主题关键词几乎总重叠，O(N²) 次往返阻塞调度轮 | 以一条集合 SQL（`unnest` 版本ID/标题数组自连接，`a.idx < b.idx`，`similarity(...) >= 0.4`）返回相似对；72小时与共同关键词在 Python 侧过滤，保持并查集和分批语义不变。R2 事件比对同样用单条集合查询。 |
| R4 | 仅当 `now.minute % 30 == 0` 才扫描；调度轮间隔为30秒加轮耗时，长轮次会跳过整个目标分钟且无补扫 | 删除分钟门禁；`worker/scheduler.py` 的 events 扫描闭包保存进程内最近成功槽 `floor(now, 30min)`，当前槽不同则执行并在事务成功后记录，失败不记录以便同槽重试。`EventCandidateService.enqueue_due_in_transaction` 不再判断分钟。 |
| R5 | 执行器首事务发现成员变化时只抛 `event_input_changed`，候选永久停在 pending 且无错误码 | 首事务回滚后调用 `_mark_failed(candidate_id, owner, "input_changed", None)` 再抛失败；`event_candidate_not_pending` 保持现状。 |
